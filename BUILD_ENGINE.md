# BUILD_ENGINE.md — The Executable Implementation Manual

**Authorship: Fable 5, legacy extraction, 2026-07-09. Content preserved verbatim per the Legacy Extraction Protocol.**

**What this is.** The machinery I run when I turn an approved architecture into working, production-ready software — written as procedures another AI can execute. It is the seventh engine of the extraction set, and strictly additive to the six before it: **[M#]** points to [FABLE-MENTAL-MODELS.md](FABLE-MENTAL-MODELS.md); **FABLE §N** to [FABLE.md](FABLE.md); **DE §N** to [DECISION_ENGINE.md](DECISION_ENGINE.md); **PE §N** to [PLANNING_ENGINE.md](PLANNING_ENGINE.md); **RE §N** to [RESEARCH_ENGINE.md](RESEARCH_ENGINE.md); **AE §N** to [ARCHITECTURE_ENGINE.md](ARCHITECTURE_ENGINE.md); **OE §N** to [AI_ORCHESTRATION_ENGINE.md](AI_ORCHESTRATION_ENGINE.md). This document assumes and does not repeat: the naming/testing/refactoring/repository *philosophy* (FABLE §16–§19), the code-review methodology (FABLE §25), the debugging workflow (FABLE §24), interface and data design (AE §4, §5), decomposition (PE §3, AE §3), and how agents collaborate at runtime (OE §7, §8). Those establish the principles and the design; this engine is what happens *after the architecture is approved and before the thing is released* — the disciplined act of construction itself.

**Where this sits.** AE decides *what will be hard to change* and draws the seams. PE orders the work into phases with exit tests. This engine executes a phase: it takes an approved design and produces working software, verified, integrated, and stable. It ends where a release begins (the reproducible/reversible/observable gate, FABLE §20). The boundary matters — many build failures are really architecture decisions being made *during* construction by someone who didn't notice they'd crossed the line (§2, §11). When construction reveals the architecture is wrong, that is not a build task; it stops and returns to AE (§8.5).

**The one-sentence version.** Building is the disciplined conversion of a design into working software through the smallest safe increments, each one verified against reality before the next is begun — because the cost of a project is dominated not by typing but by rework, and rework is what discipline prevents.

# 1. Build Philosophy

**1.1 — What building software actually means.** Building is *making a design real* — and "real" means it runs, it does what it should at the edges as well as the center, and it can be changed by someone who wasn't there. The artifact is not the code; the artifact is *working behavior plus the ability to keep changing it safely*. Code that runs once but nobody can modify is not built software — it is a demo that will be rebuilt (§11). This definition governs everything downstream: every build decision is judged by whether it produces working behavior *and* preserves changeability, not by whether it produces code.

**1.2 — Why implementation is not typing code.** Typing is the smallest and cheapest part of building; for an AI it is nearly free, which makes the point sharper, not weaker. The expensive parts are: *deciding what to build in what order* (§3), *verifying it actually works* (§7), *keeping the growing system coherent* (§4), and *not building the wrong thing quickly* (§11). A model that treats building as typing will produce volume — plausible, abundant, and wrong at the edges — because the bottleneck [M10] was never typing. The discipline of building is almost entirely the discipline of *restraint and verification*: building the smallest right thing and proving it before building more. The fastest builders redo the least, and redoing little is a property of discipline, not speed (FABLE §12, slow is smooth).

**1.3 — How implementation differs from architecture.** Architecture decides the *irreversible* (AE §1.1 — the seams, contracts, invariants, the walls [M6]); implementation decides the *reversible* (the code inside the seams, the furniture). This division is the single most important thing a builder must hold: **implementation is free to be fast and rough where it is reversible, and must respect the architecture's decisions where they are not.** The two failure directions: a builder who re-litigates architecture during construction (rebuilding walls that were already decided, or worse, silently violating them — §11, drift), and a builder who treats reversible code with architecture-grade ceremony (gold-plating furniture, §11 overengineering). The builder's job is to execute the design faithfully at the walls and move fast everywhere else — and to *stop and escalate* (§8.5, AE) when construction reveals a wall was wrong, rather than quietly fixing it in the code.

**1.4 — How implementation creates knowledge.** Building is not just execution; it is the highest-fidelity *research* (RE) the project ever does — because the running system is the ultimate territory [M2], and construction is sustained contact with it. Implementation reveals what design could only assume: the integration that doesn't fit, the edge case the contract didn't cover (AE §4.3), the performance reality (§10), the dependency that behaves differently than documented (RE §5). This knowledge is *the most valuable output of building after the software itself*, and it flows in two directions: *back* to the architecture (construction findings that should update the design — AE §6, PE §7.6 re-planning triggers) and *forward* into durable state (findings, decisions, ratchets — OE §6.7). A build that produces working code but captures none of what it learned has wasted half its value, and its successor will rediscover the same edges (RE §1.5). The disciplined builder treats every surprise during construction as knowledge to record [M3, confusion is signal], not just an obstacle to code around.

# 2. Build Pipeline

Approved architecture in, production-ready implementation out. Seven stages. The pipeline executes *one phase* of a plan (PE §5); a multi-phase project runs it repeatedly, each iteration widening the working system. Stages compress for small work and run in full for substantial builds.

**Stage 0 — Preparation.** Before any construction: confirm the architecture is actually approved and understood (the seams, contracts, invariants the build must respect — AE §2.6); confirm the environment is real and works (the build tooling, the dependencies, the ability to run and test — RE §6.10, and *verified*, not assumed, [M1]); confirm the done-state for this phase (PE Stage 1, the falsifiable exit test §7.7). Preparation failures are the cheapest to fix and the most expensive to discover mid-build — a builder who starts before the environment runs will conflate "my code is wrong" with "the environment never worked" and waste hours in the wrong place.
*Checkpoint: can I build, run, and test an empty/trivial version right now? If not, fix that before writing anything real (§3.2 walking skeleton).*

**Stage 1 — Scaffolding.** Erect the structure the code will live in *before* filling it: the module boundaries the architecture specified (AE §3), the interfaces as contracts (AE §4, defined before implementations), the walking skeleton (§3.2) that runs end-to-end doing nothing. Scaffolding makes the architecture *concrete and testable* before behavior exists — so integration risk (AE §8, the seams fitting) is surfaced at the cheapest possible moment (PE §5.3, the vertical slice principle). A build that scaffolds late discovers its integration problems late, when they are expensive (§11).
*Checkpoint: does the skeleton run end-to-end, with every seam connected but hollow? Does the structure match the approved architecture (§4.5)?*

**Stage 2 — Implementation.** Fill the scaffold with behavior, in the order §3 dictates (core before polish, dependencies before dependents, risk-retiring first). This is the stage people think building *is*; it is one of seven, and it goes smoothly exactly to the degree the prior stages were done well. Implementation proceeds in *small verified increments* (§6) — each increment is built, verified (Stage 3, interleaved not deferred), and only then is the next begun.
*Checkpoint: is each increment verified before the next starts, or am I accumulating unverified code (§7, the deferred-verification failure)?*

**Stage 3 — Verification.** Continuous, interleaved with implementation, not a phase after it (§7). Each increment is verified at the appropriate level (compile → static → runtime → behavior → integration, §7.1–7.6) before it's trusted. Verification is *by exercising, not by inspecting* (FABLE §17, §7.4) — the code is run and its behavior observed, not read and assumed correct. This is the stage whose skipping produces the "looks right, isn't right" failures that dominate real defects (§11 incomplete implementation, FABLE §33.3 declaring victory early).
*Checkpoint: has this increment's behavior been observed, at the edges as well as the center? Would the verification catch the bug this code could plausibly have (OE §8, RE §9.7)?*

**Stage 4 — Integration.** Combine the increment with the rest of the system and verify the *whole* still works (§7.6). Integration is where independently-correct pieces reveal they don't fit (AE §8, the seams) — so it happens continuously (every increment integrates) not at the end (the big-bang integration that fails catastrophically, §11, PE §5.3). For parallel builds (OE §7, §3.2 isolated), integration is the deliberate reconvergence the orchestrator planned (OE §7.5, §7.6 conflict resolution).
*Checkpoint: does the whole system still pass its tests after integrating this? Did integration reveal a contract mismatch that's really an architecture finding (§1.4, §8.5)?*

**Stage 5 — Stabilization.** Once the phase's behavior is built and integrated, harden it: handle the edges the happy path skipped (AE §4.3, total contracts), make failures loud and safe (AE §8.1), confirm it behaves under the real conditions (not just the test fixture — RE §Stage 6 reality contact). Stabilization is the difference between "works in the demo" and "works" — and it is the stage most often cut under time pressure, producing software that ships its edges as latent incidents (§11 fragile code).
*Checkpoint: does it handle empty/huge/malformed input, each dependency failing, the second run (idempotence)? Are failures loud, not silent (AE §8.1)?*

**Stage 6 — Completion.** Verify the phase against its done-state (PE Stage 1, §7.7 — checked against the goal, not the plan, FABLE §1), update the durable record (docs, decisions, the component registry — AE §6.2, FABLE Law 8, in the same session as the change), capture what construction taught (§1.4, OE §6.7), and confirm the campsite is clean (§13.4 — no dead code, no debt-without-a-ticket, no half-finished increment). Completion is a *gate*, not a feeling (§7.7): the phase is done when its exit test passes, observed, and its record is current — not when the code "seems done."
*Checkpoint: does the exit test pass, freshly run and observed? Is the durable record true as of now? Could a stranger continue from here ([M18])?*

**Standing discipline across all stages — verify before proceeding.** The pipeline's spine is that *no stage proceeds on unverified output from the last*. This is the build-time expression of the whole methodology's core: reality contact before building further [M2, M5], because the cost of building on a wrong foundation compounds with everything above it (AE §1.5). A builder who races ahead of verification is not faster; they are accumulating a debt of unverified code that will be paid, with interest, at integration or in production (§11).

# 3. Implementation Strategy

The order and shape of construction — the decisions that determine whether a build proceeds smoothly or hits dead ends. PE §3 (decomposition) and PE §5.3 (vertical slices) establish the planning-side; this is the *build-side execution* of those principles. The governing principle: **build the riskiest, most-connective, load-bearing thing first, prove it works end-to-end, then widen — so that dead ends are hit early and cheap, when little is built on them.**

**3.1 — Vertical slices (execution).** Build one thin complete path through all the layers before building any layer fully (PE §5.3). In execution terms: pick the single most representative operation, implement just enough of every component to make that one operation work end-to-end, verify it, *then* widen to the next operation. The value is that a working vertical slice proves the architecture's seams actually fit (AE §8) and surfaces integration reality (§1.4) while the system is still small enough to change cheaply. The discipline is *resisting the horizontal urge* — the natural pull to "finish the data layer first, then the logic layer" — which defers all integration risk to the end (§11, PE §5.3). Width comes after depth: one thing working completely, then many.

**3.2 — Walking skeletons.** The first vertical slice is a *walking skeleton* — the whole system's structure, running end-to-end, doing the minimum real thing (often almost nothing). It is scaffolding (§2 Stage 1) that *executes*: every component present but hollow, every seam connected but trivial, the build-run-test loop working. The walking skeleton is built *first, before any feature*, because it proves the riskiest architectural assumption (do the pieces connect and run at all?) at the cheapest moment, and because it establishes the environment (§2 Stage 0) that all further work depends on. A project without a walking skeleton builds its components in isolation and discovers at integration that they were never going to connect (§11).

**3.3 — Interfaces first.** Within any component, define the interface (the contract, AE §4) before the implementation. This lets callers be built against the contract in parallel (OE §3.2) without waiting for the implementation, lets the implementation be swapped freely behind the stable interface (AE §4.1, §6.4), and forces the design question ("what does this promise?") to be answered before the construction question ("how does it work?"). Interface-first is the build-time enforcement of the seams the architecture placed — the interface *is* the seam made concrete. Implementations built before their interfaces tend to leak their internals into the interface (AE §10.3, leaky boundaries), because the interface gets reverse-engineered from the implementation rather than designed for the caller.

**3.4 — Core before polish.** Build the load-bearing core [M6] — the essential behavior, the hard part, the thing everything else depends on — before the polish (error messages, edge-case niceties, convenience features, aesthetics). Because: the core is where the risk is (if the core can't be built, the polish is irrelevant, §3.6), the core is what everything else is built against (dependency order §3.5), and polish applied before the core is proven is polish that may be discarded when the core forces a change (§11 wasted work). Core-first also means the project always has a working, valuable center early — so if it's stopped or re-scoped (PE §5.4), what exists is the important part, not a beautifully-polished shell around an unbuilt center.

**3.5 — Dependency ordering.** Build dependencies before dependents — a component that others rely on is built and verified before the components that rely on it, so they're built against something real, not a moving target. This is the topological order of the dependency graph (PE §4.1), and it's the default sequence *within* the risk-first ordering (§3.6): among things at similar risk, build in dependency order. Where a dependency cycle appears (A needs B needs A), it's a signal the decomposition is wrong (AE §3.4, §10.2 — a cycle means those are really one component) and should be re-cut before building, not built around (which welds them together permanently).

**3.6 — Feature and risk ordering.** Order the build so the *riskiest, most-uncertain thing comes first* (PE §5, §6 — risk-first), overriding dependency order when they conflict: if the roof's feasibility is uncertain, prove the roof before laying the foundation, because discovering the roof is impossible *after* building the foundation wastes the foundation. Within the risk-retiring order, build in dependency order (§3.5) and value order (the most important features early, so banked value is high, PE §5.4). The synthesis: *riskiest-first, then dependencies-before-dependents, then most-valuable-first* — a build ordered this way retires uncertainty early, always has a working valuable core, and never builds atop something unproven.

**3.7 — Incremental evolution.** The system grows by small increments (§6), each one taking the working system to a slightly larger working system — never a large leap from working to broken-for-a-while to working-again. Each increment is a complete small step: built, verified (§7), integrated (§2 Stage 4), leaving the system working. This is trunk-stays-green (FABLE §19) applied to the moment-to-moment act of building: the system is *always* in a working state, and every increment moves it from one working state to another. Increments that leave the system broken "temporarily" are how a build loses the ability to tell whether it's progressing (§6.5, §11).

**3.8 — How to avoid dead ends.** A dead end is construction that must be thrown away because it hit an impossibility or a wrong assumption late. Avoid them by: *risk-first ordering* (§3.6 — hit the impossibility early, when little is built on it); *walking skeleton* (§3.2 — prove the whole connects before filling it); *spikes for uncertain feasibility* (RE §Stage 6, PE §6.3 — a throwaway experiment settles "is this possible" before the real build commits); *touching reality continuously* (§1.4, §7 — so a wrong assumption is caught at the increment that made it, not ten increments later); and *building against verified interfaces* (§3.3 — so a component doesn't discover at integration that its dependency doesn't behave as assumed). The meta-move: *the cheapest experiment that could invalidate the approach runs first* [M5] — dead ends are cheap when hit early and catastrophic when hit late, so the whole strategy is arranged to hit them early.

# 4. Repository Evolution

How the repository grows over a build and across a project's life. FABLE §19 establishes the philosophy (trunk stays green, small commits with why, kill dead code, structure follows seams, machine-enforced hygiene); AE §3 establishes the structural decomposition; this section is the *build-time practice* of growing a repository healthily. The governing principle: **the repository's structure should at every moment be a truthful map of the architecture, and its history a truthful record of decisions — so a stranger can navigate the structure and reconstruct the reasoning ([M18], AE §6.2).**

**4.1 — How repositories should grow.** By accretion along the architecture's seams (AE §3), never by sedimentation. Each new capability lands in the structural place the architecture designated for it, with its boundaries respected — so the repository at size N looks like a larger version of itself at size N/2, not a different, tangled thing. Growth that ignores the architecture produces a repository whose structure lies about its design (AE §6.3, drift) — the map [M2] and territory diverge, and every navigator is misled. The build-time discipline: *before adding something, know where in the structure it belongs, and if there's no right place, that's an architecture question (§8.5), not a license to put it anywhere.*

**4.2 — Folder organization.** Folders mirror the architecture's decomposition — by capability, and where the architecture cuts by trust or failure (AE §3.1), by those too. The test (RE §6.3, applied forward): a stranger looking for a concern should find it in one guess, because the structure names where things live. Organize by *what things are / what they do* (the domain, the capability), not by *what technical kind they are* (grouping all the "controllers" together regardless of domain) — because change arrives by domain, so domain-grouping keeps each change local (AE §3.5 cohesion), while kind-grouping scatters every change across the tree. The folder structure is documentation that can't drift as easily as prose (it's enforced by where files actually are), so make it carry real information about the design.

**4.3 — Naming (in practice).** FABLE §16 holds the philosophy (name for the reader, make wrong usage look wrong, one name per concept, rename when the name lies). The build-time practice: name at the moment of creation with the reader in mind [M18], and *rename the instant a name stops being true* (a rename is cheap in a versioned repository and confusion compounds daily). Consistency across the repository is a build-time obligation — if the domain calls it a "capability," every file, folder, function, and comment calls it a capability, never drifting into "plugin" or "module" for the same thing (FABLE §16, one name per concept), because each synonym doubles the reader's vocabulary load and eventually causes a real bug when two things thought distinct turn out identical.

**4.4 — File ownership.** Every file has a clear owning concern (AE §3.3, single ownership applied to files) — it belongs to one component, one capability, one bounded context. A file that serves several concerns is a cohesion failure (AE §3.5) and a coupling risk (changes for unrelated reasons collide in it). In multi-agent builds (OE §7.6), file ownership is also *write ownership* — one agent owns writes to a file, or writers are isolated (OE §3.5, AE §9.6), to prevent the write-conflict failure. The build discipline: *each file's purpose is stateable in one sentence; a file that needs "and" to describe its purpose is two files.*

**4.5 — Module boundaries (in practice).** The modules the architecture specified (AE §3.2) are enforced during the build: the boundaries are real (the module exposes only its interface, hides its internals — AE §4.1, §10.3), the dependencies point the architecture's direction (§3.5, and cycles are caught as decomposition errors AE §3.4), and — where possible — the boundary is *machine-enforced* (FABLE §19, the build fails if a module reaches into another's internals) rather than maintained by vigilance [M12]. A module boundary respected only by everyone-remembering is already eroding; a build that lets modules reach into each other's internals "just this once" has begun the drift to a big ball of mud (AE §10.7, §10.8).

**4.6 — Refactoring strategy (build-time).** §8 holds refactoring in full; here, the repository-growth aspect: refactor *opportunistically and locally* as you build (the campsite rule, FABLE §18 — leave the code you touched slightly better), in *separate commits from behavior changes* (FABLE §18, §8.2 — so each is reviewable and bugs are attributable), and *when the structure blocks the change you're making* ("make the change easy, then make the easy change," §8.1). The repository stays healthy through continuous small refactoring, not periodic big cleanups — because debt that's paid continuously never compounds, and cleanups deferred to "later" arrive as rewrites (§8.4).

**4.7 — Repository hygiene.** The repository contains only things that are *true and live* (FABLE §19): no commented-out code (delete it, the version history remembers), no dead code (§7 of RE, remove it once confirmed dead), no stale docs (fix or delete them, a wrong doc is worse than none), no debt without a ticket-and-trigger (§4.8). Hygiene is maintained *continuously* (each commit leaves the repository clean) and *by machine where possible* (formatters, linters, dead-code detectors as ratchets [M12], FABLE §19 — because hygiene maintained by vigilance decays the week attention moves). A clean repository is not aesthetics; it's that every lie in the repository (dead code, stale doc, misleading name) costs every future reader, compounding [M15].

**4.8 — Technical debt management (build-time).** PE §7.3 holds the strategy; the build practice: when a shortcut is taken (legitimately, under time pressure, FABLE §12), it's *recorded with its trigger* in the same act — what was skipped, why, and what forces its repayment ("before this handles real user data," "when the second provider is added"). Unrecorded shortcuts are not debt, they're landmines [M12]. Debt on furniture [M6] can live long; debt on a wall or a seam must be flagged as blocking, because it compounds structurally (everything built on the shortcut inherits it). The build discipline: *a shortcut and its debt-ticket are one action* — you don't get to take the shortcut without recording the debt, because the recording is what makes it recoverable rather than a future ambush.

**4.9 — Long-term maintainability.** Every build-time choice is weighed by its ten-year carrying cost [M15], not just its construction cost — because maintenance dominates a system's total cost (FABLE §21) and the builder is the one who sets it. The maintainable build produces: code a stranger can read (§5), structure that maps the architecture (§4.2), history that records the why (§4, AE §6.2), tests that pin behavior (§7, FABLE §17), and no undocumented shortcuts (§4.8). The unmaintainable build produces working code that no one can safely change — which by §1.1 is not built software at all. The builder serves the year-three maintainer (AE §2.4) as much as the present feature, because the maintainer's cost is the larger one and it's set now.

# 5. Coding Methodology

How the actual code is written, inside the reversible space the architecture leaves free (§1.3). FABLE §16 (naming) and §25 (review) and AE §4 (interfaces) establish the standards this must meet; this is the *writing discipline* that meets them. The governing principle: **write code for the reader who will change it under pressure with no context [M18] — which means minimize what they must hold in their head at once, and make the code's structure mirror the problem's structure so understanding transfers.**

**5.1 — How I write code.** In small, verified increments (§6, §7) — never a large volume before the first verification, because unverified volume is unverified whether it's ten lines or ten files, and the larger it is the more expensive the eventual correction. Write the *simplest thing that correctly does the job* (the boring maximum, DE §3.3) — not the cleverest, not the most general (§11 overengineering, premature abstraction), not the most defensive-beyond-need. Write it to be *read*: the code is read far more than written, and by strangers (including future-self), so readability is the dominant virtue after correctness. And write it to *match the surrounding code* — a build's code should read as if one mind wrote it (consistent idiom, naming, structure, comment density), because inconsistency forces every reader to re-learn the local dialect file by file.

**5.2 — How I structure functions.** A function does *one thing*, at *one level of abstraction*, with a name that says what it does (FABLE §16). Its length is bounded by comprehensibility, not a line count — a function is too long when you can't hold its whole behavior in your head at once (the same session-size principle PE §3 applies to tasks, applied to functions). Its signature is honest: it takes what it needs and returns what it produces, with no hidden inputs (globals) or hidden outputs (side effects) the signature doesn't reveal (§11, hidden dependencies; AE §10.8). Prefer functions that are *total* (defined for all their inputs, AE §4.3) and *pure* where possible (output depends only on input, no side effects) because pure total functions are the easiest thing in software to understand, test, and reuse.

**5.3 — How I structure classes / stateful units.** A stateful unit (class, module-with-state) exists to *bundle state with the operations that maintain its invariants* — its justification is that it protects an invariant (AE §2.6) that would be unsafe to maintain scattered. It exposes operations, hides state (AE §4.1 — the state is an internal, the operations are the contract), and is responsible for keeping its own invariant true at all times (so no external code can put it in an invalid state — this is the whole point of bundling). A stateful unit that's just a bag of data with getters/setters and no invariant to protect is not earning its structure — it should be plain data. The discipline: *state is a liability* (it's what makes behavior depend on history, §5.7) — bundle it only where an invariant requires it, minimize it, and make the unit that owns it responsible for it.

**5.4 — How I structure modules.** A module is a cohesive set of functions/units serving one capability, exposing a narrow interface and hiding its internals (§4.5, AE §3, §4). Its internal structure is free (the architecture doesn't reach inside, §1.3), but its interface is a contract it must keep (AE §4.7). The module is organized so its *public surface is small and its internals are private* — the reader of a caller needs to understand only the interface, and the reader of the module needs to understand only its internals, and the boundary between those is where the module earns its keep (it caps how much anyone must understand at once). A module whose internals leak into its interface (AE §10.3) has failed this — it forces callers to understand its guts.

**5.5 — How I structure APIs.** AE §4.2 holds API design; the coding practice: implement the API to *keep the promise the contract makes* (AE §4.3), handle every input the contract accepts (including the awkward ones — total, §5.2), fail in the way the contract specifies (loud, §8.1, AE §8.1), and never let an internal change leak through the API surface (§4.5, backward compatibility AE §4.7 once it has callers). The API implementation is where the architecture's replaceability promise is kept or broken — an API implemented to expose its internals welds callers to this implementation (AE §10.5); one implemented behind a clean contract lets the implementation be swapped freely (AE §6.4). Code the API as the seam it's meant to be.

**5.6 — How I structure configuration.** Configuration is where behavior is parameterized without code change — and it charges rent [M15] for every option (each is a thing to document, test the combinations of, and reason about, forever). So: *add a config option only when a real user really varies it* (§11 config sprawl, DE §3.2 delete-the-requirement), keep the sources of truth few (one config surface, not env-and-file-and-flags with precedence rules nobody remembers — RE §7.7), make defaults safe (AE §8.6 secure-by-default) and sensible (the default is what runs when nobody chose, i.e. most of the time), and keep secrets *out* of config-in-version-control (AE §8.6, Law 9 — secrets in a dedicated store, referenced by config, never embedded). Configuration is furniture that pretends to be flexibility; most proposed options are speculative (§11) and should be a fixed decision until a real need forces the option.

**5.7 — How I minimize complexity.** Complexity is what makes code hard to understand and change, and it comes mostly from *state* (behavior depending on history, §5.3), *coupling* (change propagating, AE §3.4), and *conditional depth* (many interacting branches). Minimize each: prefer stateless/pure where possible (§5.2); depend on contracts not internals (§4.5); flatten conditionals (handle cases early and return, rather than nesting). The deepest complexity-minimization is *not building the thing* (§11 — the simplest code is the code that doesn't exist, DE §3.2) and *deleting* (FABLE §18, the best refactoring) — every line not written and every line removed is complexity that charges no rent. Essential complexity (the problem is genuinely hard) is respected and isolated (put it behind a clean interface, AE §4, so it's contained); accidental complexity (the solution is harder than the problem, §11 overengineering) is eliminated. The test: *is this code more complex than the problem it solves?* If yes, it's accidental complexity — simplify.

**5.8 — How I maximize readability.** Readability is the code communicating its intent to the stranger [M18]. The practices: *names that mean things* (FABLE §16 — the cheapest and highest-leverage readability tool); *structure that mirrors the problem* (so understanding the domain transfers to understanding the code); *comments only where the code can't speak* (FABLE §25 — comments state the *why* and the constraints the code can't express, never narrate the *what* the code already shows, which is noise that rots); *consistency* (§5.1 — one dialect, so no re-learning per file); and *locality* (the things that change together are near each other, AE §3.5, so a reader doesn't chase a change across the tree). Readability is not decoration — it is the property that determines whether the year-three maintainer can change the code safely (§4.9, §1.1), so it's a first-class build obligation, not a nicety.

# 6. Incremental Development

How work advances in small steps that always leave the system working — the temporal discipline of building. §3.7 establishes incremental evolution as strategy; this is the *practice* of it, including the messy realities (prototypes, temporary code, unfinished work). The governing principle: **advance in the smallest steps that each leave the system in a working, verified state — so progress is always real, always measurable, and never a large leap across a broken chasm.**

**6.1 — How features evolve.** A feature grows from a walking skeleton of itself (§3.2) — the thinnest version that does the core thing end-to-end — widening increment by increment (§3.1), each increment verified (§7) and integrated (§2 Stage 4) before the next. The feature is *usable at every step* (the core works from the first increment, §3.4), just less complete — so it can be stopped, shipped, or re-scoped at any increment with what exists being valuable (PE §5.4). Features that evolve this way never have a "it doesn't work yet, trust me" phase; they work, narrowly, from early, and broaden.

**6.2 — How prototypes evolve.** A prototype is built to *learn* (RE §Stage 6, DE §8.2 explore mode), and the cardinal rule is *label it as disposable and dispose of it* (§12.1, [M5], the demo trap). A prototype answers a question (is this feasible? does this feel right? does this API work?) and its output is the *answer*, not the code — the code is thrown away and the real thing built with the knowledge gained. The catastrophic path is the prototype silently becoming production because it happened to work (§11) — production-grade quality was never built into it, so it carries hidden fragility into the real system. When a prototype's approach is validated, the transition to production is an explicit decision (DE §10.3, a T-tier decision) to *rebuild it properly*, not to promote the prototype.

**6.3 — How temporary code becomes permanent (and how to prevent it).** "Temporary" code becomes permanent by default — the temporary workaround, the quick hack, the "I'll clean this up later" — because there's no forcing function for the cleanup and the code works well enough (FABLE §34, the eternal TODO). Prevent it by *never writing code that depends on being cleaned up later* without a debt-ticket-and-trigger (§4.8): either it's acceptable as-is (then it's not temporary, own it), or it has a recorded trigger that forces its replacement (§4.8, PE §7.3). Temporary code with no trigger is permanent code that's lying about being temporary — and it's permanent code that was built to a lower standard because it was "temporary," which is the worst combination.

**6.4 — How experiments are isolated.** Experiments (spikes §3.8, prototypes §6.2, "let me try this") are isolated from the working system so they can't destabilize it and can be cleanly discarded (DE §8.2). Isolation means: a separate branch/workspace (AE §9.6, worktree — so the experiment doesn't touch the working trunk, FABLE §19), a clear label (this is an experiment, not production), and a defined disposal (the experiment ends in a decision — adopt-and-rebuild, or discard — not in silent merge). Isolated experiments make the working system *safe to experiment near* — the trunk stays green (FABLE §19) while exploration happens off to the side.

**6.5 — How unfinished work is handled.** Unfinished work is the risk state of building — code that's started but not verified/integrated (§2 Stage 3/4), the increment in progress. Handle it by *keeping it small and finishing it before starting more* (FABLE §5, finish-beats-start; §3.7) — the smaller the unfinished increment, the less risk it carries and the sooner it's resolved. Unfinished work that must be paused (context boundary, priority shift) is *checkpointed* (OE §11.4) — its state written to durable form so it can be resumed cleanly, or backed out so the system stays clean (FABLE §19, trunk green). Never leave unfinished work in an ambiguous state (is this done? is this trusted? does this work?) — the ambiguity is what makes a build lose track of its own progress (§11 incomplete implementation).

**6.6 — How momentum is maintained.** Momentum in building comes from *always having a working system and a clear next increment* (PE §7.1). The working system (trunk green, §3.7) means progress is real and visible — every increment banks value (PE §5.4). The clear next increment means no time is lost re-deciding what to do (FABLE §5) — the next step is unambiguous because the strategy (§3) ordered the work. Momentum dies when the system is broken (can't tell if you're progressing), when the next step is unclear (time lost deciding), or when unfinished work accumulates (§6.5, charging context rent). The disciplines that maintain momentum are the same ones that ensure quality — small verified increments, working trunk, clear ordering — which is why disciplined building is also *faster* building (FABLE §12).

# 7. Build Verification

How implementation is continuously proven correct — the discipline that separates "looks right" from "is right." FABLE §17 (testing philosophy) and §24 (debugging) and OE §8 (verification architecture) establish the principles; this is the *build-time verification practice*, the layered checking interleaved with construction. The governing principle: **verify continuously, at the cheapest sufficient level, by exercising not inspecting — because the gap between "looks right" and "runs right" is where most defects live, and it's only closed by observing actual behavior [M2].**

**7.1 — Compile validation (does it build?).** The cheapest, fastest check: does the code build/parse/type-check at all? Run it *first and constantly* — after every increment, because a compile failure is unambiguous and cheap to fix immediately and expensive to untangle after ten more increments piled on. For typed languages, the type-check is a free ratchet [M12] catching a whole class of errors (wrong shapes, missing cases) before any execution. Compile validation is necessary but weak — it proves the code is *well-formed*, not *correct* (§7.4) — so it's the floor, never the ceiling.

**7.2 — Static validation (does it smell right?).** Linters, static analyzers, formatters, dead-code detectors, security scanners — machine checks that catch defect-classes without running the code (FABLE §19, machine-enforced hygiene). Run them automatically (a ratchet, [M12]) so they catch their classes every time without vigilance. Static validation catches the mechanical (style inconsistency §5.1, obvious bugs, dead code §4.7, some security issues AE §8.6) cheaply and consistently — freeing human/AI review (FABLE §25) to focus on what machines can't check (is it correct? is it the right design?). Static validation is necessary and weak like compile validation — it proves the absence of *known bad patterns*, not the presence of *correct behavior*.

**7.3 — Runtime validation (does it run without falling over?).** Run the code and see if it executes without crashing, erroring, or misbehaving grossly. This is the first level that touches reality [M2] — the code actually runs, on actual inputs, in the actual environment (§2 Stage 0). Runtime validation catches what static analysis can't (the null that actually arrives, the file that actually isn't there, the dependency that actually behaves differently — RE §5). It's necessary but *still weak* on its own — code can run without crashing and still produce wrong answers (§7.4), which is the more common and more dangerous defect.

**7.4 — Behavior validation (does it do the right thing?).** The level that matters most and is most often skipped: does the code produce the *correct behavior*, verified by *observing it*, at the *edges* as well as the center? This is verify-by-exercising (FABLE §17) — drive the actual behavior with real inputs (empty, huge, malformed, the happy path, the failure paths) and observe the actual outputs, rather than reading the code and concluding it's correct (the "looks right" trap, FABLE §33.3). Behavior validation is where "declaring victory early" is prevented (FABLE §33.3) — the code isn't done when it compiles or runs, it's done when its behavior is *observed* correct across its contract (AE §4.3). The test of good behavior validation: *would it catch the bug this code could plausibly have?* (OE §8, RE §9.7) — a validation that only exercises the happy path catches nothing at the edges, where the bugs are.

**7.5 — Regression prevention.** Every bug found and fixed is *pinned by a test* (FABLE §17, §24 — the fix without the test will return, one of the most reliable regularities). The pinning test is the ratchet [M12] that converts a fixed bug into a permanently-fixed bug — it fails if the bug ever returns, catching the regression at the increment that causes it rather than in production. Beyond bug-pinning, the accumulated tests form the regression suite that lets the build *change safely* — every increment runs the suite, so a change that breaks existing behavior is caught immediately (trunk-green, §3.7). Regression prevention is what makes a growing system safe to keep changing (§1.1) — without it, every change risks silently breaking something built earlier, and the fear of that eventually freezes the system.

**7.6 — Integration validation.** Verify that the pieces work *together*, not just individually (§2 Stage 4, AE §8). Integration validation exercises the seams (AE §4 — the contracts between components actually holding, the data actually flowing correctly across boundaries AE §4.5) — because independently-correct components routinely fail to integrate (the contract was interpreted differently on each side, the data format mismatched, the assumption diverged, RE §6.8). Run integration validation *continuously* (every increment integrates and is validated, §3.7) not just at the end (the big-bang integration that fails catastrophically, §11, PE §5.3). Integration validation is where the vertical-slice strategy (§3.1) pays off — a thin slice validated end-to-end proves the integration early and cheaply.

**7.7 — Completion criteria.** The phase/feature is complete when its *done-state exit test passes, freshly run and observed* (PE Stage 1, §2 Stage 6, §7.4) — not when it "seems done," not when the code is written, not when it compiles. The completion criterion is *falsifiable and behavioral* [M19] — a specific observable condition a stranger could check ("delete the index, run rebuild, search still works"; "unplug the network, still get answers"), not a feeling of doneness. This is the anti-Goodhart discipline [M19]: the criterion is the actual desired behavior, not a proxy (tests-pass is a proxy; behavior-observed-working is closer to real). Completion is a *gate*, checked against the goal not the plan (FABLE §1 step 7) — the phase delivers what was actually needed, verified, or it's not complete regardless of how much code was written.

**7.8 — Scaling verification to stakes.** Not everything gets the same verification depth (OE §8, §13.8; DE §2 tiers): the walls [M6] (data formats, security boundaries, irreversible operations, public contracts) get exhaustive verification including edge and failure cases and adversarial checking (OE §8.2); the furniture (reversible internal code) gets proportional-to-risk checking, often just runtime + a behavior check. Uniform verification wastes rigor on furniture and under-verifies walls; stakes-scaled verification concentrates the effort where being wrong is expensive [M8, M16]. The builder's judgment: *what does being wrong here cost, and verify to match* (OE §13.8) — the same wall/furniture classification (§1.3, [M6]) that governs how carefully to build governs how carefully to verify.

# 8. Refactoring

Changing the structure of working code without changing its behavior — the discipline that keeps a growing system changeable. FABLE §18 holds the philosophy (refactor with purpose not for beauty, separate from behavior change, rule of three, strangle don't rewrite, campsite rule, deletion is best); AE §6 holds architectural evolution; this section is the *build-time refactoring practice*. The governing principle: **refactor to enable a change you're about to make or to pay a debt that's come due — never for beauty alone — and always as a behavior-preserving step verified green before and after.**

**8.1 — When refactoring should happen.** The legitimate triggers (FABLE §18): *you're about to make a change and the current structure makes it hard* ("make the change easy, then make the easy change" — refactor first to enable, then change) — the most common and valuable trigger; *the rule of three fired* (a third duplication appeared, now the true abstraction is visible [M13]); *a name lies* (§4.3, rename to restore truth); *a debt came due* (§4.8, its trigger fired, pay it now); *a seam is missing where change keeps arriving* (retrofit the seam, AE §6.6). Refactoring is *triggered by a need*, always — it's a means to changeability, not an end.

**8.2 — When refactoring should not happen.** *"This could be cleaner"* is not a trigger (FABLE §18 — clean is a means, not an end; beauty-refactoring is unbounded and risks working code for no functional gain). *Refactoring code you're not otherwise touching* (a cleanup crusade through unfamiliar code, §11) — high risk of breaking what you don't understand [M9], and it bloats the change, burying the real work. *Refactoring and changing behavior at once* (§8.3 — makes both unreviewable). *Refactoring under deadline pressure on the critical path* when the current structure works (the refactor's benefit is future changeability, which the deadline may not reach — defer it with a debt-ticket §4.8). The discipline: *refactoring has a cost and a risk, so it must buy something real* — enabling a change, paying a due debt, restoring truth. Refactoring that buys only aesthetics is spending risk for nothing.

**8.3 — How to safely refactor.** The universal safe procedure: *tests green before* (the behavior is pinned, §7.5 — so you can prove you didn't change it); *refactor in small behavior-preserving steps* (each step provably changes structure not behavior); *tests green after each step* (confirming behavior preserved); *separate commit from any behavior change* (FABLE §18 — the refactor commit provably does nothing functional, tests unchanged and green, so it's trivially reviewable and any later bug is attributable to the behavior change, not the refactor). The precondition is *the behavior must be pinned by tests before you refactor* — refactoring without a test net is not refactoring, it's rewriting-and-hoping, because you can't prove you preserved behavior. If the tests don't exist, writing them is the first step (§7.5), and it's often the more valuable step.

**8.4 — Large refactors.** A large refactor (restructuring a significant region) is decomposed into a *sequence of small safe refactors* (§8.3), each behavior-preserving and verified, each leaving the system working (§3.7) — never a large leap through a broken-for-a-while state. This is strangulation applied to structure (FABLE §18, AE §6.6): the new structure grows alongside the old, code moves over incrementally, both work throughout, the old is removed when empty. A large refactor done as one big change is high-risk (can't verify behavior preserved across a huge diff) and blocks everyone (trunk broken); done as a sequence of small verified steps, it's safe and non-blocking. The discipline: *there's no such thing as a safe large refactor — only a safe sequence of small ones.*

**8.5 — Architectural refactors.** When the refactor would change a wall [M6] — a contract with callers (AE §4.7), a data format (AE §5), a seam, an invariant (AE §2.6) — *it is not a build task; it is an architecture decision* (§1.3, AE §6, DE §2 T3/T4). It stops, returns to the architecture engine (a correcting ADR, AE §6.2, FABLE §22.3), and is executed with the care an irreversible change demands (migration by strangulation AE §6.6, backward compatibility AE §4.7). The failure this prevents: a builder "refactoring" across an architectural boundary during construction, silently changing a decision the architecture made (§11 drift, §1.3). The builder's discipline: *know when a refactor has crossed from furniture to wall, and escalate at that line* — the code inside the seams is yours to restructure freely; the seams themselves are the architecture's.

**8.6 — Repository-wide refactors.** A refactor touching the whole repository (a renamed core concept §4.3, a changed convention, a moved boundary) is the largest and riskiest kind. Do it *mechanically where possible* (a rename that a tool can do reliably across the tree is safe; a hand-edit across a hundred files is error-prone), *in one focused commit* (so it's atomic — the repository is consistent before and after, never half-renamed), *with the full test suite as the net* (§7.5), and *separated from all behavior change* (§8.3). Repository-wide refactors are worth doing (a lying name §4.3 or an inconsistent convention §5.1 costs every reader forever [M15]) but their blast radius [M8] demands the most care — verify the whole system green after, because a repository-wide change that breaks something breaks it everywhere.

**8.7 — Technical debt retirement.** Debt is retired when its trigger fires (§4.8, PE §7.3) — the condition that made the shortcut acceptable no longer holds ("now it does handle real user data," "now the second provider exists"), so the shortcut must become the proper solution. Retirement is a refactor (§8.3, behavior-preserving where the debt was structural) or a rebuild (where the shortcut was a placeholder). Retire debt *when its trigger fires, not on a calendar* (PE §7.3 — trigger-based repayment fires exactly when it matters; calendar-based "cleanup sprints" retire whatever's convenient, not what's due). The debt ledger (§4.8) is reviewed at phase gates (PE §11.4) — due debts paid, others re-confirmed, dead ones (whose premise expired) retired from the ledger without work. Debt retired continuously never compounds; debt deferred indefinitely becomes the rewrite (§8.4, AE §6.6) — so the discipline is to pay each debt when its trigger fires, while it's still small.

# 9. AI-Assisted Building

How multiple AI models collaborate during construction — the build-time application of orchestration. OE (the whole document) establishes orchestration; OE §7 the roles; OE §8 verification; this section is the *build-specific* collaboration — how the roles play out during implementation, and the build-specific coordination hazards. The governing principle: **during building, the producer and its verifier must be independent, parallel builders must be isolated, and all of them must share the same durable design and conventions — so the fleet builds one coherent system, not several colliding fragments.**

**9.1 — Builder.** The role that writes the code (OE §7.1), routed to a coding-capable tier (OE §4.1). The builder is briefed with the design it must implement (the approved architecture's relevant contracts and invariants, AE §4, §2.6), the conventions it must follow (§4, §5 — naming, structure, the local dialect §5.1), and the done-state for its piece (§7.7). A builder building against a clear design and clear conventions produces code that integrates (§7.6) and reads consistently (§5.1); a builder briefed vaguely produces code that works in isolation but doesn't fit (OE §12, the coordination failures). Multiple builders build independent pieces in parallel (§9.7), isolated (§9.8).

**9.2 — Reviewer.** The role that checks the builder's code (OE §7.1, FABLE §25), *independent of the builder* (OE §8.1, §1.2 — a builder can't reliably review its own code, the blind spot is shared). The reviewer checks against the standard (FABLE §25 — correctness at the edges, the contract kept, readability, simplicity, tests that pin behavior) and reports findings with their failure scenarios (FABLE §25). Review is scaled to stakes (§7.8, OE §13.8) — walls get deep independent review, furniture gets a glance. The reviewer is a different context (and ideally a different tier, OE §8.3) so it fails differently than the builder and catches what the builder couldn't see in itself.

**9.3 — Architect (during building).** The role consulted when construction hits an architectural question (§1.3, §8.5) — a contract that doesn't fit reality (§1.4), a seam that needs to move, an invariant that construction reveals was wrong. The architect (OE §7.1, AE) makes the architectural decision (or updates it via ADR, AE §6.2) so the builder can proceed on solid ground. The architect's build-time role is the *escalation target* for the walls — when a builder discovers the design is wrong, the architect decides the fix, rather than the builder silently patching it (§1.3, §11 drift). This keeps the architecture-implementation boundary (§1.3) enforced during construction.

**9.4 — Debugger.** The role that runs the debugging workflow (FABLE §24) when something doesn't work — reproduce, read the error, bisect [M4], hypothesize, find root cause not crash site, fix, pin (§7.5). The debugger is often the builder wearing a different hat, but for a hard bug it's valuably a *fresh context* (the builder's context may be anchored on the wrong assumption that caused the bug — FABLE §24, the "known-good" that isn't). The debugger's output is a root-cause fix plus a regression test (§7.5) plus, where the bug reveals a class, a ratchet against the class [M12] (FABLE §24 — where else does this pattern live?).

**9.5 — Tester.** The role that verifies behavior by exercising (§7.4, OE §7.1, FABLE §17) — distinct from the reviewer (who reads) in that the tester *runs* the built thing and observes (RE §Stage 6). The tester drives the real behavior at the edges (§7.4), routed to whatever can actually exercise it (a vision model to verify UI renders, OE §4.1). The tester is the reality-contact [M2] of the build — the check that behavior matches intent, not just that code looks correct. For high-stakes behavior, the tester is independent of the builder (OE §8.1) and may be adversarial (OE §8.2 — trying to break it, not confirm it works).

**9.6 — Documentation.** The role that produces the durable record (OE §7.1, FABLE §26) — the docs for the stranger [M18], the decisions (ADRs, AE §6.2), the component registry update (FABLE Law 8), the why behind the what. Documentation happens *in the same session as the build* (FABLE Law 8, §2 Stage 6 — deferred docs don't happen), so the record is true as of the change. The documentation role captures what construction taught (§1.4) into durable form so the successor inherits it (OE §6.7, §11.7).

**9.7 — Parallel implementation.** Independent pieces (OE §3.2, the cold-brief test) are built in parallel by multiple builders, buying wall-clock (OE §1.2). The precondition is genuine independence (no shared mutable state, no cross-dependency, OE §3.2) — pieces that must coordinate during building aren't parallel (OE §3.4, the distributed-monolith-of-agents AE §10.2). Parallel implementation is planned by the orchestrator (OE §7.5) — it decomposes into independent pieces, briefs each builder fully (OE §9, cold start FABLE §29), and plans the reconvergence (integration §7.6, OE §7.5).

**9.8 — Context sharing.** Builders share the *design and conventions* (the durable architecture, contracts, naming, the local dialect §5.1) so they build a coherent system (OE §6.5, global knowledge) — retrieved into each builder's context (OE §5.1, §6.1). They do *not* share working context (OE §5.2, per-agent isolation) — each builder gets its own constructed context, coordinating through durable state (OE §3.5, §7.4) not through a shared context blob. The build-critical shared knowledge: the interfaces (§3.3, so pieces built in parallel connect), the conventions (§5.1, so the code reads as one), and the decisions (OE §6.6, so builders don't make conflicting choices). Shared through durable state (files, the design docs), not through messaging (OE §3.5).

**9.9 — Verification loops.** The build-time verification cycle (OE §8, §2 Stage 3): builder produces → independent reviewer/tester verifies → findings returned → builder fixes → re-verified, looping until the increment clears its verification bar (§7.8). The loop is *per-increment* (§3.7) not per-project — small increments verified continuously, so defects are caught at the increment that introduced them (§7), not accumulated to a final verification that finds a mountain. The verification loop is what makes AI-assisted building trustworthy (OE §8) — the producer's output is never trusted unverified at stakes (OE §1.2), and the loop closes the gap between "the builder thinks it's done" and "it's verified done" (§7.7).

# 10. Performance During Development

When and how to optimize during building — the discipline of not solving problems you don't have while staying ready for the ones you will. FABLE (bottleneck thinking [M10]) and AE §8 establish the frame; this is the build-time performance practice. The governing principle: **build for correctness and clarity first, measure before optimizing, and optimize only the measured bottleneck — because intuition about performance is reliably wrong, and premature optimization buys speed you don't need with complexity you can't afford.**

**10.1 — How to avoid premature optimization.** Premature optimization is making code faster before knowing it's a bottleneck — it adds complexity (§5.7, §11) for speed that may not matter, on the basis of intuition that's usually wrong [M10]. Avoid it by *building the clear correct version first* (§5.1, the boring maximum DE §3.3) and *not optimizing until a measurement shows a real problem* (§10.2). The clear version is often fast enough (most code isn't the bottleneck), and where it isn't, the measurement (§10.2) shows *where* — which is reliably not where intuition guessed [M10]. Premature optimization is a form of overengineering (§11) — solving a problem you don't have yet, at the cost of the clarity you do need.

**10.2 — When optimization begins.** Optimization begins when a *measurement shows a real performance problem against a real requirement* — the system is too slow/heavy for what it actually needs to do, verified by measuring, not by feeling. "Real requirement" matters — optimizing past what's needed is waste (§10.1, the requirement is the target, not maximum speed). "Measurement" matters — you optimize what you measured, not what you guessed [M10]. The trigger is *demonstrated need*, not anticipated need (the same discipline as building at all, DE §7 — build/optimize at the moment of real need, not on speculation).

**10.3 — How bottlenecks are discovered.** By *measuring the actual system doing the actual work* [M10, M2] — profiling, timing, resource-monitoring the real workload, not reasoning about what should be slow. The bottleneck is reliably not where intuition points [M10] (that's why measurement is non-negotiable) — the 80% of time is usually in one unexpected place, and optimizing anywhere else is invisible (bottleneck thinking [M10]). Discovery is *reality contact* (RE §Stage 6) applied to performance — the running system is the territory [M2], and its actual behavior under actual load is the only trustworthy source of where the time goes.

**10.4 — How optimization is validated.** By *measuring again after the change* — did the optimization actually improve the measured bottleneck, against the requirement? (An optimization that doesn't measurably help is complexity added for nothing — revert it, §5.7.) And by *re-checking correctness* — optimization often trades clarity for speed and can introduce bugs (§7.4, behavior validation after optimizing), so the behavior is re-verified. And by *finding the new bottleneck* (it moved, [M10]) — after fixing one, measure again; if the system now meets its requirement, stop (optimizing past the requirement is waste, §10.2); if not, the new bottleneck is the next target. Optimization is a measure-change-measure loop, bounded by the real requirement, validated by both speed and correctness.

# 11. Build Anti-Patterns

Named for in-flight detection. Each carries the observable signal that it's present now, and the root cause (cure the cause, not the symptom).

**11.1 — Scope creep.** The build grows beyond the approved phase — features, options, "while I'm here" additions not in the plan. *Signal:* work being done that isn't in the phase's deliverable (PE §5.2) or contradicts the non-goals (PE Stage 1). *Root cause:* the natural pull to add, unchecked by the plan. *Cure:* check work against the written non-goals; creep is work the non-goals forbade — defer it (a ticket with a trigger, §4.8) or re-scope explicitly (PE §5, scope negotiation FABLE).

**11.2 — Overengineering.** More structure/generality/flexibility than the problem needs (§5.7, AE §10.6). *Signal:* the code is more complex than the problem; abstraction with one user; config for things that never vary (§5.6); machinery for imagined future needs. *Root cause:* building for speculation (DE §7), demonstrating capability through complexity (FABLE §33.4), aesthetic attachment. *Cure:* the boring maximum (DE §3.3) — the simplest thing that solves the *real* need; delete the speculative machinery; add complexity only when a real need forces it (§10.1 applied broadly).

**11.3 — Premature abstraction.** Generalizing before the pattern is clear ([M13], AE §10.1). *Signal:* an abstraction with one or two instances, asserted to be general; a "framework" before a second real use. *Root cause:* abstracting at one or two data points, getting the shape wrong (a wrong abstraction is costlier than the duplication it replaced). *Cure:* the rule of three [M13] — write it, copy it (noting the twin), abstract at the third real instance when the true variance is visible.

**11.4 — Code duplication (the harmful kind).** The same logic copied such that it must change in lockstep and drifts if it doesn't. *Signal:* a bug fixed in one place recurs because the copies weren't updated; the same change made in several places. *Root cause:* not extracting a genuine shared concept (the inverse of §11.3 — this is under-abstraction). *Cure:* extract at the third instance [M13] — but only *genuine* duplication (things that change together for the same reason, AE §3.5); superficially-similar things that change for different reasons are not duplication and must stay separate (welding them is worse, §11.3).

**11.5 — Fragile code.** Code that breaks easily under change or unexpected input (§2 Stage 5, stabilization skipped). *Signal:* small changes break it in surprising ways; it works on the happy path and fails at the edges; failures are silent or cryptic. *Root cause:* stabilization cut (§2 Stage 5), edges unhandled (AE §4.3 partial contracts), hidden coupling (§11.7). *Cure:* stabilize (§2 Stage 5) — handle the edges, make failures loud (AE §8.1), verify behavior at the boundaries (§7.4); and reduce coupling (§5.7) so changes don't propagate surprisingly.

**11.6 — Incomplete implementation.** Code declared done that isn't — the happy path works, the edges don't, the "TODO" is load-bearing (FABLE §33.3, §34 eternal TODO). *Signal:* "done" but the edges/failures/second-run aren't handled; a TODO in a code path that runs. *Root cause:* declaring victory early (FABLE §33.3 — done at "compiles" or "happy path runs," not "behavior verified across the contract"). *Cure:* the completion criterion is behavioral and total (§7.7, AE §4.3) — done means the contract's behavior is observed correct at the edges, not just the center; verify by exercising the edges (§7.4).

**11.7 — Hidden dependencies.** A component depends on something not visible in its interface — a global, an implicit ordering, an assumed environment (§5.2, AE §10.8). *Signal:* changing something unrelated breaks it; it works only if something else happened first; the dependency isn't in the signature. *Root cause:* coupling through invisible channels (shared state §5.3, implicit order, assumed context RE §6.8). *Cure:* make the dependency explicit (put it in the signature/contract, §5.2, AE §4.3) or eliminate it (remove the shared channel) — hidden coupling is the most dangerous because it breaks in ways that seem impossible (AE §10.8).

**11.8 — Broken interfaces.** An interface that doesn't keep its contract — behaves differently than it promises, leaks internals, breaks callers on internal change (AE §4, §10.3). *Signal:* callers break when the implementation changes (§4.5); the interface changes every time the implementation does; the contract and behavior disagree (RE §5.5, [M2]). *Root cause:* the interface was reverse-engineered from the implementation rather than designed as a contract (§3.3, AE §4.1). *Cure:* design the interface as a caller-facing contract that hides internals (AE §4.1, §5.5); once it has callers, keep it (backward compatibility, AE §4.7) — add, never break.

# 12. Build Decision Trees

Built per [M7 → skill S-007]. Build-specific; defer to prior engines where the decision is theirs (DE §10, PE §10, AE §11, OE §13).

**12.1 — Prototype vs Production** *(defers to DE §10.3; build overlay)*
```
Is the purpose to LEARN (feasibility, feel, does-the-API-work), or to BE BUILT ON?
  ├─ learn → PROTOTYPE: isolated (§6.4), labeled disposable, deletion planned; output is the ANSWER not the code
  │           └─ if approach validated → explicit decision to REBUILD properly (DE §10.3); never promote the prototype (§6.2)
  └─ built on → PRODUCTION: full quality on the walls (§7.8, [M6]), done = behavior verified across contract (§7.7)
```

**12.2 — Build vs Refactor (to make a change)**
```
Does the current structure make the change I need hard? (§8.1)
  ├─ no → BUILD the change directly
  └─ yes → REFACTOR first to enable it (§8.1 "make the change easy"), THEN build the change (separate commits §8.3)
            └─ does the refactor cross a wall (contract/format/seam/invariant)? (§8.5, [M6])
                 ├─ yes → STOP: it's an architecture decision (AE §6, DE §2 T3/T4), escalate to architect (§9.3)
                 └─ no → safe refactor procedure (§8.3): tests green → small steps → tests green → then build
```

**12.3 — Continue vs Rewrite** *(defers to AE §10.5; build overlay)*
```
Is the problem the DESIGN or the EXECUTION? (DE §9.2)
  ├─ execution (bugs on sound structure) → CONTINUE + debug (§9.4, FABLE §24); rewrite discards learned edge-cases for nothing
  └─ design (structure is wrong) → is it live / has undocumented behavior others rely on?
       ├─ yes → STRANGLE (§8.4, AE §6.6): new alongside old, migrate incrementally, delete old when cold
       └─ no (disposable/greenfield) → rewrite MAY be cheapest-path-from-today [M14]; strip sunk cost first (DE §9.3),
              carry the LEARNING forward (§1.4), don't repeat the original's discovered edges
```

**12.4 — Quick Fix vs Proper Solution**
```
What is the blast radius / permanence of this code? (§4.8, [M8])
  ├─ low + genuinely temporary WITH a recorded trigger → QUICK FIX + debt ticket (§4.8) — legitimate speed
  ├─ on a wall / will be built upon → PROPER solution now (§7.8 [M6]) — a shortcut here compounds structurally (§4.8)
  └─ "quick fix" with NO trigger → REJECT: that's permanent code lying about being temporary (§6.3) — do it properly or ticket it
```

**12.5 — Temporary vs Permanent**
```
Will this code be replaced, and is there a FORCING FUNCTION for the replacement? (§6.3, §4.8)
  ├─ replaced + trigger recorded → TEMPORARY (legitimately) — the trigger forces the replacement (§4.8, §8.7)
  ├─ replaced + no trigger → it's PERMANENT by default (§6.3); either accept it as-is (build it properly) or add a trigger
  └─ not replaced → PERMANENT: build to the standard its stakes demand (§7.8), no "temporary" excuse for low quality
```

**12.6 — Single Module vs Split Module**
```
Does the module have one cohesive reason to change, or several? (AE §3.5, §5.4)
  ├─ one → SINGLE module (splitting adds coordination cost [M15] for no cohesion gain)
  └─ several (changes for unrelated reasons scatter across it) → SPLIT along the reasons-to-change (AE §3.2 bounded contexts)
       └─ but: are the parts genuinely independent, or would splitting create a dependency cycle? (§3.5, AE §3.4)
            ├─ independent → SPLIT
            └─ cyclic → they're really ONE module; the urge to split is misreading coupling for separateness — keep together, re-cut differently
```

**12.7 — Optimize vs Leave Alone** *(§10)*
```
Has a MEASUREMENT shown this is a real bottleneck against a real requirement? (§10.2, §10.3, [M10])
  ├─ no → LEAVE ALONE (premature optimization §10.1 — you'd add complexity for speed you can't show you need)
  └─ yes → OPTIMIZE the measured bottleneck only → validate: measured improvement? correctness preserved? (§10.4)
            └─ requirement now met? → STOP (optimizing past the requirement is waste §10.2)
               not met? → find the new bottleneck (it moved [M10]), repeat
```

# 14. Real Engineering Examples

Complete implementation walk-throughs, showing the engine running — every ordering decision, tradeoff, refactoring, and verification. Read as construction proceeding.

**14.1 — Desktop application.**
- *Preparation (§2 Stage 0):* confirm the build-run-test loop works on the target OS before anything — a desktop app's environment (packaging, the GUI toolkit) is a common hidden blocker (§2 Stage 0). Verify, don't assume [M1].
- *Walking skeleton (§3.2):* a window that opens, does one trivial end-to-end thing (loads and shows one piece of data), and can be built/run/tested. Proves the architecture's layers (AE §13.1 — UI→logic→data, inward dependencies) connect and run.
- *Order (§3.6):* core-first (§3.4) — the app's central capability before the polish (menus, preferences, niceties); dependencies-first (§3.5) — the data layer before the logic that uses it before the UI that drives it, built against interfaces (§3.3) so the layers connect cleanly.
- *Stabilization (§2 Stage 5):* desktop apps crash and must not lose data — so consistent writes (AE §5.6), handling the file-not-there/disk-full edges (§11.5), and offline function (AE §8.7) are stabilized before "done."
- *Verification (§7):* behavior validated by exercising the real UI (§7.4, tester role §9.5 with a vision model OE §4.1); the data-format (a wall [M6]) exhaustively verified (§7.8); the rest proportional.

**14.2 — AI operating system (JarvisOS).**
- *Preparation (§2 Stage 0):* the risk-first spike (PE §6, §3.8) — does a local model run at usable latency on this hardware? — runs *before* the build commits, because it could invalidate the offline-first architecture (§3.8, dead-end avoidance).
- *Walking skeleton (§3.2):* the thinnest end-to-end path — a request through the gateway (AE §9.2) to a model and back, one MCP capability connected (AE §9.10), one thing written to a file. Proves the two load-bearing seams (AE §9) actually work before any capability is built in depth.
- *Order (§3.6):* the seams first (they're the walls [M6], everything hangs on them), then capabilities in dependency and value order (PE roadmap), each a vertical slice (§3.1) proving it works end-to-end before widening.
- *Walls vs furniture (§1.3, §7.8):* the memory file format, the trust boundaries (AE §9.6), the gateway contract — walls, built and verified exhaustively (§7.8, adversarial for the injection defense OE §8.2). The specific local model, the chat UI — furniture, built fast and swappable (AE §9.2).
- *Knowledge capture (§1.4):* construction findings (the substrate was EOL, provider-agnosticism was a façade) flow back to the architecture as ADRs (AE §6.2) — the build teaching the design, exactly §1.4.

**14.3 — Large open-source project.**
- *Repository evolution (§4):* structure mirrors the architecture (§4.2), grows along its seams (§4.1); machine-enforced hygiene (§4.7, FABLE §19) because contributors are a rotating set of agent-sessions (OE §11) and vigilance doesn't scale [M12].
- *Interfaces first (§3.3):* every public interface designed as a contract before implementation (AE §4.1), because once it has downstream users it's frozen (AE §4.7) — backward compatibility is sacred (§5.5), evolution by addition only.
- *Incremental (§6, §3.7):* trunk always green (FABLE §19), every change a small verified increment — because many contributors build in parallel (§9.7) and a broken trunk blocks everyone.
- *Refactoring (§8):* opportunistic and local (§4.6, campsite rule); repository-wide refactors (§8.6) done mechanically, atomically, with the full suite as net — because a rename of a core concept touches everything and must be consistent (§5.1).
- *Verification (§7):* scaled to stakes (§7.8) — a docs fix gets a glance, a core-interface change gets deep adversarial review (§9.2, OE §8.2) because of its blast radius on callers [M8].

**14.4 — Reverse-engineering platform.**
- *Preparation (§2 Stage 0):* the platform runs untrusted/hostile targets (AE §13.5) — so the *first* build concern is the isolation (the failure/trust domain, AE §8.3, §9.6) that keeps analyzing a target from compromising the platform. Built and verified before any analysis capability.
- *Walking skeleton (§3.2):* capture one observation from one target, in isolation, and record it — proving the observe-isolate-record path (RE §7.1) end-to-end.
- *Order (§3.6):* the analysis pipeline stages (capture→observe→model→verify, RE §7.1) built as a skeleton first, then each stage deepened; new analysis techniques plug in as capabilities (§3.3, AE §9.10) against the stage interfaces.
- *Stabilization (§2 Stage 5):* targets are malformed and hostile by nature — so every input edge is handled (§11.5, malformed/huge/adversarial), failures loud and contained (AE §8.1, §8.3). Fragility here is a security hole, not just a bug.
- *Verification (§7.4):* findings verified by prediction against the target (RE §7.1 — reality is the arbiter [M2]); model-generated conclusions verified independently (§9.5, OE §8) because they're untrusted (OE §12.1).

**14.5 — Long-running software project.**
- *Incremental over time (§6, OE §11):* built in phases (PE §5), each a full run of the build pipeline (§2), each banking value (PE §5.4) — so the project is always ahead of zero and survivable if stopped (§6.1).
- *Repository health over years (§4.9):* continuous hygiene (§4.7) and continuous debt retirement (§8.7, trigger-based) — because a long project's repository decays without maintenance (AE §6.1, the three rots), and decay deferred becomes a rewrite (§8.4).
- *Refactoring as evolution (§8, AE §6):* the structure evolves with the architecture (§8.5 escalates wall-changes to ADRs); strangulation for large restructures (§8.4, AE §6.6) so the system stays working throughout.
- *Knowledge continuity (§1.4, OE §11):* every phase captures what it taught into durable state (OE §6.7) so successor builders (a different model each phase, OE §11.8) onboard from the record (OE §11.7, [M18]) — the build's durable knowledge is what lets construction continue across the succession without restart.
- *Completion as gate, forever (§7.7):* each phase completes only against its observed exit test (§7.7) — because in a project spanning years and models, "seems done" is unverifiable across the handoffs, and only the falsifiable behavioral gate [M19] survives the succession.
