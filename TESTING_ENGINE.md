**The one-sentence version.** Testing is the manufacture of *justified confidence* that software behaves correctly — and the entire craft is in the word *justified*, because a test suite produces a feeling of safety whether or not it earns one, and the discipline is ensuring the confidence is proportional to the evidence, never to the green checkmarks [M20].

# 1. Testing Philosophy

**1.1 — What testing actually is.** Testing is *sampling a system's behavior against its intended behavior to build justified confidence it's correct*. Three words carry the weight: *sampling* (you check specific cases, never all cases — §1.4), *intended* (you compare against what it should do, which requires knowing that — §2 Stage 0), and *justified confidence* (the output is not "correct" but "correct-enough-to-trust, on this evidence, at this confidence" — §1.3). Testing is fundamentally *empirical* [M2] — it observes what the system actually does (BE §7.4, verify by exercising) rather than reasoning about what it should — which is why it catches what review (which reasons, CR) and building (which intends, BE) miss: the gap between intent and reality that only running reveals (DBG §1.1).

**1.2 — Why testing exists.** To make software *trustworthy* — to convert "I believe this works" into "I have evidence this works" [M1, M20]. Three purposes, in order:
- **To catch defects before they're trusted** — the primary purpose, cheapest when caught early (BE §7, a defect caught in test is far cheaper than in production DBG §9.3).
- **To *preserve* correctness over change** — the regression suite (§3.9, BE §7.5) is what lets a system keep changing without silently breaking, which is what keeps it *changeable* over years (AE §1.3). This is testing's most underrated value: not proving today's code works, but ensuring tomorrow's change doesn't break it.
- **To *define* correctness** — a test is an executable specification (FABLE §17), the one form of documentation that can't drift from reality [M2] (it fails when it becomes false). Tests say, precisely and permanently, what "correct" means.

**1.3 — The relationship between testing and confidence.** Testing produces *confidence*, and the cardinal discipline is that the confidence must be *justified* — proportional to what the tests actually verify, never to how many are green [M20]. This is the whole ethical core of testing: a suite of a thousand passing tests that all exercise the happy path produces a *feeling* of safety it hasn't earned (§9.4, §9.5 false confidence) — and that unearned confidence is *worse* than no tests, because it licenses trust that isn't warranted, and the failure it lets through arrives where nothing was watching. So the reviewer of a test suite (CR §4.8) asks not "how many tests?" but "what confidence do these actually justify — would they catch the failures this system can plausibly have?" (§3.1, DBG §6.3). Confidence is *calibrated to evidence* [M20], and the tests' job is to make the evidence real.

**1.4 — Why testing can never prove correctness.** Testing *samples* (§1.1) — it checks specific inputs, and the input space is effectively infinite, so testing can show the *presence* of defects (a failing test proves a bug) but never their *absence* (all tests passing proves only that these cases work, not that all cases do). This is not a limitation to lament but a truth to design around: because testing can't prove correctness, the discipline is to *sample where correctness is most likely to break* (§3.1 risk-based, §4.2 edges) rather than to chase the impossible goal of exhaustive coverage (§9.5 coverage obsession). Testing buys confidence, not proof — and the skill is buying the *most* confidence per test by sampling the highest-risk, most-representative cases, accepting that some untested case could always fail (which is why production validation §3.10 and monitoring §8.5 exist — the sampling continues in production, where the real input distribution finally arrives).

**1.5 — The relationship between testing and debugging.** They are inverses that feed each other (DBG). Debugging *finds* the cause of a known failure; testing *detects* failures and *prevents* their return. The cycle: a test detects a defect → debugging (DBG §2) finds its root cause → a regression test (§3.9, DBG §2 Stage 7) pins the fix so it can never silently return. Testing is also debugging's *precondition* — a bug needs reproduction (DBG §4) to be debugged, and a good test *is* a reproduction (a minimal, reliable trigger DBG §4.3). And debugging *improves* testing — every bug that escaped to be debugged reveals a gap in the test strategy (§7.3 false negative), and the discipline is to ask, for each escaped bug, "what test would have caught this, and what *class* does it belong to?" (§3.1, DBG §5.6), then add it.

**1.6 — The relationship between testing and review.** They are complementary verification with different mechanisms (CR §1.1). Review *reasons* about the work (a mind judging fitness, CR §4); testing *exercises* it (behavior observed empirically [M2]). Each catches what the other misses: review catches the design flaw, the security hole with no symptom (CR §6, DBG §3.9 — a test won't find what it doesn't think to check), the maintainability problem (CR §8) that no test expresses; testing catches the behavioral defect that looks correct on the page but fails when run (DBG §1.1 — the "looks right, isn't right" gap review can't fully close). Neither substitutes for the other — review approves *and* tests verify (CR §12.3 — does it actually work, not just look right). And review *examines the tests* (CR §4.8) — because a test suite is code, and a suite that produces false confidence (§1.3) is a defect review must catch.

# 2. The Testing Pipeline

Finished implementation in, justified production confidence out. Eight stages. FABLE §17 and BE §7 give the philosophy and the verification levels; this is the full pipeline of testing *as a designed activity*. The pipeline exists because testing done ad-hoc produces the false confidence (§1.3) that ad-hoc testing always produces — a scatter of tests that feel like coverage and aren't.

**Stage 0 — Requirement analysis.** Establish what "correct" *means* for this software — the behavior it must exhibit (the contract AE §4.3, the requirement RE §3, the done-state PE Stage 1). Testing validates against a standard, and this stage *is* the standard — without it, tests check that the code does what it does (tautology, §9.1), not what it *should*. For each requirement, derive what would *demonstrate* it (the observable behavior that proves it, §1.1 intended) — this is the raw material for test design (Stage 2).
*Checkpoint: can I state, for each thing this must do, the observable behavior that would prove it does? If not, I can't test it — I can only exercise it.*

**Stage 1 — Test planning (strategy).** Decide *what to test and how hard* (§3) — risk-based (§3.1), scaled to stakes (BE §7.8, [M8]). Not everything gets tested equally: the walls [M6] (correctness-critical, irreversible, security §6, data integrity) get exhaustive testing; the furniture gets proportional-to-risk. The plan allocates the finite testing effort where being wrong is most expensive (§3.1) — because testing effort, like all effort, is finite, and spreading it evenly under-tests the critical (BE §7.8, CR §3.6).
*Checkpoint: does the plan concentrate effort on the highest-risk behaviors, or spread it evenly (under-testing the walls)?*

**Stage 2 — Test design.** Design the specific tests (§4) — the cases that, together, sample the behavior space where it's most likely to break (§1.4). For each behavior: the happy path (§4.1), the edges (§4.2), the failures (§4.3), the adversarial cases (§4.4), scaled to stakes. Design tests to verify *behavior* (the contract, FABLE §17), not implementation (§9.1) — so they survive refactoring and actually pin what matters.
*Checkpoint: do these tests sample where the behavior is likely to break (edges, failures), or only where it's likely to work (happy path §9.4)? Would they catch the defects this can plausibly have (§3.1, DBG §6.3)?*

**Stage 3 — Test implementation.** Build the tests as *code* (CR §4.8 — reviewed as code, held to the standards BE §5) — readable (a test is documentation FABLE §17, so it must be clear), reliable (not flaky §7.2, or it's worse than useless §9.7), and maintainable (tests are maintained forever §2 Stage 7, so a fragile test §9.3 is a permanent cost). Tests are implemented at the right level (§5 — unit/integration/system) for what they verify (§10.1).
*Checkpoint: are these tests reliable (deterministic §7.2), readable (documentation FABLE §17), and testing behavior not implementation (§9.1)?*

**Stage 4 — Execution.** Run the tests and observe (BE §7 — the levels: they compile, run, behave, integrate). Execution is *empirical* [M2] — the tests exercise the actual system and report actual behavior. Execution happens continuously (BE §3.7 — every change runs the suite, so regressions are caught at the change that causes them §3.9) not just once.
*Checkpoint: are the tests actually exercising the real behavior (BE §7.4), and running continuously so regressions surface immediately (§3.9)?*

**Stage 5 — Failure analysis.** When a test fails, interpret it correctly (§7) — is it a real defect (the valuable case, → debug DBG §2), a flaky test (§7.2, a test-suite defect), a false positive (§7.3, the test is wrong), or an environmental failure (§7.5)? Failure analysis is where a test suite earns or loses trust: a suite whose failures are ignored because "it's probably flaky" (§7.2, §9.7) has become noise, and a real defect will hide in the noise.
*Checkpoint: is this failure a real defect, a flaky test, a wrong test, or an environment issue — and am I sure, or assuming "probably flaky" (§7.2, §9.7)?*

**Stage 6 — Regression protection.** Every defect found (by test, by debugging DBG, by production) gets a regression test that pins it (§3.9, BE §7.5, DBG §2 Stage 7 — the fix without the test will return, near-certain). The regression suite is the accumulated memory of every defect the system has had (§1.2) — it's what lets the system keep changing safely (AE §1.3), and it's a ratchet [M12] converting each fixed defect into a permanently-fixed one.
*Checkpoint: is every defect pinned by a test that fails without the fix and passes with it (DBG §2 Stage 7)?*

**Stage 7 — Maintenance.** Tests are maintained over the system's life (they're code, they rot). Maintenance: remove tests that no longer test anything meaningful (a test welded to a removed implementation §9.1); fix flaky tests (§7.2 — don't tolerate them, they poison the suite §9.7); update tests when the *contract* legitimately changes (AE §4.7 — a contract change is a deliberate test change, not a test to silence); and prune the suite toward *value* (few tests that catch real defects over many that catch trivia §9.5, FABLE §17). An unmaintained suite decays into flaky, slow, false-confidence noise (§9) — maintenance is what keeps it a trustworthy instrument.
*Checkpoint: is the suite still a trustworthy instrument — reliable, meaningful, catching real defects — or has it decayed into noise (§9)?*

**Standing discipline — confidence is the product, and it must be justified.** Every stage serves the one output: *justified* confidence (§1.3). The failure the pipeline guards against is *unjustified* confidence — the green suite that doesn't verify what matters (§9.4, §9.5), producing a feeling of safety that licenses untrusted trust [M20]. At every stage, the question is not "do the tests pass?" but "does what these tests verify justify the confidence we're placing in this software?"

# 3. Test Strategy

How to choose what to test — the highest-leverage testing decision, because testing effort is finite (§2 Stage 1) and the input space is infinite (§1.4), so *where you sample* determines what confidence you buy. The governing principle: **test where being wrong is most expensive and most likely, sample the behavior space at its break-points not its center, and buy the most confidence per test — because you can't test everything, so testing everything equally means testing the critical things insufficiently.**

**3.1 — How I choose what to test (risk-based, the master strategy).** Test by *risk* — the product of *likelihood of a defect* × *cost if it fails* × *how hard the defect would be to catch later* (the same risk calculus as PE §6, DBG §3, [M8, M16]). This concentrates finite testing effort (§2 Stage 1) where it buys the most confidence: the walls [M6] (correctness-critical logic, irreversible operations, security boundaries §6, data integrity §4.6 — high cost if wrong), the complex and novel (high likelihood of defect — simple boring code rarely breaks), and the things hard to catch later (a subtle data corruption that surfaces far downstream DBG §3.10). The furniture (simple, reversible, low-blast-radius) gets light testing. Risk-based testing is the answer to "you can't test everything" (§1.4) — you test the *riskiest* things thoroughly and accept lighter coverage of the rest, rather than testing everything shallowly (which under-tests the walls, the expensive failure).

**3.2 — Behavior-based testing.** Test *what the software does* (its observable behavior against its contract), not *how it does it* (its implementation) — FABLE §17, §9.1. Behavior-based tests survive refactoring (BE §8 — the implementation changes, the behavior and its tests don't), pin what actually matters (callers depend on behavior, not implementation, AE §4.1), and read as specifications (FABLE §17 — "given this, it does that"). This is the default testing stance: derive tests from the *contract* (AE §4.3, Stage 0 requirement) — what inputs it accepts, what outputs it guarantees, what invariants it holds — and test those, treating the implementation as a black box whose internals are free to change (§10.3 mock-vs-real, the black-box preference).

**3.3 — Contract testing.** Test that a component honors its interface contract (AE §4.3) — the specific case of behavior-based testing (§3.2) at a seam (AE §4, the boundary between components). Contract tests are high-value because seams are where integration breaks (BE §7.6, AE §8 — independently-correct components fail to fit) — a contract test verifies each side of a seam keeps its promise, so the two sides can evolve independently (AE §6.4) and integration is protected. Especially critical for contracts with many callers (AE §4.7 — frozen, so their tests guard the frozen promise) and for the seams the architecture depends on (the model gateway, MCP servers §6.2 — AE §9, the load-bearing seams).

**3.4 — Boundary testing.** Test at the edges of the input space (§4.2) — where the usual case ends and the assumed-away case begins (DBG §1.3, where bugs concentrate). The boundaries: empty/zero/null, maximum/overflow, the transition points (just-below, at, just-above a limit), and malformed. Boundary testing buys disproportionate confidence because *bugs cluster at boundaries* (DBG §1.3) — so per test, a boundary case is far more likely to find a defect than a center case (§9.4 — the happy path is where bugs hide least). The discipline: for every input with a range, test its boundaries, because the producer tested the middle (§4.1) and the boundaries are where they didn't.

**3.5 — Property testing.** Test *invariants that must hold across many inputs* rather than specific input→output pairs (a generalization of example-based testing). Where example tests check "input A gives output X," property tests check "for all valid inputs, this property holds" (the output is always sorted, the round-trip always recovers the original, the invariant AE §2.6 is always preserved). Property testing samples the input space *automatically and broadly* (§1.4 — it can't be exhaustive, but it samples far more than hand-written examples), so it finds edge cases the tester didn't think of (§4.2 — the boundary you didn't enumerate). High-value for anything with a clear invariant (data transformations, encoders/decoders, anything with a round-trip §6.5, the memory store/index consistency §6.5).

**3.6 — Scenario testing.** Test *realistic end-to-end sequences* — the actual workflows the system will perform (a user's real journey, an agent's real task OE §2). Scenario tests verify the pieces work *together* toward a real goal (§5.2 integration, §5.3 system) — catching the integration and sequence defects (DBG §3.2 state, §3.11 distributed) that unit tests miss. They're the FABLE §17 "few end-to-end over many trivial" principle — one scenario test through the real path catches whole categories a hundred unit tests miss (the seams don't fit, the state corrupts across steps, the workflow's assumptions are wrong). Scenario tests are derived from the *actual use* (Stage 0 — what will this really do), so they validate fitness-for-purpose, not just component-correctness.

**3.7 — Exploratory testing.** Testing *without predefined cases* — actively probing the system to discover how it behaves and where it breaks (DBG §7, RE §Stage 6 reality contact, applied to finding defects). Exploratory testing is human/AI judgment hunting for the unexpected (§4.4 adversarial — "what happens if I do this weird thing?") — it finds the defects that designed tests miss because designed tests only check what the designer thought of (§9.4, §9.8 untested assumptions). It's especially valuable for *new or poorly-understood* systems (where the behavior isn't fully known, so predefined tests can't be complete) and *before* designing the regression suite (exploration reveals what's worth pinning). Exploratory findings become designed tests (§3.9 — pin what exploration discovers).

**3.8 — (Scenario/exploratory covered; regression is §3.9.)**

**3.9 — Regression testing.** Test that what worked *still* works after change (BE §7.5, §1.2). The regression suite is the accumulated memory of every defect (§2 Stage 6) and every behavior worth preserving — run on every change (BE §3.7) so a regression is caught at the change that causes it (DBG §11.5), not in production. Regression testing is testing's *durable* value (§1.2 — it's why a system stays changeable AE §1.3), and each regression test is a ratchet [M12] (a defect that can never silently return). The discipline: *every* defect found, anywhere (test, debug DBG, production §3.10), gets a regression test (§2 Stage 6) — the suite grows with the system's history of failures, becoming an ever-stronger guard.

**3.10 — Production validation.** Testing *in and against production* — because production is where the *real* input distribution finally arrives (§1.4 — the cases you couldn't sample in test), and no pre-production testing fully predicts it (DBG §9.3 — the class that only appears in production: scale, real data, real load, real environment §3.6). Production validation: monitoring (§8.5 — observing real behavior for anomalies, the ongoing sample), canary/staged rollout (§5.7 — exposing a change to a fraction of production first, so a defect affects few before all), and synthetic production checks (§5.6 — automated real-behavior probes against production). Production validation accepts that testing can't prove correctness (§1.4) and so *continues sampling in production*, where the truth lives — it's the humility of §1.4 made operational.

# 4. Test Design

How to design tests that actually find defects — the craft of choosing *which* cases to check (§1.1 sampling). The governing principle: **design tests to break the software, not to confirm it works — because a test that only confirms the happy path (§9.4) buys almost no confidence (the happy path is where defects hide least), while a test that probes the edges and failures buys the most (that's where they hide most, DBG §1.3).**

**4.1 — Happy paths.** Test the primary intended behavior works (the core use case does what it should, §3.6 scenario). Necessary but *weak* — the happy path is what the producer built and tested (BE §6.1), so it's usually correct; a suite of only happy-path tests (§9.4) buys little confidence because it samples where defects are least likely. Test the happy path (it must work, and it's the regression guard for the core §3.9), then spend the *bulk* of design effort on the edges and failures (§4.2, §4.3) where the confidence is actually bought.

**4.2 — Edge cases.** Test the boundaries (§3.4) — empty, maximal, malformed, the transitions (DBG §1.3, where bugs cluster). This is where designed testing buys the most confidence per test (§3.4). For each input, enumerate its edges systematically (the empty collection, the single element, the maximum, the just-over-maximum, the null, the wrong type) — because the producer tested the middle (§4.1) and the edges are the assumed-away cases (DBG §1.4) where the false assumptions live. Edge-case design is the difference between a suite that finds defects and one that confirms function (§9.4).

**4.3 — Failure cases.** Test what happens when things go wrong (AE §8.1, CR §4.4) — each external dependency failing (the network down DBG §3.7, the file absent, the service erroring), invalid input (§4.2 malformed), resource exhaustion (§4.7 performance, out of memory/disk/connections). Failure-case testing verifies the software *fails correctly* — loud not silent (AE §8.1, §9 silent-fallback), safe not corrupting (§4.6, into a recoverable state), recoverable (§4.8). The failure paths are the *least* exercised in normal use (DBG §3.6 — they only run when something breaks) and so the *most* likely to harbor untested defects — which is why a system's failure handling is where production incidents concentrate (DBG §9.3), and why failure-case design is high-value.

**4.4 — Adversarial cases.** Test the software against *hostile* input and use — the security cases (§6, CR §6 — how would an attacker make this misbehave, [M16] inversion). Adversarial design asks "how do I break this on purpose?" (§3.7 exploratory, with malice) — injection (§6, malformed input meant to be interpreted as commands), boundary attacks (overflow, exhaustion), trust-boundary violations (untrusted input reaching privileged paths, AE §8.2). Adversarial cases find the defects that have *no symptom in normal use* (DBG §3.9 — security bugs work fine until misused) — so they're found only by deliberately probing for them, never by testing normal behavior. Essential for anything on a trust boundary (§6, AE §8.2) and for AI systems (§6, prompt injection AE §9.6).

**4.5 — State transitions.** Test the sequences, not just the individual operations (DBG §3.2, CR §4.5). State bugs work in isolation and fail in sequence (DBG §3.2) — so test the transitions: what happens on the second call, after a failure, in an unexpected order, after a reset (or without one). Design tests that exercise *sequences* of operations (§3.6 scenario) and verify the state stays valid through all of them (the invariant preserved, AE §2.6). Especially critical for stateful components (BE §5.3) and for anything where order matters (a workflow, a protocol RE §7.3, an agent's multi-step task OE).

**4.6 — Concurrency.** Test parallel execution for races, deadlocks, and lost updates (DBG §3.3, CR §4.5, §7.4). The hardest to test (DBG §3.3 — non-deterministic, timing-dependent) — the design challenge is *making the race reliable* (DBG §4.2 — forcing interleavings, widening windows, so the concurrency defect reproduces in the test rather than randomly in production). Concurrency tests verify: shared state is safe under parallel access (AE §10.4), operations assumed atomic are (DBG §3.3), and the system doesn't deadlock (§7.4). Because concurrency defects are non-deterministic (a test passing once doesn't mean the race is absent, §8.1-like), concurrency testing often uses stress (many iterations, high parallelism) to raise the probability of hitting the race (DBG §4.2).

**4.7 — Performance.** Test that the software performs acceptably against its requirement (BE §10, CR §7, DBG §3.8). Design: measure against the *real* requirement (§7.8 of CR — is the latency/throughput/resource-use within what's needed, not maximum), at *realistic* scale (§4.2 boundary applied to load — what happens at the input size that will actually occur, and at 10× it §3 scalability). Performance tests catch the algorithmic-complexity defects (DBG §3.8 — the O(n²) fine at test scale, catastrophic at production scale) *before* production (DBG §13.6). They're regression-critical (§3.9 — a performance regression is a real regression, pinned by a performance test that fails if the system slows past the requirement, DBG §13.6).

**4.8 — Recovery.** Test that the system recovers from failure (AE §8.5, DBG §12.12, FABLE §27). Design: induce a failure (a crash, a corruption, a dependency loss) and verify the system returns to a good state — the backup restores (BE §5.6 — a backup never restored is a hope, MAINTENANCE §3), the rollback works (AE §8.5), the retry is safe (idempotent, DBG §13.2), the degraded mode functions (§8.7 of AE, graceful degradation). Recovery testing is the *rehearsal* [M12] that turns a documented recovery path into a trusted one (FABLE §27, MAINTENANCE §3 — the disaster-recovery drill) — because a recovery path never exercised is fiction, and the time to discover it doesn't work is *not* during the real disaster.

**4.9 — Security.** Test the security properties hold (§4.4 adversarial, §6, CR §6) — trust boundaries enforce, validation catches bad input, secrets don't leak, injection is blocked, privilege can't escalate. Security test design is *adversarial* (§4.4) — it thinks like an attacker (CR §6, [M16]). For AI systems, the injection canary (§6, BE §14.2 — a seeded injection attempt that must fail to influence the acting system, AE §9.6). Security tests are run at every relevant change (§8.4 — a ratchet [M12] against the reintroduction of a security defect) because security defects are asymmetric [M16] and silent (DBG §3.9).

**4.10 — AI workflows.** Test AI-native behavior (§6, the full section) — the probabilistic, context-dependent behavior that classical test design doesn't cover. The key design shift (§6.1): AI behavior is *probabilistic* (OE §12.1, DBG §8.1), so tests verify *distributions and properties* (does it do the right thing *reliably enough*, across many runs, §6.1) rather than single deterministic outputs, and verify the *guardrails* (the gates AE §9.5, the trust boundaries §6.9 of CR) that contain the probabilistic behavior more than the behavior itself (§6.1 — you can't make the model deterministic, so you test that its failures are contained).

**4.11 — Long-running systems.** Test behavior over *time* (§6.11, DBG §8.10) — the failures that only emerge over months (memory rot DBG §8.6, knowledge corruption AE §5.6, drift OE §12.6, slow degradation §7.3 metrics, resource leaks §4.7). Design: *accelerated* tests (simulate long-running conditions faster — many cycles, aged data, accumulated state §5.9 simulation) and *trend* monitoring (§8.5 — watch the metrics that degrade slowly, catch the trend before the incident DBG §8.10). Long-running-system testing is hard because the failures are *slow* (they don't appear in a short test run), so it requires either time-acceleration (simulation §5.9) or long-horizon monitoring (§3.10 production validation) — a class of testing classical short-lived software rarely needed and long-running AI systems (OE §11) require.

# 5. Test Architecture

The structure of the test apparatus — the kinds of tests and how they compose into a suite that establishes and preserves confidence. AE §3 (system decomposition) informs how tests mirror structure; this is the test-suite's own architecture. The governing principle: **build a layered test architecture — many fast narrow tests at the base, fewer slow broad tests above — because the base catches defects cheaply and locally while the top catches the integration and system defects the base can't see, and the shape (wide base, narrow top) keeps the suite fast enough to run continuously (§2 Stage 4).**

**5.1 — Unit tests.** Test the smallest units (a function, a component) in isolation (BE §5.2). Fast, numerous, narrow — they catch logic defects (DBG §3.1) locally and cheaply, and they run constantly (§2 Stage 4, BE §3.7). The base of the test architecture (most numerous). Discipline: unit tests test *behavior* of the unit (§3.2, its contract) not its internals (§9.1), and a unit that's hard to test in isolation is a design signal (AE §3 — the seams are wrong, CR §8.7 testability). Unit tests are cheap confidence in the parts; they say nothing about whether the parts fit together (§5.2).

**5.2 — Integration tests.** Test that components work *together* (BE §7.6, §3.3 contract) — the seams (AE §4) hold, the data flows correctly across boundaries (AE §4.5), the contracts are honored on both sides (§3.3). Integration tests catch what unit tests can't (§5.1 — the parts are individually correct but don't fit, AE §8 — the classic integration failure). Fewer and slower than unit tests (they exercise more), positioned above unit in the architecture. High-value at the seams the architecture depends on (§3.3 — the load-bearing boundaries AE §9).

**5.3 — System tests.** Test the whole system end-to-end (§3.6 scenario) — the complete workflows through all layers (AE §3, BE §3.1 vertical slice). System tests verify *fitness for purpose* (Stage 0 — does the whole thing do what it's for) — the ultimate behavioral test (§3.2 at the largest scope). Fewest and slowest (they exercise everything), the top of the architecture. They catch the defects only visible at the whole-system scale (DBG §3.11 distributed, the emergent failures, the real workflow's assumptions). FABLE §17's "few end-to-end" principle lives here — a few good system tests catch whole categories (§3.6).

**5.4 — Acceptance tests.** Test that the system meets its *requirements* (Stage 0, the done-state PE Stage 1) from the *user's/stakeholder's* perspective. Acceptance tests are the falsifiable exit tests (PE Stage 1, BE §7.7 — "unplug the network and still get answers") — they verify the system does what was *asked* (CR §4.1 — the most important correctness dimension), not just what it was built to do. They're the bridge between "the code works" (§5.1–5.3) and "the software is fit for its purpose" (§1.1 intended, Stage 0) — and passing them is the real definition of done (BE §7.7).

**5.5 — Regression suites.** The accumulated tests that guard against reintroducing past defects (§3.9, §2 Stage 6). Run on every change (BE §3.7), the regression suite is the system's immune memory (§1.2) — every defect it's ever had, pinned so it can't return (DBG §2 Stage 7, [M12]). Architecturally, the regression suite spans all levels (§5.1–5.3 — a regression test lives at whatever level catches its defect) and *grows monotonically* with the system's history. Its discipline is maintenance (§2 Stage 7 — pruning tests that no longer mean anything, fixing flakiness §7.2) so it stays fast and trustworthy.

**5.6 — Smoke tests.** A fast, shallow test that the system *basically works* — the critical paths function, nothing is grossly broken. Run first (before the fuller suite) and frequently (after every deploy, §8.5 as a synthetic production check §3.10) — a smoke test failing means "stop, something fundamental is broken" before spending time on deeper tests. Smoke tests are the cheapest confidence (a quick "is it alive and doing the main thing") — the first line of §2 Stage 4, and the continuous production check (§3.10) that catches a broken deploy fast (DBG §13.8 — the outage caught by a failing smoke test).

**5.7 — Canary tests.** Testing a change against a *fraction* of production before all of it (§3.10) — exposing the new version to a small slice of real traffic/use, monitoring (§8.5) for defects, and rolling forward only if healthy (or back if not, AE §8.5). Canary testing is production validation (§3.10) with bounded blast radius [M8] — a defect that escaped all pre-production testing (§1.4 — something always can) affects the canary fraction, not everyone, before it's caught. The safest way to validate against real production (§3.10) — it accepts §1.4 (testing can't prove correctness) and bounds the cost of the residual risk.

**5.8 — Chaos testing.** Deliberately inducing failures in production (or production-like environments) to verify the system handles them (§4.8 recovery, AE §8 — resilience). Chaos testing is §4.3 (failure cases) and §4.8 (recovery) applied to the *live system at scale* — kill a node, sever a network, exhaust a resource, and verify the system degrades gracefully (AE §8.7) and recovers (§4.8) rather than cascading (DBG §3.11). It's the rehearsal [M12] that proves resilience is real (AE §8, FABLE §27 — trust rehearsals not plans), essential for distributed systems (§12.2, DBG §3.11) where failure is constant and the question is whether it's survived.

**5.9 — Simulation.** Testing against a *modeled* environment when the real one is unavailable, expensive, dangerous, or slow. Simulation enables testing that's otherwise impossible: long-running behavior accelerated (§4.11 — months in minutes), rare conditions forced (§4.6 concurrency, §4.3 failures), expensive/dangerous scenarios safe (a production outage, a data corruption). The caveat [M2]: a simulation is a *model*, and the model can diverge from reality (§9 — a test that passes in simulation and fails in reality means the simulation was wrong) — so simulation supplements but never fully replaces reality contact (§3.10 production validation, RE §Stage 6).

**5.10 — Golden datasets.** A curated set of known-correct input→output pairs (or input→property, §3.5) used as a fixed reference — especially for testing where "correct" is complex to compute but known for specific cases (AI outputs §6, data transformations, complex logic). The golden dataset is the *specification by example* — the system is correct if it reproduces the golden outputs (or, for AI §6.1, matches them closely enough / passes the golden properties). Discipline: the golden dataset must be *maintained* (§2 Stage 7 — a legitimate behavior change updates the golden set deliberately, not silences it) and *trusted* (the golden outputs are verified-correct, not just "what the system currently produces" — else it's a tautology §9.1, pinning current behavior as if it were correct behavior).

**5.11 — Synthetic environments.** Controlled, reproducible environments that replicate production's relevant properties for testing (§4.4 of DBG — capturing the environment). Synthetic environments make tests *reliable* (§7.2 — a controlled environment removes the environmental flakiness §7.5) and *faithful* (matching production's relevant properties, so environment-class defects DBG §3.6 surface in test not production DBG §9.3 — the "staging matches production" discipline DBG §13.8). The tradeoff: fidelity vs cost (a perfectly faithful environment is production itself; a cheap one may miss environment-specific defects) — build the synthetic environment faithful in the properties that *matter* for what's being tested (§3.1 risk-based, applied to environment fidelity).

**5.12 — Test data management.** The discipline of the data tests run against — because tests are only as good as their data (a test with unrealistic data tests unrealistic behavior). Manage: *realistic* data (representative of production's real distribution §1.4, including the awkward real cases §4.2), *controlled* data (reproducible, so tests are deterministic §7.2), *safe* data (no real secrets or personal data in test — a privacy and security requirement, AE §8.6, Law 9), and *edge* data (deliberately including the boundaries §4.2 and adversarial §4.4 cases). Test data is often where testing quietly fails — happy-path data produces happy-path testing (§9.4), and unrealistic data produces false confidence (§1.3) that evaporates on real input (§3.10).

# 6. AI-Native Testing

Testing the artifacts with the least testing tradition — probabilistic, context-dependent AI systems. This gets the most depth because a successor will find the least prior art. The governing principle: **AI systems are probabilistic and context-dependent (OE §12, DBG §8), so testing shifts from "does it produce the right output" to "does it produce acceptable output reliably enough, and are its failures contained" — you test the distribution and the guardrails, because you can't test a probabilistic system the way you test a deterministic one.**

**6.1 — The AI-native testing shift.** Classical testing assumes determinism (same input → same output, so one passing test proves that case). AI testing can't (§4.10, DBG §8.1 — same input may vary). This changes test design fundamentally: test *distributions* (run many times, verify the output is acceptable *reliably enough* — a pass rate, not a single pass, §6.1); test *properties* (§3.5 — the output always satisfies constraints, even if it varies — always valid format, always within bounds, never leaks the secret) rather than exact matches; test the *guardrails* (§6.9 of CR, AE §9.5, §9.6 — the gates and boundaries that *contain* the probabilistic behavior) *more* than the behavior itself, because you can't guarantee the model's output but you *can* guarantee its output is caught if wrong (OE §8, the verification architecture); and use *golden datasets* (§5.10) with *fuzzy* matching (the output matches the golden closely enough, or passes the golden's properties, not character-for-character). The mental shift: *you're testing a stochastic component, so you test its statistics and its containment, not its determinism.*

**6.2 — Testing prompts.** A prompt is an interface with a nondeterministic component (RE §30, CR §9.2) — test it like an interface with statistical behavior (§6.1). Test: does the prompt produce the intended behavior *reliably* across many runs (§6.1 distribution)? does it hold at the *edges* (RE §30 — the awkward inputs, §4.2)? is it robust to *adversarial* input (§4.4 — injection §6.9 of CR, does hostile content in the input override the instructions)? does it survive *model replacement* (§6.9 — test the same prompt across models, FABLE §15, so it's not overfit to one model's quirks RE §30)? Test prompts on *real* inputs (RE §30 — a prompt untested on the awkward case fails on it) via golden datasets (§5.10) of input→acceptable-output. Prompt testing is regression-critical (§3.9 — a prompt change can silently regress behavior, so pin the behavior with tests that run on prompt changes, CR §9.2 — prompt regressions are real regressions).

**6.3 — Testing MCP servers.** An MCP server is a capability behind a protocol (AE §9.10, CR §9.3) — test it as an integration (§5.2 contract §3.3) and as ordinary software (§4, §5) and for AI-specific security (§6.9 of CR). Test: does it honor the MCP contract (§3.3, AE §4.3)? does it handle malformed/adversarial calls (§4.3, §4.4 — an agent's calls may be driven by untrusted content §6.9 of CR)? is its tool surface correctly scoped and its failures safe (AE §8.1)? are its trust boundaries enforced (§6.9 of CR, AE §8.2)? MCP servers are tested as contracts (§3.3) because they're seams the system depends on (AE §9.10) — and tested adversarially (§4.4) because they're a capability grant (CR §6.9, an agent's power to act).

**6.4 — Testing A2A systems.** Agent-to-agent coordination (AE §9.10, OE §7) — test for the coordination failures (OE §12.3–12.9) and the interaction, not just the individual agents. Test: do agents coordinate correctly through their shared state (OE §7.4 — the coordination is inspectable, so testable)? do they handle conflict, duplication, and ordering (OE §7.6, §12)? does the system behave correctly when an agent fails (§4.3, §4.8 — a dead agent doesn't strand the others, OE §7.4)? A2A testing is §5.2 (integration) and §5.3 (system) applied to a fleet — the defects are in the *interaction* (OE §12.8), so the tests exercise the coordination, and often use §5.9 (simulation) to force the rare interaction failures (a race in claiming work OE §13.3).

**6.5 — Testing memory.** An AI memory system (AE §5.3, DBG §8.6, CR §9.7) — test for the memory failures (DBG §8.6, OE §12.7) and the store/index architecture. Test: the *store/index consistency* (§3.5 property — the index always reflects the store, and critically, the index *rebuilds correctly from the store*, AE §5.3 — the falsifiable test "delete the index, rebuild, search still works" BE §7.7, PE §5); *provenance and trust* (§6.9 — untrusted-derived memory is quarantined, AE §5.3, and can't become trusted without review, the injection-persistence test DBG §8.6); *recall correctness* (the right memory is retrieved for a query, §6.8); *staleness handling* (a superseded memory isn't recalled as current, RE §5.2); and *consolidation* (§4.11 — memory doesn't rot over time, DBG §8.10, tested with §5.9 accelerated aging). Memory testing verifies the system won't poison itself (DBG §8.6) or lose its knowledge (AE §9.9) — the highest-stakes long-running AI properties.

**6.6 — Testing Graphify (knowledge graph).** A graph recall tier (AE §9.8, CR §9.6) — test its correctness as an index and its placement in the recall architecture. Test: the graph *rebuilds correctly from the neutral store* (§6.5 — it's a rebuildable index AE §5.4, §9.8, so the rebuild is a §3.5 property test); *query correctness* (relationship/path/community queries return correct results, §6.8 — tested against a golden dataset §5.10 of known-correct graph queries); the *baseline fallback* (§8.7 of AE — if the graph is unavailable, recall degrades to full-text, not to nothing, tested by §4.3 inducing graph-unavailability); and *provenance* (graph-derived answers trace to sources, AE §5.3). Graphify testing verifies it's a correct *enhancement* over a guaranteed baseline (AE §9.8) — never a single point of recall failure.

**6.7 — Testing autonomous agents.** Agents acting without real-time oversight (OE §15.6, CR §9.8, DBG §8.9) — tested with the highest rigor because failures aren't caught in the moment (DBG §8.9). Test: the *guardrails* (§6.1 — the gates AE §9.5 hold, so irreversible actions can't proceed unapproved; the loop bounds OE §12.5; the drift checks OE §12.6; the escalation on uncertainty OE §8.5); the *blast radius of worst behavior* (§4.4 adversarial — what's the worst this can do unsupervised, and is it contained, AE §8.4, [M16]); and the *journaling* (DBG §8.9 — the agent records its actions/reasoning, so post-hoc testing/debugging is possible). Autonomous-agent testing tests *containment more than correctness* (§6.1) — because you can't guarantee the agent's every decision, but you can and must guarantee its failures are bounded and gated (the "would I let this act unsupervised on my behalf" bar, CR §9.8).

**6.8 — Testing context retrieval.** The retrieval that assembles an agent's context (OE §5, §6, DBG §8.3) — test that the *right* knowledge reaches the agent. Test: *relevance* (the retrieved knowledge bears on the task, §6.6 — tested against golden query→expected-retrieval sets §5.10); *completeness* (the needed knowledge is retrieved, not missed — a missing fact causes hallucination §6.9, DBG §8.3, §13.9); *freshness* (current knowledge, not stale, RE §5.2); *no poisoning* (§6.5 — untrusted content doesn't reach the context as trusted, §6.9 of CR). Context-retrieval testing is high-value because bad retrieval is a top cause of AI failure (DBG §13.9 — the hallucination caused by a missing retrieved fact) — testing retrieval quality directly tests a major failure source.

**6.9 — Testing model replacement.** Verifying the system works when the model changes (AE §7.5, §9.2, FABLE §15, OE §11.8) — the parity test. Test: the same tasks/prompts (§6.2) through the *replacement* model produce acceptable results (§6.1 distribution) — the system's behavior survives the swap (AE §9.2 — models are behind a seam, so replacement should be a config change, and this test *proves* it). Model-replacement testing is run *periodically* (OE §11.8 — the weekly parity job, not just at swap time) so replacement is a rehearsed transition (§4.8, [M12]) not a first-time emergency (AE §7.6). It's the test that keeps provider-agnosticism *real* (AE §9.5, ADR-010 — the lesson that agnosticism must be exercised, not asserted) rather than a claim that fails when finally needed.

**6.10 — Testing multi-model systems.** A system routing across models (OE §4, §9.2) — test the routing and the cross-model behavior. Test: *routing correctness* (the right model tier for the task, OE §4 — a task routed to the wrong tier is a defect); *fallback* (§4.3 — when a model/provider is unavailable, the fallback chain works, OE §9.2, ending local Law 6); *consistency* (the system behaves acceptably regardless of which model served, §6.1 — since routing may vary); and *cross-model verification* (OE §8.3 — where the system uses model disagreement as a check, test that the disagreement-detection works, DBG §8.8). Multi-model testing verifies the seam (AE §9.2) that makes models swappable actually delivers swappability and graceful degradation (§8.7 of AE).

**6.11 — Testing long-running AI workflows.** Workflows running for months (OE §11, §4.11, DBG §8.10) — test the time-dependent behaviors classical testing doesn't reach. Test: *accumulation failures* (§4.11 — memory rot §6.5, knowledge corruption AE §5.6, context drift OE §12.6, tested with §5.9 accelerated time); *stability over time* (the workflow doesn't degrade, OE §12 — tested by long-horizon monitoring §3.10 or acceleration §5.9); *recovery across sessions* (§4.8 — the workflow resumes correctly from checkpoints OE §11.4, survives model replacement §6.9 and context boundaries OE §5); and *drift detection* (OE §12.6 — the workflow stays on-goal over the long horizon). Long-running AI testing is the hardest (§4.11 — slow failures, requiring acceleration or patience) and the most necessary for autonomous long-running systems (OE §11), where the failures that matter most are precisely the slow ones that short tests never see (DBG §8.10).

# 7. Failure Analysis

How to interpret a failing test correctly — because a test failure is *information*, and misinterpreting it (dismissing a real defect as flakiness §7.2, or chasing a false positive §7.3) is where test suites lose their value. The governing principle: **a failing test is a claim that something is wrong — investigate the claim before trusting or dismissing it, because the two failure modes (trusting a false alarm, dismissing a real defect) are both corrosive, and "probably flaky" is how real defects get ignored (§9.7).**

**7.1 — How failed tests are interpreted.** A test failure means the observed behavior diverged from the expected (§1.1) — and the divergence is in *one of three places*: the *code* (a real defect — the valuable case, → debug DBG §2), the *test* (the test is wrong — a false positive §7.3, or the expectation is stale AE §4.7), or the *environment* (§7.5 — the test infrastructure, not the software). Interpretation is *diagnosis* (DBG §2 Stage 0 — read the failure completely, don't assume) — and the discipline is to *not assume which* before investigating (§9.7 — assuming "flaky" §7.2 dismisses real defects; assuming "real" chases false positives). The most valuable failure is a real defect caught before production; the most dangerous *response* is dismissing it as noise.

**7.2 — Flaky tests.** A test that passes and fails non-deterministically without the code changing (DBG §3.3 — usually a concurrency, timing, or environmental §7.5 issue *in the test*, or a real non-determinism in the code §6.1). Flaky tests are *corrosive* (§9.7) — they train everyone to ignore failures ("just rerun it"), and a real defect hides in the noise (§7.1). Discipline: a flaky test is a *defect in the test suite* (or a real intermittent bug in the code DBG §3.3), to be *fixed or removed*, never tolerated (§9.7) — because a suite with flaky tests is a suite whose green is no longer trustworthy (§1.3, false confidence). Diagnose flakiness like any bug (DBG §4.2 — make it deterministic): is the test's non-determinism its own (fix the test) or the code's (a real concurrency bug §4.6, the more important finding)?

**7.3 — False positives (the test is wrong).** A test that fails when the code is actually correct — the test's expectation is wrong, stale (AE §4.7 — the contract legitimately changed and the test wasn't updated §2 Stage 7), or testing implementation not behavior (§9.1 — the test broke because the implementation changed though the behavior didn't). False positives erode trust (a suite that cries wolf, CR §10.9) and waste effort (investigating a non-defect). Fix: update the test to the correct expectation (if the behavior legitimately changed AE §4.7) or fix the test's design (if it was testing implementation §9.1, rewrite it to test behavior §3.2). A false positive is a *test-quality* defect (§2 Stage 7 maintenance).

**7.4 — False negatives (the test misses a real defect).** A test that passes when the code is actually wrong — the most *dangerous* failure because it's *silent* (nothing alerts you; the defect ships with a green checkmark, §1.3). False negatives are found only *downstream* (a defect reaches production that the tests "covered," §3.10, DBG §7.4) — and each one reveals a gap in the test strategy (§1.5 — the defect the suite should have caught). Discipline: for every defect that escaped to production (or debugging DBG), ask "why did the tests pass?" (§1.5) — the answer is a false negative, and the fix is a test that would have caught it (§3.9 regression) *plus* consideration of its *class* (§3.1, DBG §5.6 — what else does this gap miss). False negatives are why coverage is a vanity metric (§9.5 — a suite can have high coverage and many false negatives, covering lines without verifying behavior).

**7.5 — Environmental failures.** A test failure caused by the test infrastructure, not the software (DBG §3.6 — a missing dependency, a resource limit, a network issue, a dirty environment §5.11). Environmental failures masquerade as code defects (§7.1) and as flakiness (§7.2). Discipline: distinguish environment from code (DBG §11.2 — does it fail in a clean/controlled environment §5.11?) — and fix the *environment* (make it reliable §5.11, synthetic environments) so environmental noise stops polluting the signal. Recurring environmental failures are a test-infrastructure defect (§2 Stage 7) — the environment should be controlled enough (§5.11) that its failures are rare and obvious.

**7.6 — Data failures.** A test failure caused by bad test data (§5.12) — unrealistic, stale, corrupt, or wrong-expectation data. Data failures masquerade as code defects (§7.1). Discipline: verify the *data* is correct before trusting the failure (is the golden dataset §5.10 actually correct, or is *it* stale §5.10 maintenance?) — a test failing because its golden data is wrong is a §7.3 false positive rooted in data. Manage test data (§5.12) so data failures are rare.

**7.7 — Model failures (AI systems).** An AI test failure caused by the model's probabilistic behavior (§6.1, DBG §8.1) — the model produced an unacceptable output. Discipline: distinguish a *real* model-behavior defect (the model reliably does the wrong thing — a prompt §6.2 or context §6.8 problem to fix) from *acceptable variance* (the model occasionally varies within tolerance — §6.1, expected, and the test's pass-threshold should account for it). A model test failing *once* may be variance (§6.1 — run it multiple times to see the rate); failing *reliably* is a real defect (§7.1 → debug the prompt/context/routing DBG §8). Model-failure analysis requires the §6.1 statistical lens — a single failure isn't necessarily a defect, and a single pass isn't necessarily correctness.

**7.8 — Infrastructure failures.** A failure in the systems the software runs on (DBG §3.6, §9.7 cloud) — distinct from test-environment failures §7.5 in that it's the *production* infrastructure. Discipline: distinguish software defects from infrastructure defects (DBG §11.6 hardware, §9.7 cloud — the platform's failure vs the code's) — because the fix differs (fix the code vs fix/route-around the infrastructure). Infrastructure failures in testing often reveal *untested assumptions* about the infrastructure (§9.8, DBG §3.6 — the environment assumption that was false).

**7.9 — Root cause isolation.** When a test fails, isolate the *actual* cause (DBG §5 — root cause not crash site, §2 Stage 5) before fixing. A test failure points at a divergence (§7.1); root-cause isolation (DBG §5, bisection [M4]) finds *why* — which of the three places (§7.1) and specifically what. This is where testing hands off to debugging (§1.5, DBG) — the test *detected*, debugging *diagnoses*. The discipline: don't fix a test failure at the surface (§10.9 of DBG — silence the failing test, the worst response) — isolate the root cause and fix *that* (the code defect, or the test defect §7.3, or the environment §7.5).

**7.10 — Confidence recalibration.** The meta-purpose of failure analysis: *adjust confidence to match reality* [M20]. A real defect found (§7.1) that the tests *should* have caught but didn't (§7.4 false negative) means the confidence the suite justified was too high — recalibrate (the suite is weaker than believed, §1.3). A defect found *early* by a good test means the suite is working (confidence justified). Every production incident (§3.10, DBG §9.3) is a confidence-recalibration event (§1.5 — the suite missed it, so the suite justifies less confidence than its green implied). Confidence recalibration is the honest accounting [M20] that keeps testing's output (§1.3 justified confidence) actually justified — a suite whose gaps are known produces *calibrated* confidence (we trust it *this much*, knowing it misses *these things*), which is worth far more than a suite falsely believed complete (§9.5, §9.9).

# 8. Test Automation

What to automate, what not to, and how — because automation is what makes testing *continuous* (§2 Stage 4, the regression guard §3.9) but also what can produce false confidence at scale (§9.5) and cost (§8.8). The governing principle: **automate what must run repeatedly and can be checked mechanically; keep human judgment where the check requires judgment — because automation scales repetition, not wisdom, and automating a judgment that needs a human produces a check that passes while being wrong.**

**8.1 — What should be automated.** Anything that must run *repeatedly* and can be *checked mechanically*: the regression suite (§3.9, §5.5 — run on every change, BE §3.7, the highest-value automation), the build-time verification levels (BE §7 — compile, static, runtime, behavior), smoke tests (§5.6 — every deploy), the deterministic behavioral tests (§5.1–5.3), the security ratchets (§4.9, the injection canary BE §14.2). Automation's value is *continuity* (the test runs every time, catching regressions the moment they're introduced §3.9, [M12] a ratchet) and *tirelessness* (it never skips the check under pressure, unlike a human). Automate the mechanical, repeated verification — that's most of testing.

**8.2 — What should never be automated (or: what needs human judgment).** The checks that require *judgment* the automation can't encode: *exploratory testing* (§3.7 — discovering the unexpected requires a mind, not a script), *the final fitness judgment* (CR — is this actually good, not just does-it-pass), *the acceptance of AI-output quality* where "acceptable" is a judgment call (§6.1 — a human/judgment-agent assessing whether the probabilistic output is *good*, not just within-format), and *the approval of irreversible/outward actions* (AE §9.5, OE §9.2 — the human gate, which is deliberately not automated because a human must own the downside DE §10.6). The discipline: automation scales *repetition*, not *wisdom* — automating a judgment produces a check that runs a thousand times being wrong the same way (§9.5 — the automated check that passes while missing the point). Keep judgment where judgment is needed; automate the rest.

**8.3 — Regression automation.** The core automation (§3.9, §5.5) — the regression suite runs automatically on every change (BE §3.7), continuously (§2 Stage 4). This is the highest-value automation because regression is the highest-value testing (§1.2 — preserving correctness over change) and it's purely mechanical (re-run the known-correct checks). Regression automation is the ratchet [M12] that makes a system safe to keep changing (AE §1.3) — without it, every change risks silent regression (DBG §11.5), and the fear of that freezes the system.

**8.4 — Continuous validation.** Automated testing integrated into the change flow (every commit/change triggers the relevant tests, BE §3.7, §7) — so defects are caught at the change that introduces them (DBG §11.5), not later. Continuous validation makes the trunk-stays-green discipline (BE §3.7, FABLE §19) enforceable by machine [M12] — a change that breaks the tests is caught immediately, before it's built upon. It's the automation of §2 Stage 4 (execution) as a continuous ratchet rather than a periodic event.

**8.5 — Production monitoring.** The automation of production validation (§3.10) — continuously observing real production behavior for anomalies (metrics §7.3 of DBG, error rates, latency, the trends that reveal slow failures DBG §8.10). Production monitoring is testing that *never stops* (§1.4, §3.10 — the sampling continues in production where the real distribution arrives), catching the defects that escaped pre-production (§7.4 false negatives, DBG §9.3 the production-only class). It's how a long-running system (OE §11) catches its slow failures (§4.11, DBG §8.10) before they become incidents — the automated trend-watch that turns "discovered in July, started in March" (DBG §8.10) into "caught the week it started."

**8.6 — Human approval (in the automation flow).** Where automation reaches an irreversible/outward action (AE §9.5, OE §9.2), it *stops for human approval* — the deliberate non-automation (§8.2) built into the automated flow. The automation does everything up to the blast-radius boundary (§8.4 continuous validation), then gates (the outbox AE §9.5) — so the flow is automated *and* the human owns the consequential decision (DE §10.6). This is the resolution of automation-vs-control (OE §9.3): automate the verification, gate the action.

**8.7 — Autonomous verification.** AI systems verifying their own or each other's work (OE §8 — the verification architecture, adversarial verification RE §9.7). Autonomous verification automates the *judgment* checks (§8.2) that classical automation can't — an independent AI verifier (OE §8.1) assessing whether output is correct, prompted to refute (OE §8.2). The discipline (OE §8): autonomous verification must be *independent* (a different context/model than produced the work, OE §8.1, §8.3 — else it inherits the blind spot §1.6) and *scaled to stakes* (OE §8.4 — consensus for high-stakes). It's how AI-native systems test the un-mechanical (§6.1 — is the AI output *good*), extending automation into judgment via *independent AI judgment* — but it never fully replaces human judgment at the highest stakes (§8.2, §8.6 — the human gate).

**8.8 — Cost-aware automation.** Automated testing costs (compute, time, and for AI systems, inference §10 of OE) — so automation is *allocated* by value (§3.1 risk-based, applied to automation cost). The expensive tests (§5.3 system, §5.8 chaos, §6 AI-native with real inference) run less often (on releases, nightly) than the cheap ones (§5.1 unit, §5.6 smoke — every change). Cost-aware automation runs the *right* tests at the *right* frequency (the cheap fast ones continuously §8.4, the expensive comprehensive ones at meaningful gates §5.3) — so the suite stays fast enough to run continuously (§5, the wide-base-narrow-top architecture) without the cost of running everything every time. For AI testing especially (§6, inference cost OE §10), cost-awareness matters — running expensive model tests on every change is prohibitive, so they're gated (§10.9 fast-vs-comprehensive).

# 9. Test Anti-Patterns

Named for in-flight detection. Each carries its signal and cure. These are how testing produces the false confidence (§1.3) it exists to prevent — the ways a suite feels like safety while providing none.

**9.1 — Testing implementation instead of behavior.** Tests welded to *how* the code works rather than *what* it does (FABLE §17, §3.2). *Signal:* the tests break when you refactor without changing behavior (BE §8 — a refactor that preserves behavior should keep tests green; if it breaks them, they test implementation); tests that mirror the code's structure rather than its contract. *Cure:* test behavior/contract (§3.2, AE §4.3) — treat the implementation as a black box (§10.3). Implementation-testing punishes the refactoring you want to encourage (BE §8 — it makes the tests a barrier to improvement) and produces false positives (§7.3) on every legitimate refactor.

**9.2 — Over-mocking.** Replacing so many real dependencies with mocks that the test no longer exercises real behavior (§10.3). *Signal:* the test passes but the real integration fails (§5.2 — the mocks behaved as assumed, the real dependency didn't, RE §5 — the map [M2] of the dependency, not the territory); tests that verify the code calls the mock correctly rather than that the behavior is correct. *Cure:* mock only what you must (§10.3 — external, slow, or nondeterministic dependencies), test against real components where feasible (§5.2 integration — the seams AE §4 need real testing). Over-mocking produces tests that verify the code matches your *assumptions* about its dependencies (§1.4 of DBG — the assumption that may be false) rather than reality [M2] — high coverage, false confidence (§9.5).

**9.3 — Fragile tests.** Tests that break easily on unrelated changes (§9.1 implementation-testing, over-specific assertions, timing dependence §7.2). *Signal:* small unrelated changes break many tests; tests that fail for reasons unrelated to the behavior they're meant to verify. *Cure:* test behavior (§3.2), assert on what matters (not incidental detail), remove timing/order dependence (§7.2). Fragile tests are a maintenance burden (§2 Stage 7 — they cost effort on every change) that trains people to ignore or delete tests (§9.7-like erosion) — the opposite of the suite's purpose.

**9.4 — Happy-path-only testing.** Testing only that the software works when everything goes right (§4.1). *Signal:* the tests exercise the primary path and no edges (§4.2), failures (§4.3), or adversarial cases (§4.4); the suite is green and production still breaks at the edges. *Cure:* design for the edges and failures (§4.2, §4.3 — where the confidence is actually bought §3.4, where bugs cluster DBG §1.3). Happy-path-only testing is the most common false-confidence pattern (§1.3) — it produces a green suite that verifies the least-likely-to-break behavior and misses the most-likely, so the confidence is entirely unjustified (the defects are exactly where the tests aren't).

**9.5 — Coverage obsession.** Treating code coverage (lines/branches executed by tests) as the goal (§7.4, [M19] Goodhart). *Signal:* chasing a coverage percentage; tests written to execute lines rather than verify behavior (§9.1 — a test that runs a line without meaningfully asserting on it raises coverage and verifies nothing). *Cure:* coverage is a *weak proxy* (§1.3, [M19] — it measures what's executed, not what's verified); the real question is "would the suite catch the defects this can plausibly have?" (§3.1, DBG §6.3), which coverage doesn't answer. High coverage with happy-path assertions (§9.4) is high false-negative (§7.4) — covered lines, unverified behavior. Aim for confidence justified by *what's verified* (§1.3), and treat coverage as at most a check for *un*-tested regions, never as the target [M19].

**9.6 — Ignoring production.** Treating pre-production testing as sufficient, not validating in production (§3.10). *Signal:* no production monitoring (§8.5), no canary (§5.7), surprised by production-only defects (DBG §9.3). *Cure:* production validation (§3.10) — because testing can't prove correctness (§1.4) and production is where the real distribution arrives (§3.10, DBG §9.3 — the class that only appears in production). Ignoring production is believing the pre-production suite is complete (§9.5, §9.9 — the false confidence that the sampling §1.4 was exhaustive, which it never is).

**9.7 — Tolerating flaky tests.** Accepting non-deterministic test failures rather than fixing them (§7.2). *Signal:* "just rerun it" is the response to failures; the team no longer trusts red (§7.1 — a real defect hides in the flaky noise). *Cure:* fix or remove flaky tests (§7.2 — a flaky test is a suite defect); a suite must be trustworthy (green means correct, red means broken) or it's noise (§1.3). Tolerating flakiness is *corrosive* (§7.2) — it destroys the suite's signal value, and the real defect that fails "flakily" gets rerun-until-green and ships (§7.4).

**9.8 — Untested assumptions.** Behavior that rests on an assumption no test verifies (DBG §1.4, §5.5 — the environment is X, the input is always Y, this runs after Z). *Signal:* the system works until an assumption is violated, and no test would have caught the violation (§7.4 false negative — the assumption was never tested). *Cure:* identify the load-bearing assumptions (DBG §1.4, §5.4 — enumerate what the behavior assumes) and test them (§4.3 — what happens when the assumption is false). Untested assumptions are where the surprising production defects live (DBG §3.6 environment, §5.5 hidden dependencies) — the test suite verifies the behavior *under its assumptions* and never checks the assumptions themselves.

**9.9 — False confidence (the meta-anti-pattern).** The suite produces more confidence than it justifies (§1.3) — the failure all the others (§9.1–9.8) produce. *Signal:* green suite, confident deployment, production defects the suite "covered"; confidence based on test *count* or *coverage* (§9.5) rather than *what's verified* (§1.3). *Cure:* the whole discipline of justified confidence (§1.3, §7.10 recalibration) — ask always "what do these tests actually verify, and does that justify the trust we're placing?" [M20]. False confidence is the *worst* testing outcome (worse than no tests §1.3) because it licenses untrusted trust — the deployment made confidently on a suite that didn't check what mattered, failing where nothing was watching. Every other anti-pattern is a *way* of producing false confidence; this is the thing to detect and fear.

# 10. Testing Decision Trees

Built per [M7 → skill S-007]. Testing-specific; defer to prior engines where the decision is theirs.

**10.1 — Unit vs Integration**
```
Is the behavior being verified WITHIN one unit, or ACROSS units (a seam)? (§5.1, §5.2, AE §4)
  ├─ within one unit (local logic §3.1) → UNIT test (fast, numerous, base of the architecture §5.1)
  └─ across units (the seam, the contract, the integration §3.3) → INTEGRATION test (§5.2 — catches what units can't, AE §8)
       (rule: unit tests prove the parts; integration tests prove they FIT — you need both, weighted toward units §5)
```

**10.2 — Integration vs System**
```
Does the confidence needed span the WHOLE system end-to-end, or a subset of integrated components?
  ├─ subset (some components together §5.2) → INTEGRATION test
  └─ whole system / real workflow / fitness-for-purpose (§3.6, §5.4) → SYSTEM/ACCEPTANCE test (§5.3, §5.4)
       (fewer, slower, top of the architecture §5.3 — a few good ones catch whole categories, FABLE §17)
```

**10.3 — Mock vs Real**
```
Is the dependency external, slow, nondeterministic, or unavailable in test?
  ├─ no (fast, deterministic, available) → use the REAL thing (§9.2 — testing reality [M2] beats testing assumptions)
  └─ yes → MOCK it — but mock the MINIMUM (§9.2 over-mocking), and ALSO have an integration test (§5.2) against the
       real dependency somewhere, so the mock's assumptions [M2] are validated against reality (§9.2 — the mock is a map)
```

**10.4 — Simulation vs Production**
```
Is real production available, safe, affordable, and fast enough to test against? (§5.9, §3.10)
  ├─ yes → validate against PRODUCTION (§3.10 — the real distribution §1.4; canary §5.7 to bound blast radius [M8])
  └─ no (unavailable/dangerous/expensive/slow — e.g. long-running §4.11, chaos §5.8, rare conditions) →
       SIMULATION (§5.9), knowing it's a model [M2] that can diverge — supplement with production validation (§3.10) when possible
```

**10.5 — Manual vs Automated**
```
Does the check require JUDGMENT, or is it mechanical and repeated? (§8.1, §8.2)
  ├─ mechanical + repeated → AUTOMATE (§8.1 — regression §8.3, continuous §8.4; the ratchet [M12])
  ├─ judgment, but AI-assessable → AUTONOMOUS VERIFICATION (§8.7, OE §8 — independent AI judgment, scaled to stakes)
  └─ judgment needing a human (fitness CR, exploratory §3.7, irreversible-action approval AE §9.5) → MANUAL/HUMAN (§8.2, §8.6)
       (rule: automate repetition, not wisdom §8.2 — automating a judgment produces a check that's wrong the same way forever)
```

**10.6 — Regression vs Exploratory**
```
Am I PROTECTING known behavior, or DISCOVERING unknown behavior?
  ├─ protecting (known-correct behavior must not break) → REGRESSION (§3.9, automated §8.3 — the accumulated guard)
  └─ discovering (new/poorly-understood system, hunting for the unexpected §9.8) → EXPLORATORY (§3.7, human/judgment §8.2)
       (they feed each other §3.7 → §3.9: exploration discovers, regression pins what's discovered)
```

**10.7 — Local vs Cloud (where to run tests)**
```
Does the test need cloud-specific behavior/scale/environment, or is it environment-independent?
  ├─ environment-independent (logic §3.1, unit §5.1) → LOCAL (fast, cheap, offline Law 6, run continuously §8.4)
  └─ needs real scale/cloud-environment/production-fidelity (§3.10, DBG §9.7) → CLOUD/production-like (§5.11 synthetic env,
       §5.7 canary) — but keep a local baseline (Law 6 — the offline-testable core must be locally testable)
```

**10.8 — Fast vs Comprehensive**
```
How often must this run, and what does it cost? (§8.8 cost-aware)
  ├─ every change (§8.4) → the FAST subset (unit §5.1, smoke §5.6 — seconds, so the trunk stays green BE §3.7)
  └─ meaningful gates (release, nightly) → the COMPREHENSIVE suite (system §5.3, chaos §5.8, expensive AI tests §6, §8.8)
       (architecture §5: wide fast base runs always, narrow slow top runs at gates — so continuous testing stays continuous)
```

**10.9 — Single Model vs Multi Model (AI testing)**
```
Does the system depend on a specific model, or must it survive model replacement? (§6.9, §6.10, AE §9.2)
  ├─ must survive replacement (it should — AE §9.2, FABLE §15) → test across MULTIPLE models (§6.9 parity, §6.10 —
  │     prove the behavior survives the swap, run periodically OE §11.8 so replacement is rehearsed [M12])
  └─ single-model-specific behavior being tested (a prompt tuned to one model §6.2) → test on THAT model, but flag the
        coupling (RE §30 — model-specific prompts are fragile FABLE §15; prefer model-agnostic §6.9)
```

# 11. Testing Checklists

The engine compressed. Run the long form (§2–§8) until reflex.

**11.1 — Before trusting software (the confidence gate)**
- [ ] Do I know what "correct" MEANS for this — the contract/requirement I'm testing against? (§2 Stage 0)
- [ ] Are the highest-RISK behaviors tested thoroughly (walls [M6]), not everything tested equally? (§3.1, BE §7.8)
- [ ] Do the tests verify BEHAVIOR (contract), not implementation? (§3.2, §9.1)
- [ ] Are the EDGES, FAILURES, and adversarial cases tested — not just the happy path? (§4.2, §4.3, §4.4, §9.4)
- [ ] Would these tests actually CATCH the defects this can plausibly have? (§3.1, DBG §6.3, §7.4)
- [ ] Is my confidence JUSTIFIED by what the tests verify — or by their count/coverage? (§1.3, §9.5, §9.9, [M20])
- [ ] Have I tested the ASSUMPTIONS the behavior rests on, not just the behavior under them? (§9.8, DBG §1.4)
- [ ] For AI systems: tested the distribution and the guardrails, not just one lucky output? (§6.1, §6.7)

**11.2 — Before release**
- [ ] Do the acceptance tests (the falsifiable done-when) pass, freshly run and observed? (§5.4, BE §7.7, [M2])
- [ ] Does the full regression suite pass — nothing that worked is now broken? (§3.9, §5.5)
- [ ] Are integration and system tests green — the parts fit, the whole works? (§5.2, §5.3)
- [ ] Is recovery tested — backup restores, rollback works, degraded mode functions? (§4.8, AE §8.5)
- [ ] Is the suite trustworthy — no tolerated flakiness poisoning the signal? (§7.2, §9.7)
- [ ] For high-stakes: security tested adversarially, performance at realistic scale? (§4.9, §4.7)

**11.3 — Before automating a test**
- [ ] Is this mechanical and repeated (automate §8.1), or does it need judgment (keep human/autonomous §8.2, §8.7)?
- [ ] Is the test reliable (deterministic §7.2) — or would automating it just run a flaky test forever? (§9.7)
- [ ] Does it test behavior (§3.2) so it survives refactoring, or is it fragile/implementation-bound? (§9.1, §9.3)
- [ ] Is it worth its running cost at the frequency it'll run? (§8.8 cost-aware, §10.8)

**11.4 — Before production deployment**
- [ ] Smoke tests ready to run post-deploy (§5.6), and is deploy staged/canaried to bound blast radius? (§5.7, [M8])
- [ ] Is production monitoring in place to catch what testing couldn't (§1.4, §8.5, §3.10)?
- [ ] Is the rollback tested and ready (§4.8, AE §8.5 — a rollback never tested is a hope)?
- [ ] Is there a health check to know within minutes if the deploy is bad? (§5.6, FABLE §20)
- [ ] Do I know what confidence I actually have, and what the tests DIDN'T verify (the residual risk)? (§7.10, §1.4, [M20])

**11.5 — After production release**
- [ ] Is monitoring showing healthy real behavior — or anomalies/trends? (§8.5, DBG §8.10)
- [ ] Did any defect escape that the tests should have caught — a false negative to learn from? (§7.4, §1.5)
- [ ] For each escaped defect: a regression test added, and its CLASS considered? (§3.9, §7.4, DBG §5.6)
- [ ] Is confidence recalibrated to what production revealed — is the suite weaker than believed? (§7.10, [M20])
- [ ] For long-running/AI systems: are the slow-failure trends being watched over time? (§4.11, §6.11, §8.5, DBG §8.10)

# 12. Real Engineering Examples

Complete testing strategies, showing the engine running — every decision, tradeoff, failed test, regression, and confidence adjustment. Read as the strategy being designed.

**12.1 — A desktop application.**
- *Strategy (§3.1):* risk-based — the data layer (a wall [M6], §3.4 critical) gets exhaustive testing; the UI (furniture, reversible) gets lighter behavioral testing.
- *Architecture (§5):* unit tests for the logic (§5.1); integration tests for the data-layer seam (§5.2, §3.3); a few system tests for the core workflows (§5.3, §3.6 — open, edit, save, reopen).
- *Design (§4):* the data-format handling gets heavy edge (§4.2 — empty, huge, special characters §4.6 data integrity) and recovery testing (§4.8 — crash mid-write doesn't corrupt, AE §5.6, the crash-consistency the desktop app must have).
- *Failed test / regression:* a test reveals the save corrupts on special characters (§4.6, the CR §13.1 finding as a test) → debug (DBG) → regression test pins it (§3.9).
- *Confidence (§1.3):* justified by the data-layer being thoroughly tested (the wall) — the UI's lighter testing is an accepted, recorded residual risk (§7.10, reversible furniture).

**12.2 — A distributed system.**
- *Strategy (§3.1):* the inter-node communication (a wall §3.3, DBG §3.11) gets exhaustive testing; the failure modes (DBG §3.7 — partial failure, retry, reorder) are the highest risk.
- *Architecture (§5):* integration tests for the node contracts (§5.2, §3.3); system tests for multi-node scenarios (§5.3); **chaos testing** (§5.8 — kill nodes, sever networks in a production-like environment, verify graceful degradation AE §8.7 and recovery §4.8) — essential because failure is constant in distributed systems (DBG §3.11).
- *Design (§4):* concurrency tests with forced interleavings (§4.6, DBG §4.2 — make the race reliable); failure-injection (§4.3); idempotency verification (§4.8, DBG §13.2 — retries safe).
- *Simulation (§5.9):* the rare interaction failures forced via simulation (the network partition, the split-brain) that don't occur reliably in normal testing.
- *Confidence:* justified by chaos testing (§5.8 — resilience *rehearsed* [M12], not assumed FABLE §27) — plus production monitoring (§8.5) for the distributed-only defects that only appear at real scale (DBG §9.3, §1.4).

**12.3 — A reverse-engineering platform.**
- *Strategy:* the isolation (running untrusted targets safely, AE §13.5, CR §13.6) is the highest-risk wall — tested adversarially (§4.4 — a hostile target must not escape isolation §6, AE §8.3).
- *Design (§4):* heavy adversarial (§4.4 — malformed, hostile targets §4.3) and failure testing (a target crashing/attacking must be contained §4.8, AE §8.3); the analysis correctness tested against *known* targets (§5.10 golden — reverse-engineering a target whose behavior is known, verifying the analysis finds it, RE §7.1 predict-and-test).
- *The reverse-engineering-specific test (RE §7.1, CR §13.6):* the reverse-engineered *model* is tested against the *real* target (§3.10 reality contact [M2]) — the model predicts, the target confirms (RE §7.1) — because the platform's correctness depends on the model's accuracy (DBG §9.8).
- *Confidence:* justified by the isolation being adversarially tested (the safety wall) and the analysis validated against known targets (§5.10) — with the humility (§1.4, RE §9.4) that a target outside the tested set may behave unpredictably.

**12.4 — A multi-agent AI operating system (JarvisOS).**
- *Strategy (§6):* AI-native throughout — test distributions and guardrails (§6.1), not deterministic outputs.
- *The load-bearing tests:* the **injection canary** (§4.9, §6.9, BE §14.2 — a seeded injection that must fail to influence the actor, AE §9.6, run at every model/context change §8.4 [M12]); **model-replacement parity** (§6.9, OE §11.8 — the weekly test that the system survives the swap, keeping provider-agnosticism real AE §9.2); **memory tests** (§6.5 — store/index rebuild consistency, quarantine of untrusted memory, the "delete index, rebuild, search works" acceptance test BE §7.7); **orchestration tests** (§6.4 — coordination correctness, human gates hold OE §9.2).
- *Architecture (§5):* unit tests for the deterministic parts (the gateway routing §6.10, the file operations); integration for the seams (the gateway §6.10, MCP servers §6.3); system tests for the real workflows (§5.3, the morning-brief scenario §3.6); production monitoring (§8.5) for the long-running behaviors (§6.11 — memory rot, drift DBG §8.10).
- *Confidence:* justified by the guardrails being tested (§6.1, §6.7 — the containment holds even when the probabilistic behavior varies) — the system is trustworthy not because the models are perfect (they aren't) but because their failures are contained and caught (OE §8, AE §9.5).

**12.5 — A long-running autonomous workflow.**
- *Strategy (§6.7, §6.11):* highest rigor on containment (§6.1 — failures aren't caught in the moment DBG §8.9), and on the slow failures (§4.11 — the ones that only emerge over time).
- *Design (§4):* guardrail testing (§6.7 — gates hold AE §9.5, loop bounds OE §12.5, drift detection OE §12.6, escalation OE §8.5); **accelerated long-running tests** (§5.9, §4.11 — simulate months in minutes to surface accumulation failures DBG §8.10); blast-radius testing (§4.4, [M16] — the worst unsupervised behavior is bounded AE §8.4).
- *Production (§8.5, §3.10):* long-horizon monitoring (§4.11 — watch the trends that reveal slow degradation DBG §8.10, catch them before incidents).
- *Confidence:* justified by containment (§6.1 — I'd let it act unsupervised because its failures are gated and bounded, CR §9.8) and by the slow-failure monitoring (§8.5) — with explicit acknowledgment that autonomous long-running behavior can't be fully pre-tested (§1.4), so monitoring is load-bearing.

**12.6 — A memory system.**
- *Strategy (§6.5):* test the properties that prevent the catastrophic memory failures (DBG §8.6 — poisoning, corruption, rot).
- *Design:* **rebuild consistency** (§3.5 property, §6.5 — the acceptance test "delete the index, rebuild from the store, recall still works" BE §7.7, proving the store/index architecture AE §5.3); **quarantine** (§6.5, §6.9 — untrusted-derived memory can't become trusted without review, the injection-persistence test DBG §8.6); **staleness** (§6.5 — superseded memory isn't recalled as current RE §5.2); **consolidation over time** (§4.11, §5.9 accelerated — memory doesn't rot DBG §8.10).
- *Confidence:* justified by the rebuild-consistency test (the architecture's core promise AE §5.3 — memory survives index/technology replacement) and the quarantine test (the security-critical property §6.9) being verified, not assumed.

**12.7 — A Graphify knowledge system.**
- *Strategy (§6.6):* test correctness as a rebuildable index and correct placement above the baseline.
- *Design:* **rebuild from neutral store** (§6.6, §3.5 — the graph reconstructs correctly from the source of truth AE §5.4, §9.8, so it's a disposable index not a lock-in); **query correctness** (§6.6 — relationship/path/community queries against a golden dataset §5.10 of known-correct results); **baseline fallback** (§6.6, §4.3 — induce graph-unavailability, verify recall degrades to full-text AE §8.7, not to nothing); **provenance** (§6.6 — answers trace to sources AE §5.3).
- *Confidence:* justified by the fallback test (the system recalls even without the graph §8.7) and rebuild test (the graph is a safe enhancement AE §9.8, not a single point of failure) — Graphify tested as the enhancement-over-guaranteed-baseline it's architected to be.

**12.8 — An MCP server.**
- *Strategy (§6.3):* contract + ordinary-software + adversarial.
- *Design:* **contract tests** (§3.3, §5.2 — honors the MCP contract AE §4.3, both directions of the seam AE §9.10); **ordinary correctness** (§4 — the capability works, edges §4.2, failures §4.3); **adversarial** (§4.4, §6.9 of CR — malformed/hostile calls, since an agent's calls may be driven by untrusted content); **scope/security** (§6.9 of CR — the tool surface is scoped, trust boundaries enforced AE §8.2).
- *Confidence:* justified by contract tests (the seam holds, so the server is independently replaceable AE §6.4) and adversarial tests (the capability grant is safe CR §6.9) — an MCP server tested as both an integration and a security boundary.

**12.9 — An orchestration pipeline.**
- *Strategy (§6.4, §9.5 of CR):* test the coordination and the orchestrator's responsibilities (OE §1.4), not just the individual agents.
- *Design:* **coordination correctness** (§6.4 — through the inspectable shared state OE §7.4; conflict/duplication/ordering handled OE §7.6); **verification-architecture tests** (OE §8 — high-stakes output is independently verified §8.1, gates hold §8.6); **failure/recovery** (§4.8 — an agent fails, the pipeline recovers from checkpoint OE §11.4); **simulation** (§5.9 — force the rare coordination races OE §13.3).
- *Confidence:* justified by the coordination tests (the fleet produces coherent output OE §1.2) and the gate tests (irreversible actions can't escape human approval OE §9.2) — the orchestration trustworthy because its coordination and its containment are verified.

**12.10 — A production release.**
- *Strategy (§3.10, §5.6, §5.7):* the full pre-production suite plus staged production validation, because §1.4 (testing can't prove correctness) means production is the final, real test.
- *The release test sequence:* full regression (§5.5, §11.2 — nothing broke) → acceptance tests (§5.4, the done-whens pass BE §7.7) → deploy to canary (§5.7 — a production fraction) → smoke tests on the canary (§5.6 — basically works) → monitor the canary (§8.5 — healthy?) → roll forward if healthy, back if not (§4.8, AE §8.5).
- *The confidence discipline (§7.10, §11.4, [M20]):* before deploying, state what confidence I have *and what the tests didn't verify* (the residual risk §1.4) — so the deploy is made with calibrated, not false, confidence (§9.9). The canary (§5.7) bounds the cost of the residual risk [M8].
- *After (§11.5, §7.10):* monitor (§8.5); any escaped defect is a false negative (§7.4) that recalibrates confidence (§7.10 — the suite was weaker than believed) and gets a regression test (§3.9) and a class-consideration (DBG §5.6). The release's real lesson is what production revealed that testing didn't (§1.5, §1.4) — fed back to make the next release's suite stronger.
