This document assumes and does not repeat: the orchestration *view* of context (OE §5 — context as architectural concern, per-agent isolation, externalize-early, the attack surface; OE §6 — knowledge routing; OE §11 — long-running continuity), memory's treatment of *working memory* (ME §1.4) and *restoration* (ME §5.9), the *knowledge/information* distinction (ME §1.3), the durable/disposable line (ME §1.6/§1.7), the cold-brief *delegation* discipline (FABLE §29, OE §9), and context as *security attack surface* (AE §9.4, SE §7.2). OE §5 established context as an architectural concern *within an orchestration*; ME distinguished durable knowledge from the working set. This engine is the full discipline of *the working set itself* — the most expensive, most bounded, most decision-determining resource an engineering mind has.

**Where this sits and how it differs from MEMORY.** Memory (ME) is *durable knowledge* — what the system knows, persisted, surviving sessions and models. Context is *the working set* — the bounded subset of information a mind holds *right now* to do the current work. Memory is the library; context is the desk. The relationship (ME §1.4, §5.9): context is *assembled from* memory (and from the task, the inputs, the environment) for a task, and *externalized back to* memory when it matters (ME §2.1). The two engines are complementary: ME governs what survives; this engine governs what's *active*, why active context is the scarcest resource, and how to construct/compress/preserve/restore/exchange it under a hard bound. Where ME asks "what should the system remember?", this engine asks "what should the mind hold *right now*, and how does it manage the holding when the holding is small, expensive, and determinative of every decision made from it?"

**The one-sentence version.** Context is the bounded working set of information a mind reasons from, and it is the most expensive engineering resource because every decision is only as good as the context it was made from — so context engineering is the disciplined construction of the *minimal sufficient* working set, its compression when it fills, and its faithful reconstruction across the boundaries (sessions, models, agents) that continually destroy it [M2, OE §5].

# 1. Context Philosophy

**1.1 — What context actually is.** Context is *the information a mind holds active while reasoning* — the working set loaded into the window of attention from which every decision, inference, and action is made. It is not what the system *knows* (that's memory, ME §1.1) but what it's *currently thinking with* — the task, the relevant knowledge, the inputs, the state, the constraints, all present at once in the mind doing the work. Context is *computational*, not archival (§1.7): it exists to be reasoned *from*, and it exists only during the reasoning. For an AI, context is literally the window — the bounded set of tokens the model attends to — and its management is not housekeeping but *core engineering*, because the context *is the input to every decision* (§1.8).

**1.2 — Why context exists.** Because reasoning requires holding the relevant information *together, at once* — a decision needs its goal, its constraints, its inputs, and its relevant knowledge simultaneously present to be made well (§4). Context exists to *assemble* the scattered — knowledge from memory (ME), inputs from the task, state from the work, constraints from the architecture — into one working set a mind can reason over as a whole (§4.1). Without context, information is scattered and un-reasoned-over (a fact in memory ME that isn't in context isn't influencing the current decision); with it, the relevant information is *present and integrated* (§4 — assembled deliberately for the task). Context is the *staging* that makes reasoning possible — the assembly of the right information, together, for the work at hand.

**1.3 — Context vs memory.** The foundational distinction (ME §1.4). *Memory* is durable, persistent, potentially vast — everything the system knows, held across time (ME §1.1). *Context* is transient, bounded, active — the small working subset held right now (§1.1). Memory is *storage*; context is *use*. The relationship: context is *assembled from memory* (ME §5.9 — retrieval into the working set) for a task and *externalized to memory* (ME §2.1) when it matters; memory outlives the context (a session's context ends; what it externalized to memory persists ME §1.5). The discipline: don't confuse them (§10 — treating context as storage §1.7 loses what should have been externalized to memory ME §2.1; treating memory as always-in-context floods the bounded window §9.1). Context is the desk you work at; memory is the library you fetch from and file back to.

**1.4 — Context vs knowledge.** Knowledge (ME §1.3) is *digested, trusted, actionable* understanding — a property of information regardless of where it is. Context is *what's currently active* — a location/state, not a quality. Knowledge can be *in* context (loaded into the working set §4) or *out* of it (in memory ME, not currently active). The distinction matters (§4): context construction is *selecting which knowledge* (and which task-inputs, state, constraints) to make active (§4.1) — so context is the *active projection* of the system's total knowledge, chosen for the task. Good context construction (§4) puts the *right* knowledge in the working set; the wrong knowledge in context (irrelevant, stale ME §7.10) degrades reasoning (§9) as surely as missing knowledge does.

**1.5 — Working context.** The context of the *immediate task* — the tightest, most active working set (the specific thing being reasoned about right now). Working context is maximally transient (§1.7 — it exists for the task and shifts as the task shifts) and maximally relevant (§4 — assembled precisely for the current work). It's the innermost layer (§3.1) — what the mind is most directly attending to.

**1.6 — Persistent context.** Context that *should* survive beyond the immediate moment — but "persistent context" is a careful phrase, because context is inherently transient (§1.7). What "persists" is context that has been *externalized to memory* (ME §2.1, §9.3) and can be *restored* (§6, ME §5.9) — so "persistent context" is really *memory that reconstructs context* (§6.1). The discipline (§1.7, ME §1.4): nothing important is *left* in context to persist (context is transient, it dies at the boundary §2.7) — what must persist is externalized to durable memory (ME §2.1) and restored into fresh context when needed (§6). "Persistent context" is a restoration capability (§6), not a persistent working set.

**1.7 — Context as temporary computation.** The essential nature (§1.1): context is *temporary computation*, not storage. It's assembled (§4), reasoned over (§1.2), and *discarded* (§2.8) — the working set for a task, gone when the task ends (its important products externalized to memory ME §2.1 first). Treating context as storage (§10 — leaving important things in it expecting them to persist) is the cardinal error (§9 — because context *doesn't* persist; it's destroyed at every boundary §2.7 — session end, compaction §5, model swap §8, delegation §8.4). The discipline (OE §5.3): context is a *cache over memory* (ME §1.7-like) — a transient working computation, rebuilt (§6) from the durable source (memory ME §1.6) whenever needed, never trusted to persist.

**1.8 — Why context is the most expensive engineering resource.** The claim that justifies the whole engine. Context is the most expensive resource because: (a) *every decision is made from it* (§1.1 — the context is the input to all reasoning, so context quality bounds decision quality — a decision from bad context is a bad decision however good the reasoning DE, [M2]); (b) it's *hard-bounded* (§7 — the window is finite, so context is always a scarce, allocated resource §7.9, unlike memory which can grow ME); (c) it *degrades with use* (§9.1 — a fuller context reasons worse, attention diluted AE §9.4, so every token spent has a cost beyond itself); and (d) it's *continually destroyed* (§2.7 — every boundary destroys it, so it must be continually reconstructed §6 at real cost). The synthesis: context is scarce (bounded §7), determinative (every decision depends on it §1.1), degrading (§9.1), and perishable (§2.7) — the confluence that makes it the resource whose management most determines engineering quality, and the one whose mismanagement (§9) most silently degrades it. Managing context well is not optimization; it's the precondition for reasoning well at all.

# 2. Context Lifecycle

How the working set moves from assembly to discard. OE §5 covered this within an orchestration; this is the full lifecycle discipline. The governing principle: **context is assembled minimally for the task, grows as work proceeds, is compressed when it fills, externalized before it's destroyed, and reconstructed when needed — because context is temporary computation (§1.7) that every boundary destroys (§2.7), so its lifecycle is a continual cycle of construct-use-externalize-reconstruct, never a persistent hold.**

**2.1 — How context is created (assembly).** Context is *assembled* for a task (§4, OE §5.1) — deliberately constructed from four sources: the *task* (the goal, the framing FABLE §1, what's being done), *knowledge* (the relevant subset retrieved from memory ME §5, §5.9), *inputs* (the actual data to work on), and *state* (the current state of the work, restored §6 if resuming). Assembly is *deliberate*, not accumulated (§4.9, OE §5.1 — the mind constructs the working set for the task, rather than letting it accrete). The discipline (§4): assemble the *minimal sufficient* context (§4.9 — enough to reason well, with headroom §7.9 [M17], no more §9.1) — because assembly quality determines reasoning quality (§1.8) and assembly excess degrades it (§9.1).

**2.2 — How it grows.** As work proceeds, context grows — new information enters (findings from research RE, state from the work, results from actions, new inputs). Growth is natural and necessary (the work produces information the reasoning needs) but *bounded* (§7 — the window is finite, so unchecked growth hits the limit §9.1) and *degrading* (§9.1 — a fuller context reasons worse). The discipline (§5, §7): growth is *managed* — new information that matters enters (§4.4 — relevant, not noise §4.2), and as context fills, it's compressed (§5) and pruned (§7.2 — low-value context leaves) to stay within the effective budget (§7.9) and below the degradation threshold (§9.1). Growth without management is the road to overflow (§9.1).

**2.3 — How it is prioritized.** As context grows (§2.2) toward its bound (§7), what it holds is prioritized (§7) — the essential kept (§7.1 — the goal, the constraints, the active state), the peripheral dropped (§7.2). Prioritization is continuous (§7.9 — the context budget is continually allocated to the highest-value information), and it's what makes compression (§5) and pruning (§7.2) *keep the right things*. The discipline (§7): prioritize by value-to-the-current-reasoning (§7.3 — importance, dependency §7.4, constraint §7.5, freshness §7.6, risk §7.7, operator-intent §7.8), so when context must shrink (§5, §7.2), the essential survives and the peripheral goes.

**2.4 — How it is compressed.** When context fills (§2.2, approaching the bound §7), it's compressed (§5) — summarized, distilled, the verbose replaced with the essential (§5.1 progressive summarization). Compression trades detail for space (§5.4 lossy) — keeping the *decisions, constraints, state, and knowledge* (§5.5–5.8) that the ongoing work needs, discarding the *derivation, the transcript, the detail* that's recomputable or irrelevant (§5.4). The discipline (§5): compress *losslessly where possible* (§5.3 — reference rather than include §10 of decisions) and *lossily by keeping the products not the process* (§5.4 — the decision not the deliberation, the finding not the search RE §Stage 8), so compressed context stays *sufficient* (§4.9) for the ongoing work at a fraction of the tokens.

**2.5 — How it is transferred.** Context moves between minds — to another agent (§8.4 handoff, OE §9), to a tool (§8.7), across a model swap (§8.10). Transfer is *reconstruction at the destination* (§6, §8.4) — the source externalizes what the destination needs (ME §2.1), and the destination assembles its context from that (§2.1, §6). Transfer is a *cold-brief* (FABLE §29, OE §9 — the destination has none of the source's context, so it must be given everything it needs, self-contained [M18]). The discipline (§8.4, FABLE §29): transfer by externalizing to durable/shared form (ME §3.8, OE §7.4 — the handoff note, the shared state) that the destination reconstructs from — never assume the destination shares the source's context (§8.4 — it doesn't; every transfer is a cold start).

**2.6 — How it is restored.** Context lost (at a boundary §2.7 — session end, compaction §5, resumption) is *reconstructed* (§6, ME §5.9) from durable memory (ME §1.6). Restoration reassembles the working set (§2.1) equivalent to what's needed for the resumed work (§6.1 — equivalent for the task, not identical to the lost context OE §5.5). The discipline (§6): restore the *relevant* context for the current work (§6.7 partial — not everything, which floods §9.1 and wastes §7.9), from the externalized durable record (ME §2.1 — which is why externalization §2.1 before the boundary §2.7 is essential — you can only restore what was externalized).

**2.7 — How it expires.** Context is *destroyed at every boundary* — session end (the conversation ends, the context is gone), compaction (§5 — the context is compressed, detail lost), model swap (§8.10 — the new model has no prior context), delegation (§8.4 — the sub-agent has its own fresh context), and simply time/attention shifting to another task. Expiry is *constant and inevitable* (§1.7 — context is temporary computation, it always ends). The discipline (§2.1, §1.7): expiry is *planned for* — nothing important is left in context to be destroyed (externalize before the boundary ME §2.1, OE §5.3), because context *will* expire, and what wasn't externalized is *lost* (§9 — the amnesia of un-externalized context). Treat every boundary as imminent (OE §5.3 — the session can end at any instant), so externalization is continuous (§2.1), not deferred to a planned end that may not come.

**2.8 — How it is discarded.** Context deliberately released — a task done (its working context §1.5 discarded, its products externalized ME §2.1), a line of reasoning abandoned (its context dropped), a fresh start chosen (§10 restore-vs-restart, FABLE §6 — a degraded context §9.4 deliberately discarded and rebuilt clean §6). Discard is *legitimate and often wise* (§10 — a confused/degraded context §9.4 is better discarded and reconstructed §6 than pushed through). The discipline (FABLE §6, §10): discard context deliberately when it's *done* (task complete, products externalized ME §2.1) or *degraded* (§9.4 — accumulated confusion, contradictions §9.8, stale state §9.7 — better to restart clean from good notes §6 than continue in fog). Discarding a degraded context and reconstructing (§6) is a reset that often beats continuing (§10, FABLE §6 — the clean restart from good externalized notes).

# 3. Context Architecture

The kinds and scopes of context and how they layer. OE §5.2 covered partitioning within an orchestration; this is the context-type architecture. The governing principle: **context is layered by scope and permanence — working/session/project/global, and execution/decision/reference by function — so the right information is active at the right layer, and each layer's context is constructed, bounded, and destroyed appropriately for its scope.**

**3.1 — Working context.** The innermost, most active layer (§1.5) — the immediate task's working set. Most transient (§2.7 — shifts with the task), most relevant (§4 — assembled precisely for now), smallest (§7 — the tightest budget, holding just the current work). The layer the mind is most directly reasoning from (§1.1).

**3.2 — Session context.** The context of the current session/conversation — what's been established, decided, done in this working period (OE §5, ME §3.2). Broader than working context (§3.1 — it holds the session's accumulated state, not just the immediate task) and semi-persistent within the session (§2.7 — it survives across the session's tasks but is destroyed at session end). The discipline (§2.1, ME §3.2): session context is continuously externalized (OE §5.3 — so its important content survives the session-end boundary §2.7 into memory ME §3.2, restorable §6 next session §9.3).

**3.3 — Project context.** The context relevant to the current project (ME §3.3, OE §11) — its goals, architecture, decisions, state, constraints. Project context is *large* (a project's full relevant knowledge exceeds any window §7) so it's *not all in context at once* — it lives in memory (ME §3.3) and the *relevant subset* is assembled into working/session context (§3.1, §3.2) as the current work needs (§6.7 partial, ME §5.7 layered). The discipline (ME §5.7, OE §5.7): project context is layered by need — the slow-changing essentials (goals, architecture, key constraints §7.5) more readily in context, the vast detail retrieved (§6) as specific work requires.

**3.4 — Global context.** The context that applies across all work (ME §3.5) — the operator's standing preferences (ME §3.6), the system's standing constraints (the Constitution, the laws), the operating methodology (this extraction set). Global context is *always relevant* (ME §6.5 — retrieved into every working context §4.1) but *compact* (§7.1 — the essential globals, not everything, or it floods §9.1). The discipline (§7.1, ME §3.5): the essential global context (the load-bearing preferences/constraints §7.5) is always present (§7.1 — it never leaves, because it always applies), kept compact (§5 — distilled to essentials, the full detail in memory ME §3.5).

**3.5 — Agent context.** The context an agent holds (OE §5.2, ME §3.7) — assembled for its task (OE §5.1), isolated from other agents (§3.7, OE §5.2). Agent context is working context (§3.1) scoped to the agent's delegated task (§8.4 — constructed by the orchestrator OE §5.1 from the cold-brief FABLE §29). The discipline (OE §5.2, §3.7): per-agent isolation — each agent's context is separately constructed (§8.4) and isolated (§3.7 — so one agent's context confusion §9 doesn't contaminate another OE §5.2), coordinating through shared context (§3.6), not shared working windows.

**3.6 — Shared context.** Context multiple agents share — which, for a well-designed fleet (OE §7.4, ME §3.8), is *durable shared memory* (ME §3.8) that each agent's context is assembled from (§2.1), not a shared working window. "Shared context" is really *shared memory that constructs each agent's context* (§3.7 — the agents coordinate through the shared durable state OE §7.4, each reconstructing its own working context §6 from it). The discipline (OE §7.4, §3.7): agents share *durable context* (ME §3.8 — the inspectable shared state), not *working context* (§3.1 — each agent has its own, isolated §3.7), so agents are independently replaceable (OE §6.4) and their coordination is through the durable shared record (§8.5).

**3.7 — Private context.** Context isolated to one mind/agent (§3.5, OE §5.2) — its working set, not shared. Private context is the norm for working context (§3.1 — each mind's working set is its own) and a security boundary (SE §7 — one context's sensitive content isolated OE §5.2, so a compromise SE §2.6 is contained). The discipline (OE §5.2): private working context is isolated (so confusion/compromise doesn't spread §3.5, SE §3.2), and what *should* be shared is externalized to shared memory (§3.6, ME §3.8), not held privately where others can't reach it.

**3.8 — Execution context.** The context for *doing* — the state, inputs, and immediate information an action or execution needs (BE — building, DBG — debugging, the doing). Execution context is tight and current (§3.1 — the immediate execution's working set) and *volatile* (it changes rapidly as execution proceeds §2.2). The discipline: execution context holds the *current execution state* (what's needed to do the next step BE §3.7), externalized at checkpoints (§5.9, ME §9.4 — so an execution interrupted §2.7 resumes §6).

**3.9 — Decision context.** The context for *deciding* (DE) — the goal, the options, the constraints, the relevant knowledge a decision needs (DE §2 — the decision pipeline's inputs). Decision context must hold the *deciding constraint* (DE §2 Stage 2), the *real alternatives* (DE §3), and the relevant *tradeoff information* (DE §4) — all present at once (§1.2) for the decision to be made well (§1.8 — a decision from incomplete context is a bad decision DE). The discipline (§4): decision context is assembled to hold *everything the decision turns on* (DE §2 — the constraint, the options, the stakes), because a decision is only as good as the context it's made from (§1.8, DE §1.2).

**3.10 — Reference context.** Context held for *reference* — information available to consult but not actively reasoned over (the docs, the specs, the codebase a task might need to reference RE §6). Reference context is *large and mostly latent* (§7 — you can't hold a whole codebase in working context §3.1) so it lives in memory/retrieval (ME, §6) and is *pulled into working context as specifically needed* (§6.7 partial, §4.4 — the specific reference the current step needs, retrieved when needed, not held always). The discipline (§4.4, §6): reference context is *retrieved on demand* (§6 — the specific thing when needed) not *held in bulk* (§9.1 — holding the whole reference floods the window), which is why retrieval (§6, ME §5) matters — it lets vast reference (§3.10) stay in memory and enter working context (§3.1) precisely when the reasoning needs it.

# 4. Context Construction

Deciding what belongs in the working set — the highest-leverage context skill, because construction quality determines reasoning quality (§1.8). OE §5.1 covered assembly within an orchestration; this is the full construction discipline. The governing principle: **construct the minimal sufficient context — everything the reasoning needs, nothing it doesn't — because missing context starves the reasoning (§9.2, causing wrong decisions from incomplete information) while excess context degrades it (§9.1, diluting attention AE §9.4 and wasting the scarce budget §7.9), and the sufficient minimum is the sweet spot that maximizes reasoning quality per token.**

**4.1 — How I decide what belongs in context.** By working backward from the *reasoning the context must support* (§1.2 — what decision/action/inference is this context for?) and including exactly what that reasoning needs: the *goal* (§4.6), the *constraints* (§4.5), the relevant *knowledge* (ME §5 — retrieved for this reasoning), the *inputs* (the data), the relevant *state* (§4.7), and the relevant *history* (§4.8) — each included because the reasoning needs it (§4.3 relevance), each excluded if it doesn't (§4.2 noise). The discipline (§4.9): construct for *this* reasoning, minimally-sufficiently — the context is a deliberate assembly (§2.1, OE §5.1) of what the work needs, not a dump of what's available (§9.1) or a guess at what might help (§4.2 — speculative inclusion is noise).

**4.2 — Signal vs noise.** The core construction judgment (§4.9): *signal* is information the reasoning needs (§4.3 relevant); *noise* is everything else in the context (irrelevant, redundant, stale ME §7.10, speculative). Every token of noise costs (§1.8, §9.1 — it dilutes attention AE §9.4 and consumes the budget §7.9), and enough noise buries the signal (§9.1 — the reasoning can't find what it needs in the clutter). The discipline (§4.9, §7): maximize signal, minimize noise — include what the reasoning needs (§4.3), ruthlessly exclude what it doesn't (a whole file when a section suffices FABLE §6, raw logs when three lines matter, speculative "might be useful" information §4.1). Signal-to-noise is the quality metric of constructed context (§9.1 — a low-signal context reasons poorly however much it holds).

**4.3 — Relevance scoring.** Judging whether information belongs (§4.2 signal vs noise) by its *relevance to the current reasoning* (§4.1). Relevance is *to the task at hand*, not in general (information relevant to the project ME §3.3 but not the current task is noise §4.2 for this context — it belongs in memory ME, retrievable §6 when its task comes). The discipline (§4.9): score relevance by "does the current reasoning *need* this?" — need, not "relate to" (much relates; little is needed §4.2), and not "might help" (§4.1 — speculative inclusion is noise). High relevance → include; low → exclude (leave in memory ME, retrieve §6 if the reasoning turns to need it).

**4.4 — Dependency inclusion.** Including what the reasoning *depends on* — the information the current decision/action can't be made correctly without (§3.9 — the decision's deciding constraint DE §2, the inputs it operates on, the state it builds on). Dependency inclusion is non-negotiable (§9.2 — omitting a dependency starves the reasoning, producing a decision made without something it needed, a wrong decision DE from incomplete context §1.8). The discipline (§4.1): trace the reasoning's dependencies (what must be present for this to be reasoned correctly) and include *all* of them (§9.2 — a missing dependency is context starvation), while excluding non-dependencies (§4.2 — what the reasoning doesn't depend on is noise).

**4.5 — Constraint inclusion.** Including the *constraints* the reasoning must respect (§3.9, DE §2 — the deciding constraint; the architecture's invariants AE §2.6; the security boundaries SE; the operator's standing constraints ME §3.6). Constraints are high-priority context (§7.5 — they must be present, or the reasoning violates them unknowingly §9.6 — a decision that breaks a constraint the context didn't include). The discipline (§7.5, §9.6): the *load-bearing* constraints for the current reasoning are always included (§7.1, §7.5 — the invariants AE §2.6, the security rules SE, the operator constraints ME §3.6 that this reasoning could violate), because a lost constraint (§9.6) is a reasoning that violates it silently.

**4.6 — Goal inclusion.** Including the *goal* the reasoning serves (§3.9, FABLE §1 — the done-state, the intent). Goal inclusion keeps the reasoning *aimed* (§9.3 drift — reasoning that loses its goal drifts to solving something adjacent OE §12.6). The discipline (§7.1, FABLE §1): the goal is always present (§7.1 — it never leaves, because all reasoning serves it), stated clearly (FABLE §1 — the framed problem, the done-state PE Stage 1), so the reasoning stays aimed at what it's for (§9.3 — and is checked against the goal FABLE §1 step 7, not against a drifted proxy).

**4.7 — State inclusion.** Including the relevant *current state* — where the work is now (what's been done, what's the current situation, what's the state of the thing being worked on). State inclusion lets the reasoning build on the actual current situation (§9.7 — stale state in context reasons from a situation that's no longer true DBG §3.2-like). The discipline (§9.7): include the *current* state (freshness §7.6 — the state as it actually is now, not as it was), and *restore* accurate state when resuming (§6, §9.7 — a resumed context with stale state reasons wrongly, so state is refreshed at restoration §6).

**4.8 — History inclusion.** Including the relevant *history* — how the work/situation got here, when the history informs the current reasoning ([M9] Chesterton's Fence — why was this done, before changing it; the path that led here, when it matters). History inclusion is *selective* (§4.2 — most history is noise for the current reasoning; the *relevant* history is signal). The discipline (§4.3, §5.4): include the history the current reasoning *needs* (the why behind a thing being changed [M9], the decisions that constrain now DE) — as *distilled* history (§5.4 — the relevant conclusions/decisions, not the full transcript, which is noise §4.2 and bulk §9.1), retrievable in full from memory (ME §6.7 — the history preserved) if the reasoning turns to need more.

**4.9 — Minimal sufficient context.** The construction target (§1.8, the whole engine's aim): the *smallest* context that is *sufficient* for the reasoning (§4.1) — everything needed (§4.4 dependencies, §4.5 constraints, §4.6 goal, §4.7 state, relevant knowledge ME §5), nothing not (§4.2 noise excluded), with *headroom* (§7.9 [M17] — room to grow §2.2 and reason without hitting the bound §9.1). Minimal-sufficient is the sweet spot (§1.8 — maximizing reasoning quality per token): below it, starvation (§9.2 — missing what's needed); above it, degradation (§9.1 — noise diluting attention). The discipline (§4.1–4.8): construct for minimal-sufficiency — assemble what the reasoning needs (§4.4–4.8), ruthlessly exclude what it doesn't (§4.2), leave headroom (§7.9), and *trust retrieval* (§6, ME §5 — what's not in context is in memory, retrievable if the reasoning turns to need it, so you needn't hold everything §3.10). Minimal sufficient context is the discipline that makes reasoning both *well-informed* (sufficient) and *sharp* (minimal, un-diluted §9.1) — the two properties that together make reasoning good (§1.8).

# 5. Context Compression

Fitting more reasoning into the bounded window by trading detail for space — the discipline that lets long work proceed within a finite context (§7). OE §5.4 covered compression within an orchestration; this is the full compression discipline. The governing principle: **compress by keeping the products and discarding the process — the decisions not the deliberation, the findings not the search, the state not the transcript — because the products are what the ongoing reasoning needs (§4) while the process is recomputable or irrelevant (§4.2 noise), so compression that keeps products loses nothing the work needs while reclaiming the space the process consumed.**

**5.1 — Progressive summarization.** Compressing context incrementally as it grows (§2.2) — summarizing older/completed portions while keeping recent/active portions detailed. Progressive summarization keeps the *active* reasoning detailed (§3.1 — the current work at full fidelity) while compressing the *settled* (the completed sub-tasks, the concluded reasoning, into their products §5.4). The discipline (OE §5.4): summarize *progressively* — as a portion of the work settles (a sub-task done, a decision made), compress it to its product (§5.4 — the decision §5.6, the result), keeping the active work uncompressed, so context stays within budget (§7.9) while the current reasoning stays sharp (§9.1).

**5.2 — Hierarchical compression.** Compressing in *layers* of detail — the essentials at top (always present §7.1), the detail beneath (compressed, retrievable §6). Hierarchical compression mirrors the layered architecture (§3.3, ME §5.5) — the goal/constraints/key-decisions always in context (§7.1), the supporting detail compressed to references (§5.3, §10) or summaries (§5.4), retrievable (§6) when needed. The discipline: compress hierarchically — keep the *structure and essentials* (the goal §4.6, constraints §4.5, key decisions §5.6) at full presence, compress the *detail* to summaries/references, so the context holds the shape of the whole work (§4.9 sufficient) at a fraction of the tokens.

**5.3 — Lossless compression.** Compression that loses *no* information — primarily *referencing* rather than *including* (§10 summarize-vs-reference). Instead of holding a document/decision/finding in full in context, hold a *reference* to it in memory (ME) and retrieve (§6) the full content when the reasoning needs it. Lossless compression (§10): the information isn't lost (it's in memory ME, retrievable §6), it's just not *held in context* (freeing the window §7.9). The discipline (§10, §4.4): reference what's in memory (ME — retrievable §6) rather than including it in context, when the reasoning doesn't need it *constantly present* (§3.10 reference context — held latent, pulled in when needed). Lossless-by-reference is the preferred compression (§10 — nothing lost, space reclaimed) when retrieval (§6) is reliable.

**5.4 — Lossy compression.** Compression that *discards* detail — keeping the essential, losing the rest (§5.1 summarization). Lossy compression is *deliberate loss* (§2.4 — the detail traded for space), and the discipline is *what* to lose: keep the *products* (decisions §5.6, findings RE §Stage 8, state §5.7, constraints §5.8), lose the *process* (the deliberation, the transcript, the search, the derivation — recomputable or irrelevant §4.2). The discipline (§2.4): lossy-compress by keeping products, discarding process — the decision (§5.6) not the deliberation, the finding (RE) not the search, the current state (§5.7) not the history of reaching it (§4.8 — the relevant conclusions, not the full path). Lossy compression done well loses *nothing the ongoing work needs* (§4.9 — the products are what it needs) while reclaiming the space the process consumed.

**5.5 — State extraction.** Extracting the *current state* from a verbose context into a compact representation (§5.4 — the state §5.7 as a product, the transcript of reaching it discarded). State extraction is what makes a long execution (§3.8) compressible — the accumulated work's *current state* (where it is now) extracted compactly, the step-by-step history compressed. The discipline (§5.7): extract the *current* state (what's needed to continue §3.8, §6 — the resumable state ME §9.4 checkpoint), so a long/interrupted execution resumes from the extracted state (§6) rather than the full history.

**5.6 — Decision extraction.** Extracting *decisions and their reasons* from the deliberation that produced them (§5.4 — the decision as product, the deliberation as process). Decision extraction keeps *what was decided and why* (DE §2 Stage 8 — the decision, its reason, recorded AE §6.2) while compressing the *deliberation* (the options weighed, the analysis — recomputable, and preserved in memory ME if needed). The discipline (§5.4, DE §2 Stage 8): extract decisions to their essence (the decision + the why AE §6.2, [M9] — so the reasoning that follows respects the decision and understands it), discarding the deliberation (§4.2 — noise for the ongoing work, though externalized to memory ME §6.7 if historically valuable).

**5.7 — Constraint extraction.** Extracting the *constraints* that must persist in context (§4.5, §7.5) — pulling the load-bearing constraints (invariants AE §2.6, security rules SE, operator constraints ME §3.6) into a compact, always-present form (§7.1). Constraint extraction ensures constraints *survive compression* (§9.6 — a constraint lost in compression is a constraint violated silently). The discipline (§7.5, §9.6): extract and *preserve* the load-bearing constraints across every compression (§7.1 — they never compress away, because losing them §9.6 means the ongoing reasoning violates them unknowingly).

**5.8 — Knowledge distillation.** Distilling retrieved knowledge (ME §5) to its essence for context — the finding not the full source (RE §Stage 8), the principle not the full document, the relevant fact not the whole reference (§3.10). Knowledge distillation is compression at the point of retrieval (§6, ME §5 — retrieve the knowledge, distill it to what the reasoning needs §4.9, include the distillation). The discipline (§4.9, §5.4): distill retrieved knowledge to the *relevant essence* (what this reasoning needs from it), holding the distillation in context and the full source in memory (ME — retrievable §6 if more is needed) — so context holds distilled knowledge (sufficient §4.9, compact §9.1) rather than full sources (bulky §9.1).

**5.9 — Compression checkpoints.** Compressing at *stable points* (ME §9.4 — a checkpoint, a milestone PE §5.4, before a context boundary §2.7). Compression checkpoints are where progressive summarization (§5.1) happens deliberately — at a stable point, the settled work is compressed (§5.4) to its products, a clean compact context established (§6 — restorable, a known-good state ME §9.4). The discipline (ME §9.4, §5.1): compress at checkpoints — stable points where a coherent product-state can be extracted (§5.5–5.8), producing a clean compressed context (and a checkpoint ME §9.4 externalized to memory ME §2.1, restorable §6) — so compression is at coherent boundaries, not mid-reasoning (which loses active state §9).

**5.10 — Token economics.** The economic view of compression (§1.8 — context as the expensive resource). Every token in context costs (§1.8 — attention dilution §9.1, budget consumption §7.9), so compression is *economics* — spending the token budget (§7.9) on the highest-value information (§7.3), compressing the rest to reclaim budget for what matters. The discipline (§7.9, §5.4): treat the context budget as scarce capital (§1.8) — spend it on the products the reasoning needs (§5.4, §4.9 minimal-sufficient), compress the process to reclaim it (§5.4), and maintain headroom (§7.9 [M17] — never spend to the limit §9.1, which degrades reasoning). Token economics is the quantitative discipline behind minimal-sufficient context (§4.9) — the budget is finite, so it's allocated (§7.9) to maximize reasoning value per token (§1.8).

# 6. Context Retrieval

Reconstructing context from memory when it's been lost or is needed — the mechanism that makes context *recoverable* across the boundaries that destroy it (§2.7). ME §5 (memory retrieval) and §5.9 (restoration) build the substrate; this is the context-reconstruction discipline. The governing principle: **reconstruct the context the current work needs from durable memory — equivalent for the task, not identical to what was lost — because context is destroyed at every boundary (§2.7) and reconstruction is how work continues across the destruction, so reliable reconstruction is what makes context's transience (§1.7) survivable.**

**6.1 — How context is reconstructed.** By *assembling* fresh context (§2.1) from durable memory (ME §1.6) for the current work — the same construction (§4) as initial assembly, but sourcing from memory (ME §5) what a prior context held. Reconstruction produces context *equivalent for the task* (OE §5.5 — not identical to the lost context, which is gone §2.7 and needn't be reproduced exactly — equivalent for what the current work needs §4.9). The discipline (§4, ME §5.9): reconstruct by constructing (§4 — minimal sufficient §4.9 for the current work) from memory (ME §5 — retrieving the relevant knowledge, decisions, state), so the reconstructed context is *sufficient for the resumed work*, assembled fresh (§4) rather than a stale replay of what was lost.

**6.2 — Memory-driven reconstruction.** The primary reconstruction source (ME) — the durable memory (ME §1.6) holds what was externalized (ME §2.1), and reconstruction retrieves from it (ME §5). Memory-driven reconstruction is why externalization matters (§2.1, ME §2.1 — you can only reconstruct what was externalized; un-externalized context is lost §2.7, §9). The discipline (§2.1, ME §2.1): reconstruction is *bounded by externalization* — what was externalized to memory (ME §2.1) is reconstructable (§6.1); what wasn't is gone (§9 — the amnesia of un-externalized context), so continuous externalization (§2.1) is the precondition for reliable reconstruction (§6).

**6.3 — Graph retrieval (for reconstruction).** Reconstructing context using the knowledge graph (ME §3.11, AE §9.8) — retrieving related context by relationship (ME §5.2 — "what's connected to this work," "what decisions/constraints relate"). Graph retrieval for reconstruction is powerful for restoring the *structural* context (the dependencies AE, the related decisions AE §6.2, the constraints §4.5 that connect to the current work) — the relationships that a flat retrieval (§6.4) misses. The discipline (ME §5.2): use graph retrieval to reconstruct the *connected* context (what relates to the current work — its dependencies, constraints, related decisions), so the reconstructed context includes not just the direct knowledge but its structural context (ME §8.2 — the model understanding what connects to its work).

**6.4 — Semantic retrieval (for reconstruction).** Reconstructing context by meaning-similarity (ME §5.1) — retrieving knowledge *relevant by meaning* to the current work. Semantic retrieval for reconstruction surfaces the relevant-by-meaning context (the past work that resembles this, the knowledge that bears on this meaning ME §5.1). The discipline (ME §5.1): use semantic retrieval to reconstruct the *meaningfully-relevant* context (§4.3 — what relates to the current work's meaning), with the caveat (ME §5.1 — similarity isn't sufficiency; combine with graph §6.3 and reference §6.5 for complete reconstruction §6.7).

**6.5 — Reference retrieval.** Reconstructing context by following *references* (§5.3, §10 — the references held in place of included content). Reference retrieval pulls the referenced content (the document, the decision, the source ME) into context when the reconstructed reasoning needs it (§3.10 — the reference context pulled in on demand §4.4). The discipline (§5.3, §3.10): reconstruct by resolving references on demand — the compressed context (§5.3 — referencing not including) reconstructs its full detail by retrieving the referenced content (§6) when the reasoning turns to need it, so reference-compression (§5.3) is reversible at need.

**6.6 — Project restoration.** Reconstructing a project's context (ME §3.3, OE §11) — for a new session (§9.3), a resumed project. Project restoration reconstructs the working context for the project's current state (the goals, the current phase, the recent decisions, the next actions PE §7.1) from the project memory (ME §3.3, §5.9). The discipline (ME §5.7, OE §5.5): restore the project context *layered by need* (ME §5.7 — the current phase's working context in detail, the broader project context in summary, the full detail retrievable §6.5), so project restoration is fast (ME §9.7 — not reloading the entire project history §9.1, which floods) and sufficient (§4.9 — enough to continue the current work).

**6.7 — Partial restoration.** Reconstructing *only the needed subset* of context (§4.9 minimal-sufficient, applied to restoration). Partial restoration is the norm (§3.10 — you don't restore everything, which floods §9.1 and wastes §7.9; you restore what the current work needs §4). The discipline (§4.9, ME §5.7): restore *partially and by need* — the current work's required context (§4.4 dependencies, §4.5 constraints, §4.6 goal, §4.7 state), not the whole prior context (which is gone §2.7 and needn't be reproduced §6.1), retrieving more (§6) if the work turns to need it. Partial restoration is minimal-sufficient context (§4.9) achieved through selective reconstruction.

**6.8 — Cold-start recovery.** Reconstructing context from *nothing* — a fresh mind (a new session with no prior context, a successor model AE §9.9, ME §8.10) starting cold. Cold-start recovery is the hardest reconstruction (§6 — no prior context to build on, only the durable memory ME §1.6 and the orienting structure ME §8.10). The discipline (ME §8.10, [M18]): cold-start recovery relies entirely on the durable memory being *designed for it* (ME §8.10 — organized ME §4 so a cold mind orients quickly, the *why* preserved ME §6.7, self-contained [M18]) — the cold mind reads the orienting structure (the README, the index ME, the "read this first"), then reconstructs the working context (§6.1) for its task from the durable record (ME §5.9). Cold-start recovery is the ultimate test of both memory (ME §8.10 — is it designed for a cold mind) and this engine (§6 — can context be reconstructed from nothing but the durable record); it's what makes model succession (AE §9.9) and this entire extraction work.

**6.9 — Confidence-aware restoration.** Reconstructing context *with the trust of its sources* (ME §7 — the restored knowledge carries its provenance ME §7.2, confidence ME §7.4, freshness ME §7.10). Confidence-aware restoration ensures reconstructed context isn't *falsely* trusted (§9.7 — restoring stale context ME §7.10 as if current, or unverified memory ME §10.3 as if trusted). The discipline (ME §7, §9.7): reconstruct context with its trust attached (ME §5.5, §5.6 — the restored knowledge's confidence and provenance), and *verify* the trust-critical restored context against reality ([M2], ME §7.3 — a restored state §4.7 checked current §9.7, a restored fact verified still-true ME §7.10) before reasoning consequentially from it — so reconstruction doesn't reintroduce stale/false context (§9.7) as trusted.

# 7. Context Prioritization

Allocating the bounded window to the highest-value information — the discipline that decides what survives when context can't hold everything (§1.8, the hard bound). OE §5.8 touched this; this is the full prioritization discipline. The governing principle: **rank context by value to the current reasoning and keep the highest-value within the budget — the goal, constraints, and active state always; the peripheral first to go — because the window is finite (§1.8) so context is always an allocation, and the allocation determines what the reasoning has to work with (§1.1).**

**7.1 — What always stays.** The context that *never* leaves, because the reasoning always needs it: the *goal* (§4.6 — all reasoning serves it, and losing it drifts §9.3), the *load-bearing constraints* (§4.5, §7.5 — the invariants AE §2.6, security rules SE, operator constraints ME §3.6 the reasoning could violate §9.6), and the *active state* (§4.7 — what the current work is building on). These are the *permanent context* (§3.4 — the always-present essentials), kept compact (§5.7 — distilled, so they fit permanently without flooding §9.1). The discipline (§9.3, §9.6): the goal and load-bearing constraints *always stay* — because their loss is the highest-cost context failure (goal loss → drift §9.3; constraint loss → silent violation §9.6), so they're protected from every compression (§5.7) and prune (§7.2).

**7.2 — What leaves first.** The context that's *first pruned* when the budget tightens (§2.3, §5): the *settled* (completed reasoning, compressed to products §5.4), the *peripheral* (low-relevance §4.3, retained "just in case" §4.2 noise), the *stale* (§9.7 — no longer current), and the *retrievable* (§5.3 — held in context but available in memory ME §6, so droppable and re-retrievable). The discipline (§7.3): prune lowest-value first (§7.3 ranking) — the settled/peripheral/stale/retrievable leaves before the essential (§7.1), so pruning preserves reasoning quality (§9.1 — dropping noise §4.2 improves it) rather than degrading it (dropping signal §9.2 would starve it).

**7.3 — Importance ranking.** Ranking context by *importance to the current reasoning* (§4.3 relevance, sharpened to a ranking). Importance is *how much the reasoning depends on it* — critical (the reasoning fails without it §4.4 dependency), important (the reasoning is better with it), peripheral (marginal §4.2 near-noise). The discipline (§7.2): rank by importance, keep the critical (§7.1, §4.4), prune the peripheral first (§7.2) — so the budget (§7.9) holds the most-important context, and pruning removes the least-important (§9.1 — improving signal-to-noise).

**7.4 — Dependency ranking.** Ranking by *what the reasoning depends on* (§4.4) — the dependencies ranked highest (§7.1, §4.4 — the reasoning can't proceed correctly without them, §9.2 starvation). Dependency ranking is a specific, critical importance (§7.3) — a dependency is maximally important (the reasoning is *wrong* without it §9.2, not just worse). The discipline (§4.4, §7.1): dependencies are top-priority context (§7.1 — always kept, never pruned §7.2), because a pruned dependency is context starvation (§9.2 — the reasoning made without something it needed).

**7.5 — Constraint ranking.** Ranking the *constraints* (§4.5) — the load-bearing constraints ranked highest (§7.1 — always kept, §9.6 — their loss is silent violation). Constraint ranking ensures constraints survive prioritization (§9.6 — a de-prioritized constraint that gets pruned §7.2 is a constraint the reasoning then violates unknowingly). The discipline (§7.1, §9.6): load-bearing constraints (the ones this reasoning could violate) are top-priority (§7.1 — kept across every compression §5.7 and prune §7.2), because losing a constraint (§9.6) is among the highest-cost context failures.

**7.6 — Freshness ranking.** Ranking by *currency* (§4.7, ME §7.10) — current state/knowledge ranked above stale (§9.7 — stale context reasons from a situation no longer true). Freshness ranking prefers current context and de-prioritizes/refreshes stale (§9.7 — stale state §4.7 is refreshed §6 or dropped). The discipline (§9.7, ME §7.10): rank by freshness — current context kept, stale context refreshed (§6 — re-retrieved current ME §7.10) or pruned (§7.2), so the reasoning works from the *current* situation (§4.7), not a stale one (§9.7 — the drift's root ME §10.7).

**7.7 — Risk ranking.** Ranking by the *risk of getting it wrong* ([M8], SE) — context relevant to high-stakes/irreversible/security-critical reasoning (DE §2 tier, SE) ranked higher (the reasoning that could cause catastrophic harm §1.8 needs its full context, well-prioritized). Risk ranking allocates more budget (§7.9) to the high-stakes reasoning (§1.8 — a high-stakes decision made from thin context is a high-stakes gamble DE). The discipline (§7.9, [M8]): rank by risk — the high-stakes reasoning (irreversible DE §2, security SE) gets its full required context (§4.4 — all dependencies, all constraints §4.5), while low-stakes reasoning tolerates thinner context (§7.9 — the budget spent where being wrong is expensive [M16]).

**7.8 — Operator intent ranking.** Ranking the *operator's intent and preferences* (ME §3.6 — the human the system serves Law 7) highly, because serving the operator well (Law 7) requires their intent present in the reasoning (a decision made without the operator's known preferences §4.5 serves them worse). The discipline (ME §3.6, §7.1): the operator's relevant intent/constraints are high-priority context (§7.1, §7.5 — the standing preferences ME §3.6 and the current request's intent FABLE §1 that the reasoning must serve), so the reasoning stays aligned to what the operator actually wants (Law 7, DE §10.6 — whose-downside).

**7.9 — Context budgeting.** The master prioritization discipline (§1.8, §5.10) — treating the bounded window as a *budget* allocated to the highest-value context (§7.3–7.8). Context budgeting: the budget is finite (§1.8 — the window bound), always-allocated (§2.3 — as context grows §2.2, the budget is continually re-allocated to the highest-value information), with *headroom* (§4.9 [M17] — never budgeted to the limit §9.1, which degrades reasoning — a reserve kept for the reasoning to work in). The discipline (§1.8, §5.10): budget the context deliberately — allocate to the highest-value (§7.3 importance, §7.4 dependencies, §7.5 constraints, §7.7 risk-weighted), compress/prune the rest (§5, §7.2), keep headroom (§4.9), so the reasoning has its essential context (§7.1) plus room to work (§7.9 headroom) — never a window flooded to the limit (§9.1) where reasoning degrades.

# 8. AI-Native Context

Context for a system of AI models — the discipline that makes the working set manageable across models, agents, and the boundaries AI-native systems continually cross. OE §5 (context architecture), §8 (multi-model), §9 (handoffs), §11 (long-running) build the orchestration view; ME §8 the model-independent memory; this is the AI-native context discipline. The governing principle: **AI-native context must survive the boundaries that define AI systems — model swaps, agent handoffs, tool calls, compaction — so context is engineered to be reconstructable (§6) from model-independent durable memory (ME §8.6), because in an AI-native system the working set is destroyed and rebuilt continually, and the system's competence is its ability to reconstruct the right context each time.**

**8.1 — Multi-model context.** Context across a system using multiple models (OE §4, §9.2) — different models for different tasks (OE §4.1), each needing its context constructed (§4). Multi-model context means context is *constructed per-model-invocation* (§4, OE §5.1) from the shared durable memory (ME §8.6), so each model gets the context its task needs (§4.9). The discipline (OE §4, §8.1): context is constructed for each model's task (§4 — the right context for what this model is doing), sourced from model-independent memory (ME §8.6 — so any model's context is reconstructable from the same durable record), so the multi-model system's context is coherent (all models working from the same durable knowledge ME §8.6) yet task-appropriate (§4 — each constructed for its work).

**8.2 — Cross-model context.** Context passed *between* models (OE §8, a model's output becoming another's context input). Cross-model context is a transfer (§2.5, §8.4 handoff) — one model's product externalized (ME §2.1) and another's context reconstructed (§6) from it. The discipline (§8.4, ME §8.6): cross-model context passes through *model-independent durable form* (ME §8.6 — externalized to neutral memory ME §2.1, not passed as a model-specific state), so any model can receive it (§6 — reconstruct its context from the neutral externalized form), making cross-model context transfer robust to which models are involved (ME §8.6, AE §9.9).

**8.3 — Context portability.** Context that moves across models, systems, and time (ME §8.7 — memory portability, applied to context reconstruction). Context is portable because it's *reconstructable* (§6) from portable memory (ME §8.7 — neutral, durable, model-independent §8.6) — the context itself isn't moved (it's transient §1.7), the *memory it reconstructs from* is portable (ME §8.7), so equivalent context (§6.1) can be reconstructed anywhere the memory goes. The discipline (ME §8.7, §6): context portability is memory portability (ME §8.7) plus reconstruction (§6) — port the durable memory (ME §8.7 — a copy), reconstruct context from it (§6) at the destination, so context "travels" by traveling the memory it reconstructs from.

**8.4 — Agent handoffs.** Passing context to a delegated agent (OE §9, §7; FABLE §29 cold-brief). An agent handoff is a context *transfer* (§2.5) to a fresh mind (OE §5.2 — the agent has its own isolated context §3.5, none of the delegator's). The discipline (FABLE §29, OE §9): the handoff is a *cold-brief* — the agent's context is constructed (§4, OE §5.1) to be *self-contained* (FABLE §29, [M18] — everything the agent needs, because it shares none of the delegator's context §3.5): the goal (§4.6), the inputs (by reference ME), the constraints (§4.5), the done-when, the output format (OE §9). An agent handoff that assumes shared context (§9 — "as we discussed") fails (the agent doesn't have it §3.5) — so every handoff is constructed as a complete cold-brief (FABLE §29).

**8.5 — A2A context.** Context in agent-to-agent coordination (OE §7, AE §9.10). A2A context is shared through *durable shared memory* (§3.6, OE §7.4, ME §3.8 — not shared working windows §3.7), so agents coordinate by each reconstructing context (§6) from the shared durable state (OE §7.4). The discipline (OE §7.4, §3.6): A2A context is exchanged through inspectable durable shared memory (ME §3.8, OE §7.4 — each agent externalizes to it ME §2.1 and reconstructs from it §6), so agents coordinate through durable context (auditable OE §7.4, SE §5.9) rather than direct working-context transfer (which couples them OE §12.8 and isn't inspectable).

**8.6 — MCP context.** Context in the tool interface (AE §9.10, the MCP calls). MCP context is what an agent's tool call carries (the inputs the tool needs) and returns (the results entering the agent's context §2.2). The discipline (§4.4, §5.8): the tool call carries the *minimal sufficient* context the tool needs (§4.9 — not the agent's whole context, just what the tool requires), and the tool's return is *distilled* (§5.8 — the relevant result, not raw bulk that floods §9.1) into the agent's context. MCP context is a bounded exchange (§4.4 in, §5.8 out) — the tool gets what it needs, returns what matters, keeping the agent's context (§3.5) sufficient (§4.9) not flooded (§9.1).

**8.7 — Tool context.** The context a tool holds/needs (§8.6 — the tool's working information for its task). Tool context is scoped to the tool's task (§4 — the tool gets what its operation needs, §4.9 minimal-sufficient) and often *stateless* (the tool operates on its inputs, returns results, holds no durable context — the durable state is the agent's/system's ME, not the tool's). The discipline (§8.6): tool context is minimal (§4.9 — the tool's task inputs, not surrounding context) and the tool's results are distilled back (§5.8) — so the tool boundary (§8.6) is a bounded context exchange, not a context merge.

**8.8 — Long-running orchestration (context).** Context across a long-running orchestration (OE §11, ME §9). Long-running context is *continually reconstructed* (§6) — because a long orchestration crosses many boundaries (§2.7 — sessions, model swaps §8.10, compactions §5), each destroying context, each requiring reconstruction (§6) from the durable record (ME §9.5). The discipline (OE §11, §6, ME §9): long-running context relies on continuous externalization (§2.1, ME §9.1) and reliable reconstruction (§6, ME §9.6) — the orchestration's context is transient (§1.7) and continually rebuilt (§6) from the durable memory (ME §9.5), so the long-running work continues across every boundary (§2.7) by reconstructing (§6) rather than persisting context (which it can't §1.7).

**8.9 — Graphify integration (context).** Using the knowledge graph (AE §9.8, ME §8.1) to construct/reconstruct context (§6.3 graph retrieval). Graphify integration lets context construction (§4) and reconstruction (§6.3) pull *related* context by relationship (ME §5.2 — the dependencies, constraints, related decisions that connect to the current work) — giving the reasoning its *structural* context (ME §8.2 — what connects to its work) without pre-loading it (§4.4 — retrieved by relationship when needed). The discipline (§6.3, ME §8.2): use Graphify to construct context that includes the *connected* essentials (the related constraints §4.5, dependencies §4.4, decisions AE §6.2), so the reasoning's context reflects the structure it operates within (ME §8.2 — the model understanding its work's connections), retrieved by relationship (§6.3) rather than held in bulk (§9.1).

**8.10 — Model replacement (context).** Context across a model swap (AE §9.2, ME §8.9). Model replacement destroys the old model's context (§2.7 — the new model has none) and requires the new model to reconstruct (§6, §6.8 cold-start) its context from the durable memory (ME §8.9 — model-independent §8.6). The discipline (ME §8.9, §6.8): model replacement is an amnesia-free context transition (ME §8.9) *because* context is reconstructable (§6) from model-independent memory (ME §8.6) — the new model cold-starts (§6.8) its context from the durable record (ME §5.9, §8.10), reconstructing equivalent working context (§6.1) to continue. Model replacement is survivable (AE §9.2) precisely because context is not held in the model (§1.7 — it's reconstructed §6 from memory ME §8.6), so swapping the model doesn't lose the context (it's rebuilt §6 in the new model from the enduring memory ME).

# 9. Context Failure Modes

The ways context management fails — each degrading the reasoning that depends on it (§1.8). This is inversion [M16] applied to context: knowing the failures is how you construct (§4), prioritize (§7), and reconstruct (§6) against them. The governing principle: **context failures are silent and determinative — they degrade every decision made from the failed context (§1.8) without announcing themselves, so they're detected by their symptoms (wrong decisions, drift, violated constraints) and prevented by disciplined construction (§4), prioritization (§7), and reconstruction (§6).**

**9.1 — Context overflow.** Context grown past the effective window (§2.2, §7 — the bound exceeded, or approached so closely that reasoning degrades AE §9.4). *Signal:* the window is full/near-full; reasoning degrades (attention diluted AE §9.4 — the model attends less well to any part when holding too much); important context gets pushed out (§9.2 — overflow forces out signal §4.2). *Cure:* compression (§5 — reclaim space by keeping products §5.4), prioritization (§7 — keep the high-value §7.3, prune the low §7.2), and headroom discipline (§7.9 [M17] — never fill to the limit). Overflow is the failure of unmanaged growth (§2.2) — the context that grew without compression (§5) or pruning (§7.2) until it degraded (§9.1) or overflowed (§9.2).

**9.2 — Context starvation.** Context missing what the reasoning needs (§4.4 — a dependency omitted, §4.9 — below minimal-sufficient). *Signal:* reasoning made without something it needed (a decision DE without its deciding constraint §4.5, an action without its required input §4.4) — producing a wrong result from incomplete context (§1.8 — the reasoning was sound but the context was insufficient). *Cure:* dependency inclusion (§4.4 — include all the reasoning depends on), minimal-*sufficient* construction (§4.9 — sufficient, not just minimal), and retrieval (§6 — pull in what's needed when the reasoning turns to need it). Starvation is the opposite failure to overflow (§9.1) — too little, not too much; the reasoning starved of what it needed (§4.4). Both are construction failures (§4 — the sweet spot §4.9 missed on either side).

**9.3 — Context drift.** The reasoning drifting from its goal as context evolves (§4.6, OE §12.6). *Signal:* the reasoning is competent but no longer serving the original goal (§4.6 — solving an adjacent problem, optimizing a mutated objective OE §12.6, FABLE §33.5) — the goal was lost or blurred as context grew (§2.2) and compressed (§5). *Cure:* goal always stays (§7.1, §4.6 — the goal never compresses away §7.1), re-anchoring (FABLE §1 step 7, OE §12.6 — check against the original goal, not the drifted context), and cold-brief discipline (FABLE §29 — a fresh context re-stated from the goal, not a chain of reinterpretations §8.4). Drift is the slow loss of aim (§9 — the goal §4.6 fading from context as work proceeds), prevented by keeping the goal always present (§7.1).

**9.4 — Context fragmentation.** Context scattered/incoherent — pieces that don't form a coherent working set (accumulated §2.2 without integration §4.1, contradictions §9.8 unreconciled). *Signal:* the context holds pieces that don't cohere (fragments from different tasks, contradictory state §9.8, an accumulated mess rather than an assembled whole §4.1); reasoning from it is confused (§10, FABLE §6 — the degraded context better discarded §2.8). *Cure:* deliberate assembly (§4.1, §2.1 — construct a coherent working set, don't accumulate), compression to a clean state (§5.9 checkpoint — a coherent compressed context), and deliberate discard-and-rebuild (§2.8, §10, FABLE §6 — a fragmented context discarded and reconstructed §6 clean). Fragmentation is the failure of accumulation-over-assembly (§4.1 — context that accreted §2.2 rather than being constructed §4).

**9.5 — Hidden assumptions (in context).** The reasoning resting on assumptions *not in* the explicit context ([M1], DBG §5.5, ME §10.10) — premises the reasoning assumes but the context doesn't state/verify. *Signal:* reasoning that's correct *only under* an unstated assumption (a decision assuming a constraint that isn't in context §4.5, a state assumed that isn't verified §9.7); the reasoning breaks when the hidden assumption is false ([M1] — the assumed-away case). *Cure:* explicit constraint (§4.5) and state (§4.7) inclusion (make the assumptions explicit in context), assumption auditing ([M1], DBG §5.4 — what does this reasoning assume, and is it in context/verified), and constraint extraction (§5.7 — the load-bearing assumptions preserved explicitly). Hidden assumptions in context are the reasoning built on unstated foundations (§9.6-adjacent — like lost constraints, but never-stated rather than dropped).

**9.6 — Lost constraints.** A constraint that *was* in context being lost (dropped in compression §5, pruned §7.2, faded as context grew §2.2). *Signal:* the reasoning violates a constraint it should respect (an invariant AE §2.6 broken, a security rule SE violated, an operator constraint ME §3.6 ignored) — because the constraint left the context (§7.5 — de-prioritized and pruned) and the reasoning no longer "sees" it. *Cure:* constraint ranking (§7.5 — load-bearing constraints top-priority §7.1, never pruned §7.2), constraint extraction (§5.7 — preserved across compression), and constraints-always-stay (§7.1). Lost constraints are among the highest-cost context failures (§7.1, §7.5 — a silent violation, the reasoning breaking a rule it can't see), which is why constraints are protected from pruning (§7.1).

**9.7 — Stale context.** Context holding information no longer current (§4.7, ME §7.10 — state/knowledge that was true, isn't now). *Signal:* reasoning from a stale situation (a state §4.7 that's changed, a fact ME §7.10 that's superseded ME §6.4) — producing decisions right for the *past* situation, wrong for the current one (ME §10.7 drift). *Cure:* freshness ranking (§7.6 — current context preferred, stale refreshed/pruned), state refresh at reconstruction (§6, §9.7 — restored state verified current [M2]), and confidence-aware restoration (§6.9 — restored context's currency checked ME §7.10). Stale context is the reasoning working from an outdated world (§4.7 — the situation moved, the context didn't), prevented by freshness discipline (§7.6) and verification (§6.9, [M2]).

**9.8 — Conflicting context.** Context holding contradictory information (§9.4 fragmentation's content — two pieces that disagree ME §7.6). *Signal:* the context contains contradictions (conflicting state, contradictory knowledge ME §7.6, incompatible constraints); reasoning from it is inconsistent (which contradictory piece does it use?). *Cure:* conflict resolution (ME §5.8, §7.6 — resolve the conflict, don't hold both; diagnose why RE §5.5), coherent assembly (§4.1 — construct a consistent working set), and reconstruction (§6 — a clean context rebuilt from resolved memory ME §6.3). Conflicting context is incoherence (§9.4) at the content level — the reasoning given contradictory inputs, prevented by resolving conflicts (ME §7.6) before/during construction (§4.1).

**9.9 — Incorrect restoration.** Reconstruction (§6) producing *wrong* context — restoring stale (§9.7), incomplete (§9.2 starvation), or mis-assembled (§9.4 fragmented) context. *Signal:* a resumed session/model reasons wrongly from its reconstructed context (the restoration §6 gave it stale state §9.7, missing dependencies §9.2, or an incoherent set §9.4). *Cure:* confidence-aware restoration (§6.9 — restored context's trust verified [M2]), partial-but-sufficient restoration (§6.7, §4.9 — enough, current, coherent), and verification of restored context (§6.9, [M2] — the reconstructed context checked against reality before consequential reasoning). Incorrect restoration is reconstruction's failure mode (§6 — the rebuild §6.1 producing a flawed context), detected when resumed reasoning goes wrong (§9.9 signal) and prevented by verified, sufficient, coherent reconstruction (§6.9, §6.7).

**9.10 — Detecting context failures (the meta-discipline).** Context failures are *silent* (§9 — they degrade reasoning §1.8 without announcing), so they're detected by *symptoms in the reasoning*: a wrong decision traced to missing context (§9.2 starvation), reasoning that drifted from the goal (§9.3), a violated constraint (§9.6 lost constraint), a decision right for a past situation (§9.7 stale), inconsistent reasoning (§9.8 conflicting). The detection discipline (DBG — the reasoning failure traced to its context): when reasoning goes wrong, ask *was the context adequate?* (§4.9 — sufficient, current §9.7, coherent §9.4, un-drifted §9.3) — because a reasoning failure is often a *context* failure (the reasoning was sound, the context it reasoned from was flawed §1.8). The discipline: suspect context (§9) when reasoning disappoints — the context is the input to all reasoning (§1.1), so a reasoning failure's root is frequently in the context it was made from (§1.8), and fixing the context (§4, §6, §7) fixes the reasoning.

# 10. Context Decision Trees

Built per [M7 → skill S-007]. Context-specific; defer to prior engines where the decision is theirs.

**10.1 — Remember vs Context (where should this information live?)**
```
Does the CURRENT reasoning need this information active? (§4.3)
  ├─ yes → in CONTEXT (§4 — construct it into the working set), AND if durable-worthy, also in MEMORY (ME §2.2)
  └─ no → is it worth keeping at all? (ME §2.2)
        ├─ yes (durable knowledge) → MEMORY only (ME §11.1); retrieve into context (§6) when a task needs it
        └─ no (transient, derivable) → neither; don't hold it (§9.1 — noise §4.2)
   (rule: context holds what the current reasoning needs §4; memory holds what persists ME; the durable-worthy needed-now is in both)
```

**10.2 — Retrieve vs Recompute**
```
Is the needed information cheaply retrievable from memory (ME §6), or must it be recomputed?
  ├─ retrievable + reliable (in durable memory ME §1.6, provenance/freshness intact ME §7) → RETRIEVE (§6 — cheaper, and it's the stored truth)
  └─ not reliably retrievable (not externalized ME §2.1, or stale ME §7.10, or was disposable ME §1.7) → RECOMPUTE
        (re-derive it — a spike RE §Stage 6, re-reading the territory [M2]); then externalize the result (ME §2.1) so next time it's retrievable
```

**10.3 — Compress vs Preserve**
```
Is the context approaching the budget (§7.9), AND is this portion settled (not active reasoning)?
  ├─ both → COMPRESS (§5 — the settled portion to its products §5.4, reclaiming budget §5.10)
  └─ active reasoning / budget has headroom → PRESERVE at full fidelity (§5.1 — the active work stays detailed; don't
        compress what you're actively reasoning over, which loses the working state §9)
   (never compress: the always-stays §7.1 — goal §4.6, load-bearing constraints §7.5, active state §4.7)
```

**10.4 — Summarize vs Reference**
```
Will the reasoning need this information's FULL detail, or just its ESSENCE?
  ├─ essence (the decision, the finding, the conclusion) → SUMMARIZE (§5.4 — keep the product, lossy §5.4, compact)
  └─ possibly-full detail, but not constantly → REFERENCE (§5.3, §10 — hold a pointer, retrieve §6.5 the full content when
        the reasoning turns to need it); lossless §5.3, the preferred compression when retrieval §6 is reliable
```

**10.5 — Share vs Isolate (context between agents)**
```
Do multiple agents need to COORDINATE on this, or is it one agent's private work? (§3.6, §3.7)
  ├─ coordinate → SHARE through durable shared memory (§3.6, ME §3.8, OE §7.4 — inspectable, each agent reconstructs §6
  │     its own working context from it), NOT a shared working window (§3.7 — which couples them OE §12.8)
  └─ private work → ISOLATE (§3.7, OE §5.2 — the agent's own context, so confusion/compromise §SE doesn't spread §3.5)
```

**10.6 — Restore vs Restart**
```
Is the current context COHERENT and USEFUL, or DEGRADED (§9.4 fragmented, §9.8 conflicting, §9.7 stale, drifted §9.3)?
  ├─ coherent → CONTINUE (the context is serving; keep working, compress §5 as it grows)
  └─ degraded → is a clean rebuild cheaper than untangling? (FABLE §6, §2.8)
        ├─ yes → RESTART: discard the degraded context (§2.8), reconstruct clean (§6) from good externalized notes (ME §2.1)
        └─ no (degradation is minor/local) → repair in place (resolve the conflict §9.8, refresh the stale §9.7, re-anchor the goal §9.3)
   (rule: a badly degraded context is better discarded and rebuilt §6 than pushed through FABLE §6 — the clean restart)
```

**10.7 — Global vs Local (context scope)**
```
Does this apply to ALL the reasoning, or just the current task?
  ├─ all → GLOBAL context (§3.4 — always present §7.1, the operator preferences ME §3.6, standing constraints §4.5, kept compact §5.7)
  └─ current task → LOCAL/working context (§3.1 — assembled for this task §4, discarded §2.8 when the task's done)
```

**10.8 — Graph vs Semantic (retrieval for construction)**
```
Is the needed context about RELATIONSHIPS or about MEANING-SIMILARITY? (§6.3 vs §6.4)
  ├─ relationships (dependencies, constraints, connected decisions — the structural context) → GRAPH retrieval (§6.3, ME §5.2)
  ├─ meaning-similarity (relevant-by-meaning knowledge, similar past work) → SEMANTIC retrieval (§6.4, ME §5.1)
  └─ specific known item → REFERENCE/keyword retrieval (§6.5, ME §5.3); rich need → COMBINE (§6, ME §5.4)
```

**10.9 — Human vs AI Context**
```
Is this context being constructed for a HUMAN to reason from, or an AI?
  ├─ human (a report FABLE §28, an approval decision SE §4.9, a briefing) → construct for the human (FABLE §28 — outcome-first,
  │     the essential surfaced, the consequences plain SE §4.9, calibrated [M20]); the human's context is their attention, precious
  └─ AI (a model's working set, an agent's brief §8.4) → construct for the AI (§4 — minimal-sufficient §4.9, cold-brief FABLE §29,
        model-independent-reconstructable ME §8.6); the AI's context is its window, bounded §7
```

# 11. Context Checklists

The engine compressed. Run the long form (§1–§8) until reflex.

**11.1 — Before starting work (context construction gate)**
- [ ] Is the GOAL in context, clear and framed (§4.6, FABLE §1) — so the reasoning stays aimed (§9.3)?
- [ ] Are the load-bearing CONSTRAINTS in context (§4.5, §7.5) — the invariants AE §2.6, security SE, operator constraints ME §3.6 this could violate (§9.6)?
- [ ] Are the DEPENDENCIES included (§4.4) — everything this reasoning needs (§9.2 starvation avoided)?
- [ ] Is the relevant STATE current (§4.7, §9.7 — not stale) and the relevant KNOWLEDGE retrieved (ME §5)?
- [ ] Is it MINIMAL SUFFICIENT (§4.9) — enough, with headroom (§7.9 [M17]), not flooded (§9.1)?
- [ ] Is it SIGNAL, not noise (§4.2) — is everything here needed (§4.3), or is there clutter to cut?
- [ ] Is the context COHERENT (§9.4) — an assembled whole (§4.1), not an accumulated fragment?

**11.2 — Before delegating to another AI (handoff gate)**
- [ ] Is the brief SELF-CONTAINED (FABLE §29, §8.4, [M18] — the agent shares none of my context §3.5)?
- [ ] Does it include the goal (§4.6), inputs (by reference ME), constraints (§4.5), done-when, output format (OE §9)?
- [ ] Is it constructed for the agent's task (§4.9 — minimal-sufficient for what it's doing), not my whole context?
- [ ] Is the untrusted content handled by the agent's trust tier (SE §7.2, AE §9.6 — does a reader agent get only readable, non-acting context)?
- [ ] Would this brief work handed to a stranger who wasn't in my conversation (FABLE §29, [M18])?
- [ ] Is what the agent produces going to be reconstructable (§8.2 — externalized to durable form ME §8.6, not model-specific)?

**11.3 — Before restoring a project (reconstruction gate)**
- [ ] Am I reconstructing the RELEVANT context for the current work (§6.7 partial, §4.9), not everything (§9.1 flood)?
- [ ] Is the restored STATE verified current (§6.9, §9.7, [M2] — not stale-restored §9.9)?
- [ ] Is the restored knowledge carrying its TRUST (§6.9, ME §7 — provenance, confidence, freshness)?
- [ ] Are the goal, constraints, and next-action reconstructed (§6.6, PE §7.1 — so the work can continue §9.3)?
- [ ] Is the reconstruction COHERENT and SUFFICIENT (§9.9 — not fragmented §9.4 or starved §9.2)?
- [ ] For a cold start (§6.8): did I read the orienting structure (ME §8.10 — the index, "read this first") before reconstructing?

**11.4 — Before ending a session (externalization gate)**
- [ ] Is everything IMPORTANT externalized to memory (§2.1, ME §2.1 — because context expires §2.7, un-externalized is lost §9)?
- [ ] Are the decisions made recorded (ME §2.4, DE §2 Stage 8, AE §6.2 — with their why §5.6)?
- [ ] Is the current state checkpointed (§5.9, ME §9.4 — so the next session resumes §6, §9.3)?
- [ ] Is a handoff note written if a boundary is imminent (OE §5.4, ME §9.4 — self-contained [M18] for reconstruction §6)?
- [ ] Is the next-action externalized (PE §7.1 — so the next session knows where to continue §9.3)?
- [ ] Have I assumed the session could end NOW (OE §5.3 — externalized continuously §2.1, not waiting for a clean end)?

**11.5 — Before compressing context**
- [ ] Am I compressing SETTLED portions (§10.3, §5.1 — not active reasoning, which loses working state §9)?
- [ ] Am I keeping the PRODUCTS (§5.4 — decisions §5.6, findings, state §5.5) and discarding the PROCESS (deliberation, transcript)?
- [ ] Are the always-stays PRESERVED (§7.1 — goal §4.6, load-bearing constraints §5.7/§7.5, active state §4.7 — never compressed away)?
- [ ] Is lossless-by-reference preferred where possible (§5.3, §10 — reference to memory ME §6, nothing lost)?
- [ ] Is the compressed context still SUFFICIENT (§4.9 — the ongoing reasoning has what it needs, §9.2 starvation avoided)?
- [ ] Is a checkpoint externalized at this compression (§5.9, ME §9.4 — the pre-compression state restorable §6 if the compression lost something needed)?

# 12. Real Engineering Examples

Complete context strategies, showing the engine running — every construction, prioritization, compression, restoration, and tradeoff. Read as the strategy being made.

**12.1 — A desktop AI application.**
- *Context construction (§4):* the working context for a user request is assembled (§2.1) from the request (goal §4.6), the user's relevant preferences (ME §3.6, retrieved §6), and the relevant app state (§4.7). Minimal-sufficient (§4.9 — this request's needs, not the whole app history §9.1).
- *Prioritization (§7):* the user's intent (§7.8) and the current request's goal (§7.1) always present; older interaction detail pruned (§7.2 — settled, low-relevance §4.3).
- *Compression (§5):* completed interactions compressed to their outcomes (§5.4 — what the user did/decided, not the full exchange), the app's learned preferences externalized to memory (ME §2.1).
- *Restoration (§6):* on reopening, the app restores the relevant user context (§6.6 — preferences ME §3.6, recent state §4.7) — partial (§6.7 — the current session's needs, not all history).
- *Tradeoff:* local-only context (SE §13.3 — privacy, the personal context stays on the machine), reconstructed from local memory (ME §3.12).

**12.2 — A reverse-engineering project.**
- *Context construction (§4):* the working context holds the current hypothesis (RE §7.1), the observations supporting/refuting it (§4.4 — the evidence the reasoning depends on), and the reverse-engineered model so far (RE §7.1). The target's full behavior is reference context (§3.10 — retrieved §6 as specific analysis needs).
- *Prioritization (§7):* the current hypothesis (§7.1 goal-like) and the observations that test it (§7.4 dependencies) stay; peripheral observations (§7.2) compressed to the model they informed (§5.6-like — the conclusion, not every observation RE §7.1).
- *Compression (§5):* the accumulated observations compressed to the *model* they built (§5.4 — the understanding RE §7.1, the observation-log externalized to memory ME for reference §6.5). State extraction (§5.5 — the current model as the resumable state).
- *Trust in reconstructed context (§6.9):* the reverse-engineered model is held as *hypothesis* (RE §7.1, ME §7.4 — inferred, not verified [M1]) — so reconstructed context carries that uncertainty (§6.9), and the reasoning treats the model as testable (RE §7.1, [M2]) not certain.

**12.3 — A multi-agent AI operating system (JarvisOS).**
- *Context architecture (§3, §8):* each agent's context isolated (§3.5, OE §5.2), constructed (§4, OE §5.1) from shared durable memory (§3.6, ME §3.8); agents coordinate through the shared durable state (§8.5, OE §7.4), not shared working windows.
- *Construction (§4, §8.4):* each agent gets a cold-brief (FABLE §29, §8.4 — self-contained: goal §4.6, inputs, constraints §4.5, done-when, output format), with the trust tier respected (SE §7.2, AE §9.6 — a reader agent's context can hold untrusted content because it can't act §8.6; an actor agent's context never holds raw untrusted content).
- *Prioritization (§7):* the operator's intent (§7.8, Law 7) and the standing constraints (§7.5 — the Constitution, the invariants AE §2.6, the security rules SE) are global context (§3.4) always present in every agent's construction (§7.1).
- *Compression & long-running (§5, §8.8):* continuous externalization (§2.1, OE §5.3) to durable memory (ME §9.5); checkpoints (§5.9, ME §9.4) at phase boundaries (PE §5.4); the orchestration's context continually reconstructed (§6, §8.8) across the many boundaries (§2.7) a long-running system crosses.
- *Model replacement (§8.10):* amnesia-free (ME §8.9) — context reconstructable (§6, §6.8) from model-independent memory (ME §8.6), so a model swap is a cold-start reconstruction (§6.8), not a loss.
- *Why it holds:* context is treated as transient (§1.7) and continually reconstructed (§6) from durable model-independent memory (ME §8.6) — so the system's competence survives every boundary (§2.7) because it can always rebuild the right context (§6) from the enduring record (ME).

**12.4 — A Graphify knowledge system.**
- *Context construction via graph (§8.9, §6.3):* the working context is constructed by graph retrieval (§6.3, ME §5.2) — pulling the *connected* context (the dependencies, related decisions AE §6.2, constraints §4.5 that connect to the current work), so the reasoning has its structural context (ME §8.2) without pre-loading it (§9.1).
- *On-demand structural context (§8.9, ME §8.2):* a model querying "what depends on this decision" (ME §5.2) gets that structural context retrieved (§6.3) into its working set precisely when needed (§4.4) — reducing what must be held (§9.1) by making the structure queryable (§8.9).
- *Tradeoff:* the graph as a retrieval tier (§6.3) over the durable store (ME §3.11, §1.7) — context reconstruction (§6) uses the graph for relationship-context (§6.3) and falls back to semantic/keyword (§6.4, §6.5) if the graph's unavailable (ME §5.3 baseline).

**12.5 — An MCP ecosystem.**
- *Tool context (§8.6, §8.7):* each MCP call carries minimal-sufficient context (§4.9 — the tool's task inputs §4.4, not the agent's whole context §8.6), and returns distilled results (§5.8 — the relevant result, not raw bulk that would flood §9.1 the agent's context).
- *Bounded exchange (§8.6):* the tool boundary is a bounded context exchange (§4.4 in, §5.8 out) — the agent's context (§3.5) gives the tool what it needs (§4.9) and receives distilled results (§5.8), staying sufficient (§4.9) not flooded (§9.1).
- *Tradeoff:* distilling tool results (§5.8) trades completeness for context-economy (§5.10 — a tool that returns bulk floods §9.1; distilling keeps the agent's context sharp §9.1, with the full result retrievable ME §6.5 if needed).

**12.6 — A long-running autonomous workflow.**
- *Continuous reconstruction (§8.8, §6):* the workflow crosses many boundaries (§2.7 — sessions, compactions §5, model swaps §8.10), each destroying context, each requiring reconstruction (§6) from the durable record (ME §9.5).
- *Externalization (§2.1) & checkpointing (§5.9):* continuous externalization (OE §5.3 — the workflow's state, decisions, progress to durable memory ME §9.1) and checkpoints (ME §9.4 — restorable states §6), so the workflow resumes (§6, §9.3) across every boundary.
- *Goal preservation (§7.1, §9.3):* the goal always present (§7.1) across the long horizon, re-anchored (§9.3, OE §12.6) at each reconstruction (§6) — so the workflow doesn't drift (§9.3, OE §12.6) over its long run.
- *Freshness (§7.6, §9.7):* state refreshed at reconstruction (§6.9, §9.7 — the long-running workflow's world changes, so restored state is verified current [M2], not stale-restored §9.9).
- *Tradeoff:* the workflow holds minimal working context (§4.9), relying on reconstruction (§6) — so it's robust to the boundaries (§2.7) but depends on reliable externalization (§2.1) and reconstruction (§6); a gap in externalization (§9 — un-externalized context lost §2.7) is a gap in the workflow's continuity.

**12.7 — A production incident.**
- *Context construction under pressure (§4):* the incident's working context is assembled fast (§4 — the symptom DBG §2 Stage 0, the affected system's state §4.7, the recent changes §4.8 that might have caused it §DBG §11.5) — minimal-sufficient (§4.9) for diagnosis, not the whole system (§9.1 — no time, and flooding degrades §9.1 the pressured reasoning).
- *Prioritization (§7.7 risk):* the incident is high-stakes (§7.7 — production harm), so its context gets full budget (§7.9) — the relevant state, changes, and constraints (§4.5 — what must not be violated in the fix) all present (§9.2 — starvation here is a bad fix under pressure).
- *Evidence preservation (§2.1, SE §10.7):* the incident's context (logs, state DBG §4.5) externalized (§2.1) before the stabilizing restart (FABLE §27.2 — which destroys the context §2.7), so forensics (SE §10.7) can reconstruct (§6) it.
- *Restoration for forensics (§6):* after stabilization (FABLE §27), the incident's context is reconstructed (§6) from the preserved evidence (§2.1, SE §10.7) for root-cause analysis (DBG §5) — the reconstruction §6 must be faithful (§9.9 — an incorrectly-restored incident context leads to a wrong root cause).

**12.8 — A model replacement.**
- *Cold-start reconstruction (§8.10, §6.8):* the new model has no context (§2.7 — the old model's context is gone). It reconstructs (§6.8 cold-start) from the model-independent durable memory (ME §8.6, §8.9).
- *Orientation first (§6.8, ME §8.10):* the new model reads the orienting structure (ME §8.10 — the README, the index, the "read this first," this extraction set) before reconstructing (§6.8) — establishing the global context (§3.4 — the methodology, the constraints, the operator ME §3.6) before the task context (§3.1).
- *Verification (§6.9, [M2]):* the reconstructed context is verified — the restored state checked current (§9.7), the restored knowledge's trust intact (ME §7) — so the new model doesn't inherit stale (§9.7) or incorrectly-restored (§9.9) context.
- *Why it works (ME §8.9, §8.6):* model replacement is amnesia-free (ME §8.9) *because* context is reconstructable (§6) from model-independent memory (ME §8.6) — the new model rebuilds equivalent context (§6.1) and continues; this entire extraction is the ultimate instance (ME §8.10 — the successor reconstructing the predecessor's working approach from the durable record).

**12.9 — A cold-start recovery.**
- *The hardest reconstruction (§6.8):* context reconstructed from *nothing* — a fresh mind, no prior context, only the durable memory (ME §1.6) and its orienting structure (ME §8.10).
