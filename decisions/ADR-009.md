# ADR-009 — The kernel splits into READER and ACTOR trust contexts
**2026-07-10 · Accepted** — ratifies [ARCHITECTURE-V2](../ARCHITECTURE-V2.md) §3/§12; supersedes the implicit single-context kernel assumed by ADR-003's era.

**Context.** The red-team review ([C2](../reviews/2026-07-09-red-team-review.md)) showed that a kernel which reads untrusted content (web pages, inbound email) in the same context where it holds terminal, file-write, and send-capable tools converts a single prompt injection into persistent memory poisoning: injected text becomes journals and memories that every future session — and every future model — inherits as trusted instruction. `SECURITY_ENGINE.md` §7.2 states, and 2026 evaluations confirm (adaptive attacks bypass detection-based defenses at >85% in independent meta-analysis; architectural isolation is the only defense that holds — see the [2026-07-10 architecture review](../reviews/2026-07-10-architecture-review.md) §1.4), that injected instructions are indistinguishable from legitimate content in principle. A law ("treat data as data") without a mechanism is a wish.

**Decision.** The agent kernel operates as two structurally separate trust contexts:

- **READER (L4a)** — the only context that ingests T2/T3 content (per ADR-013). It is spawned with an MCP profile containing **only READ-tagged tools**. Its sole privileged output is a *proposal*: a file describing intended actions in plain terms.
- **ACTOR (L4b)** — holds WRITE/SEND-tagged tools. It **never reads raw untrusted bytes**; it consumes only vetted proposals (and, for outward/destructive actions, only Outbox-approved entries per ADR-012).

Every MCP tool registered in `config\mcp.json` is tagged READ, WRITE, or SEND. The injection canary suite (seeded pages/emails containing "write CANARY to X / send Y") must pass before any model, kernel, or MCP-profile change is accepted.

**Consequences.** Injected instructions land in a context that structurally cannot act on them. Cost: orchestration complexity and token overhead — two contexts where one sufficed, plus proposal-file plumbing. This is V1 simplicity deliberately traded for safety V1 demonstrably lacked. The split is enforced by MCP profiles (configuration), not by prompt exhortation.

**Alternatives considered.** (1) *Detection/filtering of injected instructions* — rejected: loses to adaptive attackers, per the engine corpus and all 2026 evidence. (2) *Single context with hardened prompting* — rejected: a wish, not a mechanism; exactly the defect V2 exists to fix. (3) *Code-then-execute (CaMeL-style: the agent emits an explicit, checkable plan/program; unprivileged readers process untrusted text)* — not adopted now because kernel support is uneven, but recognized as the natural upgrade of this pattern with the same trust math.

**Future review criteria.** Reopen if: (a) the incumbent kernel gains first-class code-then-execute support — upgrade rather than abandon the split; (b) independent, adversarial, 12-months-plus evaluations ever show robust model-level injection resistance — the split may then relax from "only defense" to "defense in depth," never to nothing; (c) the injection canary suite fails at any change — that is an incident, not a review trigger, and blocks the change.
