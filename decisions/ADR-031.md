# ADR-031 — Glass Overlay: an always-on-top HUD as a replaceable L5 interface
**2026-07-12 · Accepted** — Priority 2 of the operator's JARVIS-feel directive (2026-07-12 session); an implementation-selection ADR in the ADR-030 pattern. No frozen document is touched; the overlay is an L5 interface under ARCHITECTURE.md §L5 and the ADR-029 contract.

**Context.** The operator's JARVIS-feel priority order (voice → glass overlay → visual awareness → presence → MCP) calls for a JARVIS presence *on the desktop itself*: a translucent, always-on-top head-up display that can be summoned with a hotkey, accepts a typed request, and streams the reply — without opening a browser or the Open WebUI adapter. No ADR designs this surface yet; ADR-029 already classifies any such thing as an L5 interface ("how the human reaches the system"), and Convention 5 (ADR-030 journal; jarvis_interface.py) requires every interface to speak only to the single JARVIS interface on 127.0.0.1:11435 — never to a raw model, the gateway, or Ollama.

The component question is what to build the overlay *from*. Candidates surveyed (Law 3: never build what exists; RESEARCH_ENGINE §OSS-evaluation):

| Candidate | Verdict |
|---|---|
| **tkinter (CPython stdlib) + ctypes Win32 calls** | **Chosen.** Zero new dependencies (ships inside the uv-managed CPython already in use — verified `TkVersion 8.6` on this machine); layered-window alpha gives the glass translucency; `ctypes` gives the global summon hotkey (`RegisterHotKey`) and no-activate/topmost styles. Boring in exactly the Law 10 sense. |
| PySide6 / Qt | Real acrylic blur and richer visuals, but a ~1 GB dependency for a HUD; adopted only if the operator wants visual polish tkinter cannot give. **Named successor.** |
| Rainmeter | Mature desktop-overlay platform, but interactive *streaming chat* requires plugin work in its own DSL — more glue than Python, in a less survivable language. Second successor for the passive-status half only. |
| Electron / Tauri | A browser engine or Rust toolchain for one translucent window violates Law 3's glue budget and Law 10. Rejected. |

**Decision.**

1. **The Glass Overlay is a replaceable L5 adapter** in the exact shape of the voice adapter (ADR-022 pattern): `config\kernel\jarvis_overlay.py` (Law 3 glue, ≤200 lines, assembles stdlib components), configured by `config\overlay.yaml`, started by `install\start-jarvis-overlay.ps1`, validated headlessly by `tests\overlay.ps1`. Removing it (delete the file, the config, the task) leaves the Runtime untouched.
2. **Stack: tkinter + ctypes, stdlib-only** (pyyaml is the sole pip dependency, matching every other adapter). Isolated uv venv at `config\overlay\.venv` so no adapter shares an environment (voice-venv precedent).
3. **Convention 5 holds:** the overlay POSTs to `http://127.0.0.1:11435/v1/chat/completions` (streaming) and reads `GET /health`. It never talks to the gateway, Ollama, or a model. Local-only; no listening socket of its own.
4. **Trust tiers (ADR-013):** typed operator input in the overlay is T0, same as any operator keyboard input. The overlay renders reply text only; it executes nothing, and no SEND-class action exists at L5 (the Outbox is Phase 6).
5. **Passive state it may display** comes only from the file substrate (ADR-008/029 hub principle): `data\health-status.md` (watchdog) and — once voice is live-confirmed — a voice-state file published by the voice adapter. It never opens sockets to other adapters.
6. **Visuals within tkinter's ceiling:** per-window alpha translucency, frameless, topmost, dark glass + accent styling. True acrylic blur is explicitly out of scope for v1; wanting it is the trigger for the PySide6 successor, behind the same seam.

**Consequences.** The desktop gains a summonable JARVIS surface with zero new heavyweight dependencies and no new trust boundary (everything flows through the interface, which already enforces routing/thinking policy via the gateway). Cost: tkinter's plain look versus a blurred acrylic ideal; accepted for v1, upgrade path named. One more logon task and watchdog concern once live-validated.

**Alternatives considered.** Recorded in the candidates table above; additionally (a) *extending Open WebUI into an overlay* — rejected: it is an external product used stock (branding-ceiling lesson, Phase 1 T4), not a codebase we fork; (b) *waiting for Visual Awareness (Priority 3) to co-design a combined surface* — rejected: priorities are ordered to ship feel incrementally, and the overlay's seam (files in, interface out) will not change shape when awareness arrives.

**Future review criteria.** Reopen if: (a) the operator asks for acrylic/blur or animation beyond tkinter — swap to PySide6 behind the same config and interface contract; (b) the overlay glue exceeds ~200 lines — stop and adopt a component instead (Law 3's own rule); (c) a mature open-source "LLM desktop HUD" appears and passes the COMPONENTS.md bar — prefer it and demote this glue; (d) Priority 3 (Visual Awareness) needs screen capture — that is a *new* ADR (it is a sensor, T2/T3 data, not an interface concern).
