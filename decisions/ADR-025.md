# ADR-025 — Physical repository mapping: how the four-repo partition lands on disk
**2026-07-11 · Accepted** — implements ADR-011 concretely; operates under ADR-016; supersedes the root-level `memory\`, `journal\`, `vault\` paths of the V1 directory contract (ARCHITECTURE.md §4, README map) by relocation, not by editing the frozen documents.

**Context.** ADR-011 mandates four repositories by data classification, but the frozen directory contract places `memory\`, `journal\`, and `vault\` at the root of `D:\Fable OS` — and two git repositories cannot share one root. ARCHITECTURE-V2 §3 already writes the path `data\memory\_quarantine\`, implying the intended physical answer. The mapping must be pinned before the first `git init` (T5), because repository boundaries are the hardest thing to move later.

**Decision.**

```
D:\Fable OS\                     ← REPO 1: fableos-docs (root)
├── *.md  decisions\  reviews\  skills\  install\  tests\
├── config\                      ← REPO 2: fableos-config (nested)
│   ├── jobs\   kernel\   vault\SECRETS-INVENTORY.md   models.yaml   mcp.json
├── data\                        ← REPO 3: fableos-data (nested)
│   ├── memory\  (incl. memory\_quarantine\)
│   └── journal\
└── projects\<name>\             ← REPO N: one repo per project (nested)
```

1. **Ownership.** `fableos-docs` owns methodology, decisions, reviews, skills, install scripts, tests. `fableos-config` owns all configuration, jobs, kernel instructions, and the secrets *inventory* (names only, per Law 9 — `vault\` relocates to `config\vault\`). `fableos-data` owns memory and journals — the operator's externalized mind. Each `projects\<name>\` owns itself.
2. **Git boundaries.** The parent (docs) repo ignores `config/`, `data/`, `projects/` entirely; nested repos are invisible to it. Every repo carries the gitleaks pre-commit hook via tracked `core.hooksPath`. `fableos-data` additionally carries an unconditional pre-push block.
3. **Backup boundaries.** Remote policy per ADR-011: docs — may push (public or private); config — private remote only; data — **never leaves the machine unencrypted; restic only (Phase 3)**; projects — own remotes, mandated at creation. Local baseline copies (the T1 pattern, `C:\FableOS-Backups\`) cover the whole tree regardless of repo, because a cross-disk restore point has no privacy cost.
4. **Synchronization boundaries.** Nothing under `data\` synchronizes to any console or cloud service in readable form (ADR-026). Config and docs sync only via their git remotes. There is no file-sync layer (no OneDrive/Syncthing over the tree) — git and restic are the only movers.
5. **Housekeeping.** The pre-existing `landing\` web project relocates to `projects\landing\` at T5 (its correct home under the contract).

**Consequences.** The V1 one-liner "backup = copy this folder" is formally retired in favor of ADR-011's per-tier policy; local wholesale copies remain valid as *additional* protection. Frozen documents referencing root `memory\`/`journal\`/`vault\` stay frozen and historically accurate; GLOSSARY.md (Phase 2) carries the current map. Path references in future skills/jobs use the ADR-025 paths exclusively.

**Alternatives considered.** (1) *Sibling top-level directories (`D:\FableOS-docs`, `D:\FableOS-data`, …)* — rejected: shatters the single-folder mental model ("the system lives in D:\Fable OS") that the whole operator experience leans on. (2) *git submodules binding the four repos* — rejected: submodule ergonomics are a notorious non-programmer trap; plain nested-and-ignored repos need no coordination. (3) *One repo with git-crypt for personal paths* — rejected in ADR-011 already; partial encryption fails silently. (4) *Keeping `vault\` at root as a fifth repo* — rejected: a whole repo for one inventory file is ceremony; the inventory is config-tier by classification.

**Future review criteria.** Reopen if: (a) the system spans more than one machine with state (ADR-011's own trigger — the partition then needs a sync design); (b) any nested repo accidentally becomes visible to the parent (test suite checks this; a hit means the root `.gitignore` regressed); (c) a future phase needs a directory that fits no existing repo's classification — classify first (PRIVACY.md), then place; never place by convenience.
