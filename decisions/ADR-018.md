# ADR-018 — Supply-chain policy for MCP servers and skills: pinned, verified, never auto-updated
**2026-07-10 · Accepted** — from the [2026-07-10 architecture review](../reviews/2026-07-10-architecture-review.md) §4.2 / §6 R6; extends ADR-001 and ADR-013.

**Context.** The architecture defends *outbound actions* (the Outbox, ADR-012) and *inbound content* (trust tiers, ADR-013) but had no defense for **inbound code**: the MCP servers and skills themselves, each of which runs with real capabilities inside the trust boundary. 2026 supplied the warning shots: over a thousand malicious skills found in one agent-framework marketplace, hundreds of MCP servers exposed on the internet with no auth, a systematic academic study of injection via tool/skill ecosystems, and the LiteLLM PyPI compromise. OWASP's Agentic Top 10 (2026) ranks agentic supply chain as a first-class category. In a design whose motto is "everything is an MCP server," the plug standard is also the attack standard.

**Decision.** Every MCP server and skill adopted into the system is governed by:

1. **Provenance requirement.** Prefer first-party or foundation-governed servers (official registry entries, vendor-published, Linux Foundation projects). A random-repo server requires a recorded justification in COMPONENTS.md.
2. **Version pinning.** Every server and skill is pinned (version + hash where the packaging allows) and recorded in VERSIONS.md. **No auto-update, ever** — updates are deliberate acts at the quarterly checkup or in response to an advisory.
3. **Integrity verification** at install: hash or signature check against the pinned release. When the official MCP registry's signing and trust-scoring reaches GA, its verdicts become the default vetting input.
4. **Least scope.** Servers get only the credentials and filesystem scope their role requires (per ADR-009's READ/WRITE/SEND tagging); a server needing more than its role's contract is a selection error, not a configuration task.
5. **Canary gate on change.** The injection canary suite (ADR-013) runs after **any** MCP server or skill install or update — extending its trigger from "model/kernel change" to "any trust-boundary code change."

**Consequences.** The "config edit" of ADR-001 gains a checklist — adding a capability now costs minutes of vetting instead of seconds of pasting. That is the correct price: the red-team's C2 attack arrives more plausibly today as a trojaned MCP server than as a crafted email. Cost: pinned servers age between checkups; accepted, because a stale-but-verified server beats a fresh-but-unvetted one for this operator.

**Alternatives considered.** (1) *Trust the registry ecosystem implicitly* — rejected: registries index, they do not (yet) attest; the 2026 marketplace incidents happened inside registries. (2) *Sandbox every MCP server (per-server containers/VMs)* — rejected as baseline: violates ADR-006/014's substrate simplicity for a marginal gain over least-scope + pinning on a single-user machine; the ACTOR sandbox (ADR-020) already contains the highest-consequence path. (3) *Write all servers in-house* — rejected: violates Law 3 and forfeits the ecosystem that makes ADR-001 valuable.

**Future review criteria.** Reopen if: (a) the official registry's signing/trust-scoring GAs — fold it in as the default gate and simplify item 3; (b) a vetted, pinned server is nonetheless implicated in an incident — the policy's assumptions failed, escalate to per-server sandboxing (alternative 2) by superseding ADR; (c) OS-level per-agent/per-tool permission brokering (Windows agentic security roadmap) matures enough to enforce item 4 natively — adopt it and retire the hand-rolled scoping.
