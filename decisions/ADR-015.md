# ADR-015 — Graphify is an enhancing recall tier above the SQLite-FTS baseline, never a replacement for it
**2026-07-10 · Accepted** — ratifies [ARCHITECTURE-V2](../ARCHITECTURE-V2.md) §9/§12; extends ADR-004.

**Context.** The red-team review ([I13](../reviews/2026-07-09-red-team-review.md)) noted the operator already owns graphify — a knowledge-graph skill (any input → persistent graph with community detection, query/path/explain tools) — while the memory design reinvented a strictly weaker keyword index. Queries like *"what did we decide about X, and what depends on it"* are path-and-community questions FTS cannot serve. The 2026 memory-framework landscape (Zep/Graphiti's temporal knowledge graphs leading the benchmarks) independently confirms graph-shaped recall is where flat files + FTS fall short. Constraint: graphify is one person's skill, not maintained OSS — under Law 4 it may enhance a role, never solely fill one.

**Decision.** The recall role is two-tiered:

1. **Baseline (guaranteed):** SQLite FTS5 + sqlite-vec over `memory\` and `journal\`, local embeddings, rebuildable from the files at any time (ADR-004). This tier must always work alone.
2. **Graph tier (enhancing):** graphify builds (a) a graph over `data\memory\` + `journal\` answering decision-and-dependency queries by path and community; (b) a **decisions graph** linking laws ↔ ADRs ↔ components, making impact analysis ("what breaks if we drop ADR-002?") a traversal; (c) per-project graphs in `projects\<name>\graphify-out\` for codebase understanding.

Graph artifacts are rebuildable indexes under Law 1 — never sources of truth. If graphify is unavailable, recall falls back to FTS with degraded richness, never zero. The fallback is *tested* (delete graph output, run recall suite), not assumed. Graph nodes derived from quarantined memory inherit quarantine exclusion (ADR-013).

**Consequences.** The system gains the query shapes its own governance needs most (decision impact analysis) from a tool the operator already trusts. Cost: a bus-factor-one dependency deliberately confined to the enhancement tier; the insurance (FTS) must stay continuously exercised or it rots into the same fiction as V1's dormant successor kernel.

**Alternatives considered.** (1) *FTS only* — rejected: leaves the "what depends on X" query class permanently unserved. (2) *Adopting an OSS memory framework (Zep/Graphiti, Mem0, Letta)* — rejected for now: none is a standard (2026 has standardized benchmarks, not formats), each wants to own storage in violation of Law 1/5, and each is a heavier dependency than a skill over plain files; the strongest of them is named here as the successor if graphify is lost *and* graph recall has proven load-bearing. (3) *Graph database (Neo4j-class)* — rejected: a resident service holding derived data (Laws 1, 10).

**Future review criteria.** Reopen if: (a) the quarterly fallback test fails — the baseline has rotted; fix before touching the graph tier; (b) graphify goes unmaintained past two quarterly checkups — decide: adopt (vendor the skill into `fableos-docs` with documentation) or retire the tier; (c) an open standard for agent memory/knowledge-graph interchange actually emerges — re-evaluate both tiers against it; (d) memory exceeds ~1M documents or goes multi-machine (ADR-004's own reopen trigger).
