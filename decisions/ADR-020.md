# ADR-020 — The ACTOR context runs inside an OS-level sandbox: Windows Agent Workspace or a dedicated non-admin account
**2026-07-10 · Accepted** — from the [2026-07-10 architecture review](../reviews/2026-07-10-architecture-review.md) §5.1; amends the *mechanism* of ADR-009, not its structure.

**Context.** ADR-009's ACTOR context holds the system's dangerous tools (write, send, execute). V2 designed its containment by hand: MCP profiles, the egress allowlist, the Outbox gate. Since then the substrate itself grew the missing primitive: Windows 11 documents agentic security as an OS feature — agents running as distinct non-admin Windows accounts inside isolated "Agent Workspace" sessions, auditable and governable by the OS, off by default, folder-scoped by default. Law 10 says prefer the built-in mechanism; ADR-014 already makes Windows 11 the substrate. Hand-rolled isolation where the OS provides isolation is a clever moving part waiting to become a 3 a.m. failure.

**Decision.**

1. The ACTOR context (and any headless scheduled job that can reach WRITE/SEND tools via the Outbox processor) runs **under a dedicated non-admin Windows account**, using **Agent Workspace where available** — with filesystem scope limited to `D:\Fable OS\` and the specific directories its jobs require.
2. Agent Workspace is used **as a sandbox primitive only**. No JarvisOS component may depend on its APIs, session model, or configuration format beyond "the process runs inside it." It is a Microsoft preview feature; this system outlives previews. The fallback — a plain dedicated low-privilege account with NTFS ACLs — must remain sufficient on its own, and is the baseline the design assumes.
3. The READER context needs no OS sandbox beyond default user privileges — its containment is the absence of tools (ADR-009), which no OS feature replaces.
4. The watchdog verifies the ACTOR account's privilege level (non-admin, expected scope) as a standing check.

**Consequences.** A compromised or manipulated ACTOR is bounded by the operating system, not only by our own configuration — defense in depth where the blast radius is largest, at near-zero maintenance cost because the OS owns the mechanism. The Windows 11 migration (ADR-014) gains a second, positive justification. Cost: one-time account/scope setup in the Phase 2 install script, and occasional friction when a legitimate new job needs a scope extension (a visible, logged act — the correct default).

**Alternatives considered.** (1) *MCP-profile separation only (V2 as written)* — rejected as the ceiling: it remains the primary mechanism, but it lives in configuration the kernel itself reads; an OS boundary holds even if the configuration layer is subverted. (2) *Per-job VMs or containers* — rejected: ADR-006/014 substrate posture; disproportionate maintenance for a single-operator machine. (3) *Deep Agent Workspace integration (its policy APIs, its scheduling)* — rejected explicitly by item 2: coupling a 10-year system to a preview feature inverts the risk this ADR reduces.

**Future review criteria.** Reopen if: (a) Agent Workspace is discontinued or breaking-changed — the fallback account is already the baseline, so the response is deleting one install-script branch, and that must remain true; (b) Agent Workspace GAs with a stable policy surface — reconsider item 2's prohibition, by new ADR, if native policy would retire custom guard code; (c) the watchdog ever finds the ACTOR running with elevated privilege — incident, not review.
