# ADR-033 — Presence: an on-demand probe of honest signals, adopted early by operator directive
**2026-07-13 · Accepted** — Priority 4 of the JARVIS-feel directive. ADR-029 reserved Presence for Phase 7 "subject to its own ADR at adoption"; the operator's explicit resume directive of 2026-07-13 (decision-hierarchy rank 1) orders adoption now. This is that ADR. ADR-029's recorded constraints are honored in full, not relaxed.

**Context.** ADR-029 reserved Presence with three constraints already on the record: presence data is **T2** (ADR-013), it **never leaves the Brain** (ADR-026), and **camera sensing requires explicit operator consent**. The operator's directive names six candidate signals (tailnet, Bluetooth, phone proximity, webcam, keyboard, mouse) and orders: implement what can be validated today, scaffold the rest cleanly, no new framework, no event bus, no daemon.

Substrate findings (2026-07-13, on the Brain):
- **Keyboard/mouse idle** — `GetLastInputInfo` (Win32, stdlib ctypes): available, instant, exact. The strongest local presence signal.
- **Session lock** — `LogonUI.exe` running: available, boring.
- **Tailnet** — `tailscale status --json` enumerates both consoles (Tab S7+, Xiaomi 14) with online/last-seen. **Honesty requirement:** a phone online on the tailnet is *reachable*, not *nearby* — it proves connectivity anywhere on Earth. It is recorded as `phone_reachable`, never as proximity.
- **Bluetooth proximity** — pairing records exist, but live BLE presence scanning needs a real component (WinRT via **bleak**). Not validatable today → **scaffold**, disabled in config, bleak named for adoption.
- **Webcam** — device present, but ADR-029's consent constraint stands and no vision route exists behind the gateway yet → **scaffold**, disabled, requires an explicit consent flag *and* its own validation before any future enablement.

**Decision.**

1. **Presence is an on-demand probe, never a monitor** — the ADR-032 pattern exactly: `config\kernel\jarvis_presence.py` (Law 3 glue, ≤200 lines) runs only when invoked (CLI now; watchdog/morning-brief/kernel-via-MCP later, each invocation explicit). No polling loop, no resident process, no event bus (ADR-008/029).
2. **Implemented today (validatable now):** input idle seconds (`GetLastInputInfo`), session-lock state (`LogonUI` presence), tailnet console reachability (`tailscale status --json`; phone + tablet, online/last-seen). Each behind a consent toggle in `config\presence.yaml`.
3. **Verdict semantics, deliberately modest:** `present` (recent input, unlocked) · `idle` (no recent input) · `away` (locked, or idle beyond threshold). Thresholds are config knobs. Tailnet reachability is reported *alongside* the verdict as context, never folded into it (see honesty requirement).
4. **Scaffolded, disabled, named:** Bluetooth LE proximity (component at adoption: **bleak**; a future session validates and enables it by config + its own test), webcam presence (**hard-gated**: requires `webcam.consent: true` set by the operator's own hand *and* a vision-capable route; until then the stub reports "scaffolded"). Enabling either is a config change under this ADR — no new ADR needed — but each must arrive with its executable test.
5. **Privacy:** all output is T2 data written to `data\presence\last-presence.json` (+ `.md`), **overwritten every run** (single last reading, no history — the ADR-032 retention rule), gitignored, never leaves the Brain (ADR-026).
6. **Isolation:** own uv venv (`config\presence\.venv`, pyyaml only); deletion of script + config + venv leaves the Runtime untouched (Law 4).

**Consequences.** JARVIS can answer "is the operator here?" from honest, locally-validatable signals today, and the two speculative signals have clean, named landing spots instead of half-built code. Cost: no true radio-proximity until bleak is adopted; the verdict is console-centric by design. ADR-029's Phase-7 reservation is consumed by this ADR for the probe *form only* — serving presence through MCP remains future work under ADR-019's timeline.

**Alternatives considered.** (1) *A resident presence service updating state continuously* — rejected: the daemon ADR-008/029 forbid, and continuous location-grade tracking exceeds what any consumer needs; (2) *phone GPS / router ARP scanning for real proximity* — rejected: exports personal location data or requires network scanning beyond the Brain's boundary (ADR-026 spirit); BLE at adoption answers proximity with less exposure; (3) *webcam face-presence now* — rejected: violates ADR-029's consent constraint as a default and adds a vision dependency with no route to use it.

**Future review criteria.** Reopen if: (a) bleak (or a successor) is adopted for BLE — validate, enable, and record the component row (Law 4/8); (b) webcam consent is ever granted — the consent flag alone is insufficient: that enablement needs its own validation and a COMPONENTS row; (c) any consumer invokes the probe on a timer faster than the watchdog cadence — that is monitoring; remove it or supersede this ADR explicitly; (d) MCP unpauses (ADR-019) — wrap the probe as an L3 sensor server, same module.
