# ADR-029 — The JARVIS Runtime: identity and host-independence contract
**2026-07-11 · Accepted** — ratified by operator directive 2026-07-11; the final architectural decision before Phase 1. After this ADR, the architecture is frozen and future work concerns implementation only.

**Context.** The project was named "JarvisOS," but the system was never an operating system — the founding README already called it "an assembly of mature open-source components, wired together through open standards." A 2026-07-11 identity review sharpened the abstraction: the permanent thing being built is a portable **runtime**; the operating system underneath it is a replaceable host. The review also proposed new runtime machinery (an event bus and five first-class modules), which was evaluated against the Constitution and ADR record and found to conflict with both; the identity was accepted and the machinery rejected (see below).

**Decision.**

1. **The project remains JarvisOS. The product is the JARVIS Runtime.**
2. **The Runtime is not an executable, not a service, not a daemon.** It is the **architectural contract** formed by: the kernel role (ADR-003), memory (ADR-004/013/015/021), context conventions (the engine corpus), skills (ADR-023), the gateway seam (ADR-002/027), MCP (ADR-001/018/019), the file contracts (ADR-025), the ADR ledger itself (ADR-016), the security guards (ADR-009/012/013/020), and the operational rules (Constitution, MAINTENANCE, PROJECT_STATUS discipline).
3. **The Runtime is portable; the host OS is replaceable.** Windows today — and Linux or any future platform — are **Host Adapters** filling five substrate roles: scheduling (Task Scheduler → cron/systemd timers), secrets (Credential Manager → secret-service), installation (winget → apt/brew/nix), sandboxing (non-admin account / Agent Workspace → POSIX user), and scripting (PowerShell → shell). Porting the system means rewriting the adapter set and nothing else. The adapter enumeration in this paragraph is the port checklist.
4. **The hub principle is reaffirmed, not replaced:** everything connects to the Runtime; nothing connects directly to another subsystem. The Runtime's hub is the kernel plus the file tree — the journal is the event log; files are the coordination substrate (ADR-008, ARCHITECTURE.md §6).
5. **Nothing else changes.** No repository renamed, no file moved, no script modified, no roadmap restructuring. New documents use "JARVIS Runtime" for the product and "JarvisOS" for the project.

**Explicitly rejected**, with reasons on the record so these ideas do not return unexamined:

| Proposal | Rejected because |
|---|---|
| **Event Bus** | ADR-008 by name ("no message bus"); ARCHITECTURE.md §6 (no always-on custom services); Law 10 (a resident daemon is a 3 a.m. failure); and it flattens the trust boundaries ADR-009/013 enforce through tool possession per context — a pub/sub fabric reintroduces the confused-deputy path the READER/ACTOR split exists to kill. The hub it would provide already exists: the kernel and the file tree. |
| **Intent Engine** (as a module) | Law 3 (never build what exists): converting operator outcomes into tool execution is precisely what the agentic kernel over MCP is. Outcome-orientation is recorded in the kernel instructions file (Phase 1), not built as software. |
| **Planner Engine** (as a module) | Same grounds; planning is kernel cognition (AI_ORCHESTRATION_ENGINE §2). Reifying it as infrastructure repeats the agent-framework mistake the ecosystem already buried, and breaks ADR-003 by making the most-churning layer un-replaceable. |
| **Reasoner Engine** (as a module) | Same grounds; reasoning is the model behind the gateway seam (ADR-002/027). A bespoke reasoning pipeline is the hardest possible violation of ADR-003's kernel-as-commodity rule. |
| **Runtime Manager service** | Law 10: startup/shutdown/health/scheduling are already filled by the host scheduler role, the watchdog (V2 §7), and the kernel's own lifecycle. A custom lifecycle daemon duplicates boring, working parts. |
| **Session Manager service** | Law 5: session state (current project, conversation, objective, history) lives in files — `data\memory\`, `data\journal\`, PROJECT_STATUS.md, project PLAN/TASKS. A process that *holds* this state would be a sole-holder violation; the file contract gets the name "session state," not a process. |

**Presence.** Reserved as a **future capability only** — an L3 MCP-served sensor role (Bluetooth/phone/input/camera), recorded for **Phase 7** and subject to its own ADR at adoption, with constraints already known: presence data is T2 under ADR-013, never leaves the Brain under ADR-026, and camera sensing requires explicit operator consent. Not implemented, not designed further, by this ADR.

**Consequences.** The system's identity finally matches its construction: a portable contract over replaceable hosts. Cost: essentially zero — one status line, this document, and a vocabulary discipline going forward. The deepest claim of the identity review ("the user should never think about applications") requires no new infrastructure; it becomes true when Phase 1 ships, because that is what an agentic kernel over MCP already is.

**Alternatives considered.** (1) *Adopt the full proposal (bus + five modules)* — rejected per the table above; it contradicted Laws 3/5/10 and ADR-003/008/009/013 while adding months of work and standing services. (2) *Reject the proposal entirely* — rejected: the identity clarification is genuinely better than the incumbent wording, names the port checklist, and costs nothing. (3) *Rename the project, repos, and paths to match* — rejected: churn without value one day into the repos' lives; names of things on disk are implementation, and implementation is frozen against vocabulary fashion.

**Future review criteria.** Reopen if: (a) a host swap is actually attempted — item 3's adapter enumeration is the checklist, and any gap found there amends this ADR; (b) Presence is proposed for adoption — that is a new ADR against the constraints recorded here; (c) any future proposal reintroduces a rejected structure — it must overturn this ADR's reasons explicitly, not rediscover the idea; (d) the kernel role ever becomes genuinely incapable of outcome-to-execution conversion — the Intent Engine rejection rests on that capability existing, and its loss would be a real (if unlikely) trigger.
