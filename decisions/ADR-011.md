# ADR-011 — Privacy partition: four repositories by data classification; personal data never leaves the machine unencrypted
**2026-07-10 · Accepted** — ratifies [ARCHITECTURE-V2](../ARCHITECTURE-V2.md) §4/§12; amends the single-monorepo contract of ARCHITECTURE.md §4.

**Context.** The red-team review ([C3, I8, I9](../reviews/2026-07-09-red-team-review.md)) found the monorepo to be a privacy accident: journals will contain the operator's email contents and calendar; disaster recovery said "clone from GitHub"; therefore the operator's private life was scheduled for upload to a third party — while, in the other direction, no job ever ran `git push`, so the GitHub leg of DR silently didn't exist. Backup, privacy, and DR were designed in three documents and never reconciled. Offsite encrypted backup was "optional" for a machine holding someone's externalized memory.

**Decision.** `D:\Fable OS\` is partitioned into repositories by data classification:

| Repo | Contents | Remote policy |
|---|---|---|
| `fableos-docs` | Constitution, architecture, ADRs, FABLE, engines, install, tests, reviews | May push to GitHub (public or private) |
| `fableos-config` | `config\` (sans secrets), vault inventory, jobs, kernel instructions | Private remote only |
| `fableos-data` | `memory\`, `journal\` | **Never leaves the machine unencrypted; restic only** |
| `projects\<name>` | each project | Own remote, **mandated at creation** |

`fableos-data`'s only offsite path is **restic** (encrypted, deduplicated) to an external drive and optionally an untrusted cloud bucket — mandatory, scheduled, with a monthly automated restore-verify job. A pre-push guard blocks personal-tier data from any git remote. SQLite indexes are backed up via `.backup` (consistent snapshot), never live file copy.

**Consequences.** The C3 contradiction dissolves: what may leave the machine is decided by classification, not accident. "Backup = copy this folder" is retired in favor of *restic snapshot + docs/config push* — documented, drilled, and scheduled. Cost: four repos and restic are more setup than one folder; the phase install scripts, not the operator, must carry that burden, and PRIVACY.md must map every directory to its classification.

**Alternatives considered.** (1) *One monorepo, private remote* — rejected: still uploads memory/journals to a third party in plaintext, and one misconfigured visibility toggle is catastrophic. (2) *One monorepo, no remote, restic only* — rejected: loses cheap, versioned, browsable offsite for the docs that are genuinely safe to push. (3) *git-crypt/encrypted-git for the data repo* — rejected: key management burden on a non-programmer, and partial-encryption schemes fail silently; restic is boring and proven (Law 10; restic 0.19.x actively maintained as of July 2026).

**Future review criteria.** Reopen if: (a) the monthly restore-verify fails — incident; (b) the system ever spans more than one machine (the partition must then gain a sync design); (c) restic dies (COMPONENTS.md names its successor); (d) the operator's threat model changes (e.g. the cloud bucket provider is no longer acceptable even for encrypted blobs).
