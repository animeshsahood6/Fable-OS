# ADR-022 — Voice is a session-adapter seam beside the gateway, not behind it
**2026-07-10 · Accepted** — from the [2026-07-10 architecture review](../reviews/2026-07-10-architecture-review.md) §3.1 A9–A10 / §4.3; resolves red-team I11; documents an explicit exception to ADR-002's "one dialect" claim.

**Context.** ADR-002 promised every model interaction flows through one OpenAI-compatible endpoint. Realtime voice broke that promise while nobody was looking: speech-to-speech models (gpt-realtime-2.x, Gemini Live) are stateful WebRTC/WebSocket *sessions* with per-provider protocols and order-of-magnitude price spreads — they do not fit a chat-completions proxy. Separately, the red-team (I11) found Phase 4's voice loop had no viable component and violated Law 3's 200-line glue budget. The ecosystem has since supplied named parts: RealtimeSTT (VAD + streaming faster-whisper, Windows-native), Kokoro TTS (Apache-2.0) and piper1-gpl (the maintained Piper successor — the original rhasspy/piper was archived October 2025), and LocalAI's OpenAI-Realtime-compatible local pipeline proving the shape. Fully local speech-to-speech models exist (Qwen3-Omni-class) but exceed this machine's 12 GB VRAM at quality.

**Decision.**

1. **Voice is its own thin seam**: a session-adapter layer holding swappable stages — VAD → STT → (kernel/gateway for thinking) → TTS. The *thinking* still routes through the gateway (ADR-002 governs text); only the audio session lives in the adapter.
2. **Local baseline (Law 6):** RealtimeSTT (VAD + faster-whisper) for input; **Kokoro** (preferred: Apache license, active) or **piper1-gpl** for output. COMPONENTS.md's Piper row updates at Phase 4 install: chosen = Kokoro, replacement = piper1-gpl, per Law 4.
3. **Cloud realtime voice is an optional adapter** behind the same seam — added only if local latency proves inadequate in use, chosen then by current price/quality (the ~50× provider spread is exactly why this stays a config-level choice).
4. **Voice input is T3-adjacent content**: transcribed audio that did not come from the operator's own push-to-talk action (e.g. ambient capture, media) enters through the READER context per ADR-013. Push-to-talk operator speech is T0 — but the STT text is displayed/confirmed before any SEND-class action it triggers, because transcription errors are an unsigned instruction channel.
5. The adapter glue is held to Law 3's budget by *assembling* the named components, not reimplementing them; if assembly exceeds ~200 lines, adopt LocalAI's realtime pipeline as the component instead.

**Consequences.** Phase 4 becomes an assembly of maintained parts instead of a Law-3 violation; provider churn and price chaos in realtime voice stay contained in one adapter; the gateway abstraction stays honest by declaring its boundary instead of silently breaking. Cost: one more seam to document, and end-to-end speech-to-speech quality (single-model fluidity) is deliberately forgone until local hardware/models allow it.

**Alternatives considered.** (1) *Extend the gateway to proxy realtime sessions* — rejected: LiteLLM-class proxies don't own this well, it fattens the most security-critical component (ADR-017), and it launders a genuinely different interaction shape through an abstraction built for another one. (2) *Cloud realtime as the primary voice path* — rejected: violates Law 6, and voice is the modality the operator will use most casually — it must work offline. (3) *Wait for local speech-to-speech models* — rejected: indefinite delay for a capability the pipeline pattern delivers now; the seam means the pipeline can be *replaced* by such a model later without touching anything else.

**Future review criteria.** Reopen if: (a) a local speech-to-speech model fits 12 GB VRAM at usable quality — swap the pipeline stages for it behind the same seam; (b) measured push-to-talk round-trip exceeds ~2 s sustained — activate the cloud adapter (item 3); (c) Kokoro or piper1-gpl goes unmaintained (quarterly pulse) — Law 4 succession; (d) an open realtime-session standard emerges across providers — reconsider whether the adapter can thin to a config.
