# ADR-019 — MCP spec versioning: Phase 2 targets the 2026-07-28 spec; stdio locally; no deprecated features
**2026-07-10 · Accepted** — from the [2026-07-10 architecture review](../reviews/2026-07-10-architecture-review.md) §6 R2; extends ADR-001.

**Context.** MCP won — Linux Foundation governance (December 2025), adoption by every frontier vendor, native Windows 11 support — which converts the risk from "wrong standard" to "unmanaged standard motion." The 2025-11-25 spec was the largest release since launch (tasks, extensions, URL-mode elicitation, OAuth hardening); a breaking-flavored **2026-07-28 revision** is in release candidate eighteen days after this review: stateless protocol core (sessions and the initialize handshake removed), tasks moved to an official extension, MCP Apps, and **sampling and logging deprecated** with a 12-month removal clock. The red-team (I10) separately established that MCP *client* configuration formats differ per kernel — the spec version is one more thing that silently drifts unless pinned.

**Decision.**

1. **Phase 2 builds against the 2026-07-28 spec** (final by the time Phase 2 starts), using tier-1 SDKs only. No MCP glue is written against the release candidate.
2. **stdio is the transport for local servers** — the correct fit for a single-machine system; streamable HTTP only for genuinely remote servers, which also puts them behind the egress allowlist (ADR-013).
3. **No component may depend on deprecated protocol features** — today that means sampling and logging. Anything currently assuming MCP sampling migrates its pattern now, before it ships, not against the removal clock.
4. **The spec version is pinned in `config\mcp.json`** and validated by config lint (Missing Test #6 from the red-team review) before any kernel restart. Spec upgrades are deliberate, quarterly-checkup-sized events with the canary suite (ADR-018 item 5) as their gate.
5. **Long-running work standardizes on the Tasks extension** rather than bespoke job-status plumbing, where the kernel supports it.

**Consequences.** The system rides the standard's mainstream instead of its edges: stateless core, official extensions, first-party SDKs. Timing works in our favor — Phases 0–1 touch no MCP, so the transition is absorbed before it can break anything. Cost: waiting for the final spec means Phase 2 cannot start early; accepted, since Phase 0–1 have months of work regardless.

**Alternatives considered.** (1) *Build Phase 2 against 2025-11-25 now, migrate later* — rejected: shipping onto a spec with a public expiry when the successor lands before we start is manufacturing migration work. (2) *Track the spec continuously (always-latest)* — rejected: unmanaged motion is the risk being decided against; pin-and-upgrade-deliberately is the whole system's update posture (Law 10, ADR-018). (3) *Wrap MCP behind an in-house abstraction layer* — rejected: ADR-001 already made MCP servers thin wrappers over durable tools; a wrapper around the wrapper is insulation nobody maintains.

**Future review criteria.** Reopen if: (a) the 12-month deprecation clock fires and any dependency on sampling/logging remains — that is a missed gate, treat as incident; (b) a subsequent spec revision breaks stdio or the extension model — re-evaluate transport and Tasks choices; (c) MCP is ever genuinely superseded — ADR-001's own mitigation stands (regenerate thin wrappers; tools and data untouched), and this ADR is superseded with it.
