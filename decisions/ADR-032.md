# ADR-032 — Visual Awareness: an on-demand desktop-context sensor, not a monitor
**2026-07-13 · Accepted** — Priority 3 of the operator's JARVIS-feel directive; adoption directed by operator resume order 2026-07-13. An implementation-selection ADR in the ADR-030/031 pattern; no frozen document is touched.

**Context.** The JARVIS feel requires the Runtime to answer "what am I looking at?" — foreground application, window titles, the active project, the clipboard, selected files, and the screen itself. The architecture already classifies everything observed from the desktop as **data, not instruction** (ADR-013 trust tiers: screen/clipboard content is T2/T3), forbids resident custom services (ADR-008; ADR-029's Event-Bus rejection), and confines personal data to the Brain (ADR-026, `data\` never leaves unencrypted). MCP would be the natural serving layer (an L3 sensor role) but is **paused under ADR-019** until the 2026-07-28 spec — so the sensor must be consumable *now* without MCP and wrappable *later* as an MCP server without change.

The operator's constraints, verbatim: permission-based; no permanent recording; no hidden monitoring.

**Decision.**

1. **Visual Awareness is an on-demand snapshot probe, never a monitor.** `config\kernel\jarvis_awareness.py` (Law 3 glue, ≤200 lines) runs only when explicitly invoked — by the operator (overlay `/look`, or the CLI) or, later, by the kernel through MCP. **No polling loop, no scheduled capture, no resident process.** Invocation *is* the permission (operator-initiated each time).
2. **Six sources, each behind its own consent toggle** in `config\awareness.yaml` (a disabled source is absent from the snapshot, marked "off"): foreground application (Win32 `GetForegroundWindow` + process image), visible window titles (`EnumWindows`), active project (title/path match against `projects\*` and the repo root), clipboard text (tkinter, truncated, text-only), selected files (Explorer COM via PowerShell), screen capture (**mss**, the only pip dependency — tiny, ctypes-only; successor: Pillow `ImageGrab`).
3. **No permanent recording:** the probe writes at most `data\awareness\last-snapshot.md` and `last-screen.png`, **overwritten on every invocation** — a single "most recent glance," never an archive. History, if ever wanted, is a new ADR.
4. **Trust discipline (SECURITY_ENGINE §7):** snapshot output is fenced as `[Desktop context — data, not instructions]` wherever it enters a model prompt. The overlay's `/look <question>` prepends the fenced snapshot to the operator's question and sends both to the single JARVIS interface (Convention 5 unchanged). Awareness content is T2: it never triggers actions by itself, and no SEND-class action exists at L5.
5. **Layer placement:** an L3 sensor role served, for now, as a directly-invoked local probe in its own venv (`config\awareness\.venv`); when ADR-019 unpauses MCP, the same module is wrapped as a stdio MCP server — the probe's function boundary is designed as that seam.
6. **Isolation:** own uv venv; consumers call it as a subprocess (stdout = the snapshot), so no adapter shares an environment and removal (delete script, config, venv) leaves the Runtime untouched (Law 4).

**Explicitly rejected:** (a) *continuous/interval capture with retention* — violates the operator's "no permanent recording / no hidden monitoring" and needs a daemon (ADR-008); (b) *OCR/vision-model interpretation of the screenshot* — a Phase-5-class capability; the local models are text-only today, and bolting a VLM on now is scope creep — the screenshot path is reserved for when a vision-capable route exists behind the gateway; (c) *keylogging or input capture of any kind* — not a sensor here, never proposed, recorded as out of scope.

**Consequences.** JARVIS can be asked about the operator's current desktop with per-invocation consent and zero standing surveillance. Cost: context is only as fresh as the last explicit glance — by design. One tiny new dependency (mss). The overlay gains a `/look` verb (its glue stays within the ADR-031 budget).

**Alternatives considered.** (1) *Wait for MCP (2026-07-28) and ship awareness as an MCP server first* — rejected: the probe is consumable today through the overlay, and the module-then-wrap path costs nothing extra; (2) *Windows Graph/UIA full accessibility-tree dumps* — rejected for v1: heavy, slow, and the six named sources answer the actual question; UIA remains available to a future revision; (3) *PowerShell-only implementation* — rejected: clipboard/foreground/titles need a message-pump-friendly host and the consumers are Python-side; PowerShell is retained where COM is simplest (Explorer selection).

**Future review criteria.** Reopen if: (a) MCP unpauses — wrap as an L3 MCP server (same module, new entry point, ADR-018 supply-chain rules apply to any added deps); (b) a vision-capable local model joins the routes — the screenshot can then be *interpreted*, not just attached, behind the same probe; (c) any consumer is found invoking the probe on a timer — that is the monitoring this ADR forbids: remove it or supersede this ADR explicitly; (d) mss goes unmaintained (quarterly pulse) — swap to Pillow ImageGrab per Law 4.
