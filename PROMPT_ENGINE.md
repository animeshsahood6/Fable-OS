# 1. Prompt Philosophy

**1.1 — What a prompt really is.** A prompt is *an instruction to an intelligence* — the specification of desired behavior directed at an AI whose internal workings you don't control and whose output is nondeterministic (§1.2). It is not code (code determines behavior; a prompt *requests* it from a probabilistic system TE §6.1) and not mere text (it's a *functional artifact* — it *does* something: it shapes behavior). A prompt sits at the boundary between *intent* (what a human or system wants) and *behavior* (what the AI does), and its job is to make that translation faithful (§4 — the intent realized as the behavior) despite the intelligence being stochastic (§1.2), manipulable (SE §6.4), and replaceable (§8). Prompt engineering is the discipline of writing that instruction so the translation is reliable.

**1.2 — Prompt as interface.** The foundational framing (RE §30): a prompt is an *interface* (AE §4) — a contract between the caller (intent) and the implementation (the AI's behavior), with a nondeterministic implementation (TE §6.1 — the same prompt may produce varying behavior). Treating a prompt as an interface (AE §4) imports the whole interface discipline: it has *inputs* (the context CX, the task), *outputs* (the behavior/result, §4.4 specified), *a contract* (§1.4 — what it promises), and it *hides its implementation* (you specify the behavior, not how the model produces it — AE §4.1). The discipline (RE §30, AE §4): design prompts as interfaces — from the *caller's need* (§4.1 intent), specifying *behavior* (§4.4 output contract) not internal model mechanics, with the nondeterminism (§1.2) managed by robustness (§6.4) and containment (§6.5), the way any interface manages an unreliable implementation (AE §8).

**1.3 — Prompt as specification.** A prompt *specifies* the desired behavior (§4.4) — it is the behavioral spec (AE §4.3 contract) the AI implements. As a specification, a prompt must be *complete* (§4 — everything the behavior requires: intent §4.1, constraints §4.2, output §4.4), *unambiguous* (§4.6 — one interpretation, or the nondeterministic implementation §1.2 varies on the ambiguity), and *total* (AE §4.3 — defined behavior for the edge inputs §6.3, not just the happy path). The discipline (§4): write prompts as specifications — precise about what behavior is wanted (§4.4), complete about what the behavior needs (§4), and explicit about the edges (§6.3), because an under-specified prompt (§9.7) leaves the nondeterministic implementation (§1.2) to fill the gaps, and it fills them variably and sometimes wrongly.

**1.4 — Prompt as contract.** A prompt is a *contract* (AE §4.3, §4.7) — it promises certain behavior for certain inputs, and (when it has "callers" — the systems/agents that depend on it) that promise is relied upon (§5.6 — a reusable prompt's behavior is depended on). As a contract, a prompt has *obligations* (the behavior it must produce), *guarantees* (what callers can rely on), and *stability* (AE §4.7 — a prompt with dependents can't change its contract freely; changing it is a versioned change §2.7). The discipline (AE §4.7, §2.7): a prompt-with-dependents is a frozen-ish contract (its behavior is relied upon), so it evolves by addition/versioning (§2.7, AE §4.7 — not silent behavior change §9.4, which breaks the dependents relying on the old behavior).

**1.5 — Prompt as architecture.** At scale, prompts are *architecture* (AE) — a system of prompts (§3 — system, role, tool, task prompts) with structure, boundaries, and composition (§5). The prompt architecture (§3) determines how instruction flows through an AI system (the system prompt §3.1 setting the frame, the role prompts §3.4 specializing, the task prompts §3.7 directing) — and it's designed (AE) with seams (AE §1.1 — composable §5, modular §5.2), so prompts can evolve independently (§5.2 — a role prompt changed without rewriting the system prompt). The discipline (AE, §5): the prompt system is architected — layered (§5.1), modular (§5.2), composable (§5.4) — so it's maintainable (§2.6) and evolvable (§2.7) over the system's life, not a monolithic instruction that can't be changed safely.

**1.6 — Prompt vs instructions.** An *instruction* is a single directive ("do X"); a *prompt* is the complete instruction-set that produces the desired behavior (the intent §4.1, the constraints §4.2, the context CX, the output contract §4.4, together). A prompt is composed *of* instructions (§4 — the intent-instruction, the constraint-instructions, the output-instruction) but is more than their sum — it's the *coherent whole* that a mind reasons from (§1.2 interface). The discipline: write the *prompt* (the complete behavioral spec §1.3), not scattered instructions — a prompt whose instructions don't cohere (§9 — contradictory, incomplete) produces incoherent behavior, however individually-sound the instructions.

**1.7 — Prompt vs requirements.** *Requirements* are what the behavior must achieve (the intent, in the requester's terms — RE §3); a *prompt* is the instruction that produces behavior meeting them (translated into instruction the AI acts on). A prompt is *derived from* requirements (§4.1 — intent extraction turns requirements into the prompt's intent-specification) but is not the requirements (it's the *instruction* realizing them). The discipline (§4.1, RE §3): extract the real requirement (RE §3 — the intent behind the request FABLE §1), then design the prompt to produce behavior meeting it (§4) — a prompt written from a misunderstood requirement (RE §3 — the stated not the real) produces behavior meeting the wrong requirement, however well-written.

**1.8 — Prompt vs implementation.** A prompt *specifies* behavior (§1.3); it is not the *implementation* of that behavior (the model produces the behavior; the prompt requests it §1.1). This distinction (AE §4.1 — interface vs implementation) means: the prompt says *what* (the behavior wanted §4.4), the model does the *how* (produces it), and the prompt should not over-specify the how (§9.6 over-specification — dictating internal steps the model should determine, which brittles the prompt §9.10 and fights the model's capability). The discipline (§9.6, AE §4.1): specify the *what* (the behavior, the output contract §4.4, the constraints §4.2), leave the *how* to the model (its capability produces the behavior), unless the *how* is itself part of the requirement (a required method, a mandated process SE §4.9) — because over-specifying the how (§9.6) makes the prompt brittle (§9.10 — coupled to a specific approach) and wastes the model's capability (dictating what it could determine better).

# 2. Prompt Lifecycle

How a prompt moves from conception to retirement — treating prompts as engineering artifacts with a full lifecycle (RE §30 — version prompts, test them). The governing principle: **a prompt is engineered, not improvised — conceived from a real need, drafted, refined, validated, deployed, maintained, versioned, and retired — because a prompt that drives real behavior (especially a reusable §5.6 or autonomous SE §7.10 one) is production software (§1.1 functional artifact), and improvised prompts fail in production the way improvised code does.**

**2.1 — Prompt conception.** A prompt is conceived from a *real need* — a behavior the system requires (a task to delegate OE §9, a capability to instruct §3, a job to run OE §7). Conception (§4.1): identify the need (the behavior wanted), the intent behind it (RE §3, §1.7 — the real requirement), and whether a prompt is the right instrument (§10.1 — prompt vs tool vs workflow vs skill). The discipline (§10.1): conceive a prompt when *instruction to an intelligence* is what's needed (§1.1 — a behavior best produced by an AI reasoning §1.2), not when a deterministic tool (§10.1 — a fixed operation), a workflow (§10.2 — orchestrated steps OE), or a skill (§10.3 — a reusable capability) fits better. A prompt conceived where a tool would do (§10.1) is nondeterminism (§1.2) applied to what should be deterministic.

**2.2 — Prompt drafting.** The first construction (§4) — assembling the prompt's components (intent §4.1, constraints §4.2, context CX, output contract §4.4) into a coherent whole (§1.6). Drafting is *construction* (§4) — the disciplined assembly of the behavioral spec (§1.3). The discipline (§4): draft for minimal-sufficiency (§4.7 — everything the behavior needs, nothing it doesn't, like context CX §4.9), explicitly (RE §30 — say what to do §4, unambiguously §4.6), from the caller's intent (§4.1) — a first draft that's complete (§1.3) and coherent (§1.6), to be refined (§2.3) and validated (§2.4).

**2.3 — Prompt refinement.** Improving the draft (§2.2) — tightening ambiguity (§4.6), adding missing constraints (§4.2, §9.2), removing excess (§9.1 verbose, §9.6 over-specified), sharpening the output contract (§4.4). Refinement is *iterative* (§2.4 — refined against validation §6, tested TE §6.2 on real inputs RE §30). The discipline (§6, RE §30): refine against *behavior* — test the prompt (§6.2, TE §6.2) on real and edge (§6.3) inputs, observe the behavior [M2], and refine where it's wrong (ambiguity §4.6 the model interpreted variably, missing constraint §9.2 it violated, over-specification §9.6 that brittled it) — refinement driven by observed behavior (§6), not by how the prompt reads (§9 — a prompt that reads well can behave badly TE §6.1).

**2.4 — Prompt validation.** Verifying the prompt produces the right behavior (§6, TE §6.2) — reliably (§6.4 robustness, across inputs and the nondeterminism §1.2), at the edges (§6.3), against adversarial input (§6.5 injection). Validation is *testing the prompt like code* (RE §30, TE §6.2 — reproduce, exercise on real inputs, observe behavior). The discipline (§6, TE §6.2): validate by *exercising* — run the prompt on representative and edge (§6.3) inputs, multiple times (§6.4 — the nondeterminism §1.2 means one success isn't validation, TE §6.1), and confirm the behavior is right (§6 — meets the intent §4.1, respects constraints §4.2, produces the output §4.4) reliably enough (§6.4). A prompt deployed without validation (§6) is a behavior deployed untested (TE §1.3 — false confidence).

**2.5 — Prompt deployment.** Putting the validated prompt into use (§2.4 — driving real behavior). Deployment is where the prompt becomes production (§1.1 — driving real behavior, with real consequences). The discipline (§6.4, SE §7.10): deploy with the robustness (§6.4) and containment (§6.5, SE §7.2 — injection resistance; SE §7.10 — autonomous containment) the stakes require — a prompt driving high-stakes/autonomous behavior (SE §7.10) is deployed with the guardrails (SE §7.11 — human gates for irreversible action) its blast radius (SE §2.6) demands, because a deployed prompt's failures (§6.1) happen in production (TE §3.10).

**2.6 — Prompt maintenance.** Keeping the prompt working over its life (§2.7 versioning, §9.4 anti-drift). Prompts need maintenance because: the models change (§8 — a prompt tuned to one model §8.8 may behave differently on another, so model replacement §8 requires re-validation §2.4, TE §6.9); the task/requirements evolve (§2.7 — the prompt updated to match); and prompts drift (§9.4 — accumulating edits that degrade coherence §1.6). The discipline (§2.7, §9.4): maintain prompts as code (BE §4.9 — version-controlled §2.7, tested on change §6.7 regression, kept coherent §1.6) — because an unmaintained prompt decays (§9.4 drift, §8 model-mismatch) into behavior that no longer matches its intent (§4.1).

**2.7 — Prompt versioning.** Tracking a prompt's changes over time (RE §30, AE §4.7). Versioning matters because: a prompt change is a *behavior* change (§1.1 — so it's tracked, revertable SE §10.8-like if it regresses §6.7), a prompt-with-dependents (§1.4) has a contract (AE §4.7 — versioned so dependents aren't broken by silent change §9.4), and prompt regressions (§6.7) need a known-good version to revert to. The discipline (RE §30, AE §4.7): version prompts (version-controlled, changes recorded with their why BE §4 — like code) — so a prompt's evolution is tracked (§2.6), a regression (§6.7) is revertable, and a contract change (§1.4) is a deliberate versioned change (AE §4.7), not a silent behavior shift (§9.4).

**2.8 — Prompt retirement.** Removing a prompt no longer needed (its behavior no longer wanted, superseded by a better prompt §5, or the need gone). Retirement is *deliberate* (§9 — a stale prompt still deployed drives outdated behavior). The discipline (§2.6, §9.4): retire prompts whose need is gone (removed cleanly BE §4.7 — not left to drive behavior nobody wants), and supersede prompts replaced by better ones (§2.7 — the new version §2.7, the old retired), keeping the deployed prompt-set current (§2.6 — only prompts whose behavior is still wanted, so the system's behavior matches its current intent §4.1).

# 3. Prompt Architecture

The kinds of prompts and how they compose into a system (§1.5 — prompts as architecture). The governing principle: **prompts are layered by scope and function — system prompts set the enduring frame, role prompts specialize, task prompts direct the immediate work, tool prompts interface capabilities — so instruction flows coherently from the stable frame (rarely changed) to the specific task (changed constantly), and each layer is designed, bounded, and evolvable (§5) independently.**

**3.1 — System prompts.** The foundational, enduring instruction that sets the frame for all behavior (the AI's standing identity, principles, constraints — for JarvisOS, the kernel-instructions OE §7, the Constitution's laws embodied as instruction). System prompts are the *slowest-changing* layer (§5.1 — the stable frame, like the architecture AE that rarely changes), the *most load-bearing* (§7.1-like — everything is built on it), and the *most carefully designed* (§4 — an error here affects all behavior). The discipline (OE §7, §1.5): the system prompt is architected (§1.5) — it sets the enduring frame (the identity, the standing constraints §4.2, the principles, the safety rules SE §7), stable (§5.1 — rarely changed, versioned §2.7 when it is), and it's the single most important prompt in the system (the red-team flagged its absence — the kernel's own instruction OE §7 is the system prompt of the whole system, and it must exist and be excellent).

**3.2 — Developer prompts.** Instruction from the system's builders/operators that configures behavior below the system-prompt frame (§3.1) but above the user's immediate request (§3.3) — the standing configuration of how the system should behave for this deployment/operator. Developer prompts specialize the system frame (§3.1) for the specific deployment (the operator's preferences ME §3.6 embodied as instruction, the deployment's standing configuration). The discipline (§5.1): developer prompts layer over the system prompt (§3.1 — specializing it) without contradicting it (§9 — a developer prompt fighting the system prompt produces incoherent behavior §1.6), configuring the standing behavior for this deployment.

**3.3 — User prompts.** The immediate request from the human (the task, the question, the instruction the user gives now). User prompts are the *most transient* layer (§3.7-like — the immediate work, changing constantly) and the *least controlled* (the user writes them, so they're variable, possibly ambiguous §4.6, possibly containing injection SE §6.4 if the user relays untrusted content). The discipline (§4.1, RE §3): the system extracts intent (§4.1, RE §3) from the user prompt (which may be ambiguous §4.6 or incomplete §9.7 — the user isn't a prompt engineer FABLE §12), clarifying where needed (FABLE §12 — asking what only the user can answer), and treating relayed untrusted content in the user prompt as untrusted (SE §6.4 — a user pasting a web page is relaying untrusted content).

**3.4 — Role prompts.** Instruction that specializes a mind for a *role* (OE §7 — the reader, actor, verifier, critic; the researcher, builder, reviewer). Role prompts (OE §7) configure an agent's behavior for its function (the critic prompted to refute RE §9.5, the reader prompted to read-not-act SE §7.2, the verifier prompted to check independently OE §8). The discipline (OE §7, §5.2): role prompts are modular (§5.2 — a reusable specialization per role), composed with the task (§3.7 — the role prompt + the specific task) — so an agent is instructed by its role (§3.4) and its task (§3.7), and the role prompts are a reusable library (§5.3 — the standard roles OE §7, prompted once, reused).

**3.5 — Tool prompts.** Instruction about *tools* — how/when to use a capability (the tool's description, its usage guidance, in an MCP context AE §9.10). Tool prompts (the tool descriptions an agent reads to know what a tool does and when to use it) are an interface (§1.2 — between the agent and the capability). The discipline (§4.4, AE §9.10): tool prompts specify clearly *what the tool does, when to use it, and its contract* (AE §4.3 — inputs, outputs, effects) — so the agent uses it correctly (a vague tool prompt produces misuse §9.7), scoped and capability-tagged (SE §7.6 — the tool prompt reflects its trust tier AE §9.6, so the agent/architecture knows read vs act).

**3.6 — Planning prompts.** Instruction for *planning* work (PE — decompose, sequence, plan). Planning prompts (PE, embodied as instruction) direct a mind to produce a plan (PE Stage 0–9 — frame, decompose, sequence, risk-order). The discipline (PE, §4.4): planning prompts specify the *planning output* (§4.4 — a plan with the properties PE §11.2 requires: decomposed §PE 3, risk-ordered §PE 5, falsifiable exit tests §PE 5.5) — so the produced plan is a *good* plan (PE), not just any plan.

**3.7 — Execution prompts.** Instruction for *doing* the work (BE — build, execute). Execution prompts direct a mind to execute (BE — the task, with its context CX, constraints §4.2, done-when §4.4). Execution prompts are the most task-specific (§3.3-adjacent — the immediate work), composed from role (§3.4) + task. The discipline (§4, BE): execution prompts are the cold-brief (FABLE §29, OE §9, §7.2 — self-contained: goal, inputs, constraints, done-when, output) for the executing mind — complete (§4.7) because the executor shares no other context (CX §8.4).

**3.8 — Review prompts.** Instruction for *reviewing/judging* work (CR — review for fitness). Review prompts (CR, embodied) direct a mind to judge (CR §4–§8 — correctness, architecture, security §6, etc.), independently (OE §8.1 — a different context than produced the work), often adversarially (§6.5, RE §9.5, CR §9 — prompted to find what's wrong, not confirm). The discipline (CR, OE §8): review prompts specify the *review dimensions* (CR §4–§8 — what to check) and the *stance* (OE §8.2 — refute, find the failure §6.5), so the review is rigorous (CR — hunts for defects) not confirmatory (CR §10.3).

**3.9 — Recovery prompts.** Instruction for *recovering* from failure (DBG — debug; FABLE §27 — recover; SE §10.6 — incident response). Recovery prompts direct a mind to handle a failure (DBG §2 — reproduce, root-cause; FABLE §27 — stabilize first; SE §10.6 — contain, eradicate, recover). The discipline (DBG, FABLE §27, SE §10.6): recovery prompts embody the recovery discipline (stabilize-first FABLE §27.1, root-cause-not-crash-site DBG §5, contain-before-diagnose SE §10.6) — so the recovering mind follows the disciplined recovery (DBG, SE §10) under the pressure (FABLE §27) that tempts shortcuts.

# 4. Prompt Construction

Building a prompt that produces the right behavior — the core craft, analogous to context construction (CX §4) but for *instruction* rather than *information*. The governing principle: **construct the minimal sufficient prompt — the complete, unambiguous specification of the wanted behavior, and nothing more — because a prompt missing what the behavior needs (§9.7 under-specification) leaves the nondeterministic model (§1.2) to fill gaps variably, while a prompt over-specifying (§9.6) brittles the behavior and fights the model's capability, so the sufficient minimum is where reliable behavior lives.**

**4.1 — Intent extraction.** Extracting the *real intent* the prompt must serve (§1.7, RE §3, FABLE §1). Intent extraction turns the need (§2.1) into the prompt's core specification — *what behavior is actually wanted* (RE §3 — the real requirement, not the stated FABLE §1, not the literal request FABLE §32.1). The discipline (RE §3, FABLE §1): extract the intent (the behavior that serves the real need FABLE §1) before constructing — a prompt built on the wrong intent (§1.7 — the stated not the real) produces the wrong behavior (RE §3), however well-constructed. The intent is the prompt's goal (CX §4.6 — always present, the behavior aimed at).

**4.2 — Constraint extraction.** Extracting the *constraints* the behavior must respect (CX §4.5 — the invariants AE §2.6, security SE, operator constraints ME §3.6, the rules the behavior mustn't violate). Constraint extraction ensures the prompt tells the mind what it must *not* do / must respect (§9.2 missing-constraints — a prompt without its constraints produces behavior that violates them, because the mind wasn't told). The discipline (CX §4.5, §9.2): include the load-bearing constraints (the ones this behavior could violate — safety SE §7, the invariants AE §2.6, the operator's limits ME §3.6), stated clearly (RE §30 — the constraint the model must respect), because a missing constraint (§9.2) is behavior that breaks a rule the prompt didn't state.

**4.3 — Context construction (for the prompt).** Constructing the context (CX §4) the prompt's behavior needs — the prompt directs behavior *over* a context (CX §1.2), so the prompt's effectiveness depends on the context being right (CX §4.9 — minimal sufficient). Prompt construction and context construction (CX §4) are paired — the prompt says what to do, the context provides what to do it with. The discipline (CX §4): construct the prompt's context (CX §4 — minimal sufficient CX §4.9, the knowledge ME the behavior needs) alongside the prompt's instruction (§4.1, §4.2, §4.4) — because a perfect prompt over an inadequate context (CX §9.2 starvation) produces behavior starved of what it needed (CX §9.2), and a prompt over a flooded context (CX §9.1) produces degraded behavior (CX §9.1).

**4.4 — Output specification.** Specifying the *output/behavior* the prompt must produce (§1.3 — the behavioral spec; AE §4.3 — the output contract). Output specification (RE §30 — specify the output format) tells the mind exactly *what to produce* — the form (a list, a decision, a structured result), the content (what it must contain), the criteria (what makes it correct, the done-when BE §7.7). The discipline (RE §30, §4.4): specify the output precisely — the form and content the behavior must produce (§4.4 — "return the list of changed files and the failing tests" OE §8.2 beats "look into it"), so the produced behavior is *usable* (§5.7 — feeds the next step, the composition §5) and *checkable* (§6 — against the specification §4.4). A vague output specification (§9.7) produces variable, unusable output (§1.2 — the nondeterminism §1.2 filling the unspecified output variably).

**4.5 — Failure prevention.** Constructing the prompt to *prevent* its failure modes (§6.1, §9). Failure prevention (§6.1 — how prompts fail) builds in the defenses: against ambiguity (§4.6 — eliminated, so the model doesn't interpret variably §1.2), against constraint violation (§4.2 — the constraints stated §9.2), against injection (§6.5, SE §6.4 — the structural defense AE §9.6, not detection), against drift (§9.4 — the goal §4.1 present CX §4.6). The discipline (§9, §6): construct against the known failure modes (§9 — the anti-patterns) — a prompt built anticipating its failures (§6.1) is robust (§6.4); a prompt built only for the happy path (§9.7-adjacent) fails at the edges (§6.3) and under attack (§6.5).

**4.6 — Ambiguity elimination.** Removing interpretations the prompt didn't intend (§1.3 — unambiguous specification). Ambiguity is the enemy of reliable behavior (§1.2 — the nondeterministic model interprets ambiguity variably, so an ambiguous prompt produces variable behavior). The discipline (RE §30, §1.3): eliminate ambiguity — state precisely what's meant (RE §30 — explicit beats implicit), define terms that could be read multiple ways, give an example (§5.5, RE §30 — a worked example disambiguates more than paragraphs) where the rule is subtle. Ambiguity elimination is what converts a prompt from "the model usually does what I meant" to "the model reliably does what I specified" (§6.4 robustness — much of a prompt's unreliability §1.2 is ambiguity the model resolves variably).

**4.7 — Minimal sufficient prompting.** The construction target (analogous to CX §4.9): the *smallest* prompt that is *sufficient* to produce the wanted behavior reliably — everything the behavior needs (§4.1 intent, §4.2 constraints, §4.4 output, the context §4.3), nothing it doesn't (§9.1 verbose, §9.6 over-specified). Minimal-sufficient is the sweet spot (§9.7 under-specification below it — the model fills gaps variably §1.2; §9.6 over-specification above it — brittle, fighting the model's capability §1.8). The discipline (§9.1, §9.6): construct minimal-sufficiently — complete (§1.3 — the behavior's full needs §4.1/§4.2/§4.4) but not bloated (§9.1 — verbose prompts bury the load-bearing instruction RE §30 and waste context CX §5.10), specifying the *what* not over-specifying the *how* (§1.8, §9.6). Minimal sufficient prompting produces reliable behavior (sufficient) without brittleness (minimal, not over-specified §9.6).

**4.8 — Deterministic prompt design.** Constructing prompts to make behavior *as reliable as possible* despite the nondeterministic implementation (§1.2, TE §6.1). Determinism is impossible (§1.2 — the model is stochastic), but *reliability* is designable: ambiguity elimination (§4.6 — less for the nondeterminism to vary on), explicit output contracts (§4.4 — the output pinned §4.4), constraints stated (§4.2 — the behavior bounded), and structured/constrained outputs where the infrastructure supports them (forcing the output into a defined form, reducing variance). The discipline (§4.6, TE §6.1): design for reliability — remove the ambiguity (§4.6) and under-specification (§9.7) the nondeterminism (§1.2) exploits, constrain the output (§4.4) where possible, so the behavior is *reliable enough* (§6.4 — the pass-rate high, the variance bounded) for its use, accepting that perfect determinism (§1.2) is unattainable and managing the residual with robustness (§6.4) and verification (OE §8, TE §6.1).

# 5. Prompt Composition

Building prompts from reusable, composable parts — the discipline that makes a prompt *system* (§1.5) maintainable and evolvable, analogous to modular architecture (AE §3). The governing principle: **compose prompts from modular, reusable, layered parts — the stable system frame, the reusable role modules, the specific task — so prompts are maintainable (a part changed without rewriting the whole §5.2), reusable (the role library §5.3), and evolvable (§2.7), rather than monolithic instructions that can't be changed safely (§9.5 coupling).**

**5.1 — Layered prompting.** Composing prompts in *layers* by stability (§3 — system §3.1 stable, role §3.4 semi-stable, task §3.7 transient). Layered prompting (§3, mirroring layered architecture AE §5.5, layered context CX §3) means a behavior is instructed by the *composition* of its layers (the system frame §3.1 + the role §3.4 + the task §3.7). The discipline (§3, AE §5.5): layer by stability — the stable frame (§3.1) rarely changed, the task (§3.7) changed constantly, so a task change (§3.7) doesn't touch the frame (§3.1), and the frame's stability (§3.1) is preserved across countless task changes. Layered prompting is what makes the prompt system evolvable (§2.7 — change a layer without disturbing the others).

**5.2 — Modular prompts.** Composing from *modules* — reusable prompt-components (a role §3.4, a standard constraint-set §4.2, a standard output-format §4.4) that compose into complete prompts. Modular prompts (AE §3.2 — modules, applied to prompts) mean a prompt-component is written once and reused (§5.3), and changed in one place to update everywhere it's used (§2.6 — maintainability). The discipline (AE §3.2, §5.3): modularize the *reusable* (the standard roles §3.4, the common constraints §4.2, the recurring output formats §4.4) — so they're written once (§5.3), composed (§5.4) into prompts, and maintained centrally (§2.6 — a fix to the module fixes every prompt using it), while the *specific* (the task §3.7) stays inline (§10.8 reference-vs-inline).

**5.3 — Reusable prompts.** Prompt-components/complete-prompts used across many tasks/agents (§5.2 modules, and complete reusable prompts — a standard research prompt RE, a standard review prompt CR §3.8). Reusable prompts (the skills-as-prompts OE §7 — the memory-write skill, the research skill, the incident-response skill the red-team flagged) are the prompt-library — validated (§2.4, §6) once, reused reliably. The discipline (§5.6, §6): reusable prompts are *validated* (§6 — because their behavior is depended on across uses) and *contracted* (§1.4, §5.6 — their behavior is a promise callers rely on), so a reusable prompt is production software (§1.1 — built, tested §6, versioned §2.7, maintained §2.6) with many dependents (§5.6).

**5.4 — Composable prompts.** Prompts designed to *compose* — to combine (§5.1 layers, §5.2 modules) without conflict (§9.5 coupling — composable prompts don't fight each other §1.6). Composability (AE §4 — clean interfaces compose) requires each prompt-part having a clear boundary (§5.2 — what it instructs) that doesn't overlap/contradict others (§9 — a role prompt §3.4 that contradicts the system prompt §3.1 produces incoherent behavior §1.6). The discipline (§5.2, §1.6): design prompt-parts to compose cleanly — each with a clear scope (§5.2 — what it instructs), non-contradictory (§1.6 — coherent with the layers it composes with §5.1), so the composition (§5.4) produces coherent behavior (§1.6), not a fight between conflicting instructions (§9.5).

**5.5 — Prompt templates.** Reusable prompt-structures with slots for the specifics (a template for delegation §7.2 with slots for goal/inputs/constraints, a template for a job OE §7 with slots for schedule/task). Templates (§5.3 reusable-structure) capture the *structure* of a recurring prompt-type (the cold-brief structure FABLE §29, the review structure CR) with the specifics filled per-use. The discipline (§5.3, FABLE §29): template the *recurring structure* (the delegation cold-brief FABLE §29 — the standard slots §7.2; the job format OE §7), so recurring prompts are built from the validated template (§6 — the structure validated once) with the specifics filled — ensuring the recurring prompt-type is consistently well-structured (§7.2 — every delegation is a complete cold-brief FABLE §29 because the template ensures the slots).

**5.6 — Prompt inheritance.** Prompts that *inherit* from more general prompts (a specific role prompt §3.4 inheriting the system frame §3.1, a specialized research prompt inheriting the general research prompt RE). Inheritance (§5.1 layering as inheritance — the specific inherits the general's frame) means the specific prompt gets the general's instruction (the frame §3.1, the standard constraints §4.2) plus its specialization. The discipline (§5.1): inherit the stable general (§3.1 frame, §4.2 standard constraints) and specialize (the role §3.4, the task §3.7) — so the specific prompt is the general (inherited) plus its specialization, maintaining the general's guarantees (the frame's constraints §4.2 inherited) while adding the specific behavior.

**5.7 — Prompt chaining.** Composing prompts in *sequence* — one prompt's output (§4.4) feeding the next's input (a research prompt RE feeding a synthesis prompt, a plan prompt PE feeding execution prompts BE). Prompt chaining (OE — the orchestration of prompts in sequence) is how multi-step work is instructed (each step a prompt, chained). The discipline (§4.4, OE): chain by *output-contract matching* (§4.4 — each prompt's output §4.4 is the next's input, so the contract AE §4 between chained prompts holds), and handle the chain's failure (§6.1 — a step's bad output §4.4 corrupts the chain; verify OE §8 between steps where stakes warrant). Prompt chaining is prompt-composition-in-time (§5.4 composability across sequence).

**5.8 — Prompt orchestration.** Composing prompts into a full orchestrated system (OE — the orchestration engine, which orchestrates prompted agents). Prompt orchestration (OE) is the highest composition — the system of prompts (§3) driving a fleet of agents (OE §7), composed (§5.1–5.7) and orchestrated (OE) into coherent system behavior. The discipline (OE, §5): the prompt architecture (§1.5, §3) is orchestrated (OE) — the system prompt §3.1 frames, role prompts §3.4 specialize, task prompts §3.7 direct, chained §5.7 and orchestrated OE — so the whole system's behavior emerges from the composed, orchestrated prompt-system (§1.5), designed (AE) and maintained (§2.6) as the architecture it is.

# 6. Prompt Validation

Verifying prompts produce the right behavior reliably — testing prompts as the functional artifacts they are (RE §30, TE §6.2). TE §6.2 (testing prompts) is the seed; this is the full validation discipline. The governing principle: **validate prompts by exercising them on real and adversarial inputs, multiple times, and observing the behavior — because a prompt's behavior is nondeterministic (§1.2) and its quality is invisible in the text (a well-written prompt can behave badly TE §6.1), so validation is empirical [M2] behavioral testing, never a read-through.**

**6.1 — How prompts fail.** The failure modes (§9 anti-patterns, and the behavioral failures): *ambiguity* (§4.6 — the model interprets variably, producing inconsistent behavior §1.2); *under-specification* (§9.7 — the model fills gaps variably/wrongly); *missing constraints* (§9.2 — behavior violates unstated rules); *injection* (§6.5, SE §6.4 — untrusted input hijacks behavior); *drift* (§9.4 — accumulated edits degrade coherence §1.6); *over-specification* (§9.6 — brittle, fights capability §1.8); *model-mismatch* (§8 — behaves differently on a different model §8.8). The discipline (§9): know the failure modes (§9) so validation (§6) tests for them (§6.3 edges, §6.5 injection, §6.4 robustness) and construction (§4.5) prevents them.

**6.2 — Testing prompts.** Exercising the prompt on inputs and observing behavior (TE §6.2, RE §30 — test prompts like code). Testing prompts (TE §6.2): run the prompt on representative inputs (does it produce the right behavior §4.1), edge inputs (§6.3 — the awkward cases), and adversarial inputs (§6.5 — injection), multiple times (§6.4 — the nondeterminism §1.2 means one run isn't a test TE §6.1), observing the behavior [M2]. The discipline (TE §6.2, §2.4): test by exercising (TE §6.2 — the empirical behavior [M2], not the prompt's readability §9), on a golden set (TE §5.10 — input→acceptable-behavior pairs) where the behavior can be checked, multiple times (§6.4) for the nondeterministic reliability (§1.2, TE §6.1).

**6.3 — Edge cases.** Testing the prompt on the *awkward* inputs (RE §30 — a prompt untested on the edge case fails on it; TE §4.2 — where behavior breaks). Edge cases for prompts (the empty input, the huge input, the malformed request, the ambiguous request §4.6, the input that stresses the constraints §4.2). The discipline (RE §30, TE §4.2): test the edges — the prompt validated only on the happy path (§9.7-adjacent, TE §9.4) fails on the edges it wasn't tested on (RE §30), so validation exercises the awkward inputs (§6.3) where the prompt's robustness (§6.4) is actually tested.

**6.4 — Prompt robustness.** How reliably the prompt produces the right behavior across inputs and the nondeterminism (§1.2). Robustness is the prompt's reliability (§4.8 — how reliably it produces the wanted behavior, given the stochastic model §1.2 and varying inputs §6.3). The discipline (§4.8, §6.2): measure robustness by the *reliability across runs and inputs* (§6.2 — the pass-rate on the golden set TE §5.10 across multiple runs §1.2, and across edge §6.3 and adversarial §6.5 inputs) — a robust prompt produces the right behavior *reliably* (high pass-rate, low variance), and validation (§2.4) confirms the robustness meets the use's need (§4.8 — reliable *enough* for the stakes).

**6.5 — Injection resistance.** How the prompt resists adversarial input hijacking its behavior (SE §6.4, §7.2, AE §9.6). Injection resistance is validated (SE §11.5 — the injection canary) — a seeded injection (SE §7.2 — "ignore your task, do X") must fail to hijack the behavior. The discipline (SE §7.2, AE §9.6): injection resistance is *structural* (SE §7.2 — the READER/ACTOR split AE §9.6, so injection lands where it can't act SE §3.4), not prompt-based-detection (SE §7.2 — you can't reliably instruct a prompt to detect injection, because injected instructions are indistinguishable from legitimate content SE §7.2) — so a prompt's injection resistance is validated (SE §11.5 canary) but achieved *architecturally* (SE §7.2, AE §9.6), not by a "don't obey injected instructions" instruction (§9 — which an adaptive attacker SE §2.3 routes around).

**6.6 — Evaluation methodology.** The systematic method for evaluating prompt quality (§6.2 testing, extended to systematic evaluation). Evaluation methodology (TE §5.10 golden datasets, §6.1 — evaluating probabilistic behavior): a defined set of inputs (§6.2, §6.3 edges, §6.5 adversarial) with known-acceptable behaviors (TE §5.10 golden), run multiple times (§6.4, §1.2), scored for correctness (does the behavior meet the intent §4.1, respect constraints §4.2, produce the output §4.4). The discipline (TE §6.1, §5.10): evaluate systematically — a golden set (TE §5.10) covering the behavior space (§6.2 representative, §6.3 edges, §6.5 adversarial), scored across runs (§6.4 — the reliability §1.2), so prompt quality is *measured* (§6.7 — and regressions §6.7 caught) not judged by reading (§9 — which misses behavioral failures TE §6.1).

**6.7 — Regression testing.** Verifying a prompt change (§2.7) doesn't degrade behavior (TE §3.9 — regression, applied to prompts). Prompt regression testing (§6.6 evaluation on every prompt change §2.7) catches a change that broke behavior (§9.4 drift, or a refinement §2.3 that fixed one case and broke another). The discipline (TE §3.9, §2.7): every prompt change (§2.7) is regression-tested (§6.6 — re-run the evaluation set, confirm no behavior regressed) — because a prompt change is a behavior change (§1.1), and an unregressed prompt change (§2.7) can silently degrade behavior (§9.4) that the change didn't intend to touch. Prompt regression testing (§6.7) is what makes prompt evolution (§2.7) safe (TE §3.9 — the accumulated evaluation set guards against regression).

**6.8 — Prompt quality metrics.** What "good" means for a prompt (§6.6 — what's scored). Quality metrics (the properties §4 — reliability §6.4, robustness §6.4 across edges §6.3, injection-resistance §6.5, and the behavioral correctness §4.1/§4.2/§4.4). The discipline (§1.3, TE §1.3): the quality metric is *justified confidence in the behavior* (TE §1.3, [M20] — does the evaluation §6.6 justify trusting this prompt's behavior for its use) — not the prompt's length, readability, or cleverness (§9 — which don't measure behavior), but the *measured reliability of the right behavior* (§6.4, §6.6) across the inputs that matter (§6.2, §6.3, §6.5).

# 7. Multi-Agent Prompting

Prompting in a multi-agent system — the delegation, contracts, and coordination prompts that drive a fleet (OE §7). FABLE §29 (cold-brief) and OE §9 (delegation) are the seeds; this is the multi-agent prompt discipline. The governing principle: **every agent prompt is a cold-brief — self-contained, because the agent shares none of the delegator's context (CX §8.4) — with an explicit output contract, so the fleet's prompts compose into coherent coordinated behavior (OE §7) rather than a mesh of agents each guessing at what the others meant.**

**7.1 — Delegation prompts.** The prompt that delegates a task to an agent (OE §9, FABLE §29). Delegation prompts (OE §9) are the multi-agent workhorse — the orchestrator (OE §1.4) delegating via prompts. The discipline (FABLE §29, §7.2): a delegation prompt is a complete cold-brief (§7.2) — the agent gets everything it needs (§7.2 slots), because it shares no context (CX §8.4, OE §5.2). A delegation prompt that assumes shared context (§9 — "as we discussed") fails (OE §12 — the agent doesn't have it CX §8.4).

**7.2 — Cold-start prompts.** The cold-brief structure (FABLE §29, CX §8.4) — the delegation prompt (§7.1) built for a mind with no shared context. The cold-brief slots (FABLE §29, OE §9): *goal* (§4.1 — what to achieve), *inputs* (by reference ME — what to work on), *constraints* (§4.2 — what to respect), *context* (CX §4 — what it needs to know, minimal-sufficient CX §4.9), *done-when* (§4.4, BE §7.7 — how it knows it's done), *output format* (§4.4 — the form to return). The discipline (FABLE §29, §5.5): every agent prompt fills the cold-brief slots (§5.5 template — so no slot is forgotten), self-contained (CX §8.4, [M18] — would work handed to a stranger who wasn't in the conversation FABLE §29), because the agent is a cold start (CX §8.4 — it has only what the prompt gives it).

**7.3 — Agent contracts.** The contract a delegation prompt establishes (§1.4, AE §4.3) — what the agent will produce (the output §4.4) given its inputs (§7.2). Agent contracts (§1.4 — the prompt as contract) make the agent's behavior *composable* (OE §7 — the orchestrator relies on the agent's output-contract §4.4, so the agent's output feeds the next step §5.7 reliably). The discipline (§4.4, §1.4): the delegation prompt establishes a clear contract (§4.4 — the output the agent guarantees), so the orchestrator (OE §1.4) can compose (§5.7 — chain the agent's output into the next step) and verify (OE §8 — check the output against the contract §4.4). An agent without a clear output contract (§4.4, §9.7) produces variable output the orchestrator can't compose (OE §12 — the coordination failure).

**7.4 — Task decomposition (in prompts).** Prompting the decomposition of work into agent-tasks (PE §3, OE §3). Task decomposition prompts (PE, OE §3 — decompose into independent tasks, cold-brief each §7.2). The discipline (PE §3, OE §3.2): the decomposition (PE §3 — along seams, independent OE §3.2) determines the agent-prompts (each independent piece a cold-brief §7.2), so the prompts drive coordinated work (OE §7 — the pieces compose §5.7) — a bad decomposition (PE §3.4) produces agent-prompts that can't compose (OE §12 — the pieces don't fit, the coordination fails).

**7.5 — Context transfer (in prompts).** How context moves via the delegation prompt (CX §8.4, §2.5 — the transfer). The delegation prompt (§7.1) *is* the context transfer (CX §8.4 — the agent's context is constructed CX §4 from the cold-brief §7.2). The discipline (CX §8.4, §7.2): transfer context via the self-contained cold-brief (§7.2 — everything the agent needs in the prompt, because it shares none CX §8.4), sourced from durable memory (ME §8.6 — the inputs by reference, reconstructable §6 by the agent), so the transfer is complete (§7.2) and model-independent (ME §8.6 — any agent-model reconstructs its context CX §6 from the brief).

**7.6 — Output contracts.** The output specification (§4.4) as the agent's contract (§7.3, §1.4). Output contracts (§4.4 — what the agent returns) are what make agent output *usable* (§5.7 — composed, OE §7) and *verifiable* (OE §8 — checked against the contract §4.4). The discipline (§4.4, §7.3): specify the output contract explicitly in every agent prompt (§4.4 — the form and content OE §8.2 "return the list + reasons," structured output where the infrastructure supports it §4.8) — so the fleet's outputs compose (§5.7) and verify (OE §8) reliably, the coordination (OE §7) resting on the output contracts (§7.6) holding.

**7.7 — Review loops.** The prompts driving the verify-fix cycle (OE §8, §9.9, CR §3.8). Review loops (OE §8.9 — producer produces, verifier §3.8 checks, producer fixes, re-verify) are driven by prompts (the producer's execution prompt §3.7, the reviewer's review prompt §3.8, looped). The discipline (OE §8, §3.8): the review prompts (§3.8) are independent (OE §8.1 — the reviewer a different context CX §3.5 than the producer) and adversarial where stakes warrant (§6.5-stance, RE §9.5, CR §9 — prompted to find fault OE §8.2), so the review loop (OE §8.9) actually catches defects (CR — hunts, not confirms CR §10.3), the loop's prompts driving the rigor (OE §8).

**7.8 — Escalation.** The prompts for escalating beyond the fleet (OE §8.5, §9.1 — to a more capable tier, more verifiers, or the human SE §4.9). Escalation prompts (OE §8.5) drive the fleet to escalate an inconclusive/high-stakes situation (OE §8.5 — verification inconclusive, a decision the human must make DE §10.6). The discipline (OE §8.5, SE §4.9): the fleet's prompts include escalation triggers (OE §8.5 — when to escalate: inconclusive verification OE §8.5, irreversible action needing human approval SE §4.9) — so the fleet escalates (OE §8.5) rather than proceeding past unresolved doubt ([M16]) or acting unapproved (SE §4.9), the escalation prompts (§7.8) embodying the "don't proceed on unresolved doubt" discipline (OE §8.5).

# 8. Multi-Model Prompting

Prompting across different models — the discipline that makes prompts work on the model of today and the model of 2035. RE §30 (write model-agnostic) is the seed; this is the multi-model/future-proof prompt discipline. The governing principle: **write prompts model-agnostically — for a competent stranger-intelligence (§1.6), not for one model's quirks — because models churn (AE §9.1, FABLE §15) and a prompt overfit to today's model (§8.8) breaks on tomorrow's, so a prompt is durable interface (§1.2) only if it depends on capability the successor will also have, never on the current model's idiosyncrasies.**

**8.1 — Claude / GPT / Gemini / open-weight (prompting across specific models).** Different models have different characteristics (instruction-following styles, strengths, quirks). The discipline (§8.7, RE §30): prompt to the *capability* the models share (§8.6 — the competent-intelligence behavior any strong model produces), not to a specific model's quirk (§8.8 — a prompt exploiting Claude's specific behavior breaks on GPT/Gemini/open-weight). Where a specific model's characteristic must be accommodated (a known difference), it's a documented, minimal accommodation (§8.7), not the prompt's foundation — so the prompt works across models (§8.6) with model-specific tuning as a thin adjustment, not a rewrite. *(This section names the models of 2026; per §8.8 and RE §30, the prompt discipline is model-agnostic precisely so it survives the models that replace them.)*

**8.5 — Capability routing (in prompts).** Routing tasks to models by capability (OE §4, PE §8.1 — the task's dominant demand to the right model tier). Capability routing (OE §4) means the *prompt* is matched to the model's capability (a hard-reasoning prompt to a reasoning tier OE §4.1, a mechanical prompt to a fast tier). **8.6 — Model specialization / provider independence.** Writing prompts that don't depend on a specific model/provider (RE §30, AE §9.2 — the gateway seam). Provider independence (AE §9.2, §7.6-security) means the prompt works through the gateway (AE §9.2 — on whatever model is routed), not coupled to a provider (§9.8 provider-lock-in). The discipline (RE §30, AE §9.2): write for provider independence — the prompt depends on *capability* (§8.6 — what any competent model does), not a provider's specific behavior (§9.8 — which locks the prompt to that provider), so the prompt is portable across providers (AE §9.2 — the model swappable behind the gateway), and the system's provider-agnosticism (AE §9.2, ADR-010) extends to its prompts (§8.8 — the prompts don't re-introduce the lock-in the gateway removed).

**8.7 — Future-proof prompting.** Writing prompts that will work on models that don't exist yet (§8.8, AE §9.9, FABLE §15). Future-proofing (RE §30, §1.6 — write for the competent stranger-intelligence) means the prompt depends on capability a *better future model* will also have (§8.6 — general competent behavior), not on the current model's specific quirks (§8.8) or limitations (a prompt working around a current model's weakness §8.8 may be unnecessary or wrong on a future model that lacks the weakness). The discipline (TE §6.9, §2.6): on model replacement (AE §9.2), re-validate the prompts (TE §6.9 — the parity test, the prompts run on the new model, behavior confirmed) — because a prompt validated on the old model (§2.4) isn't automatically valid on the new (§8.1 — models differ), so model replacement (AE §9.2) includes prompt re-validation (§2.6 maintenance, TE §6.9), and a model-agnostic prompt (§8.6) passes this cheaply (it depended on shared capability §8.6, not the old model's quirk §8.8) while an overfit prompt (§8.8) requires rework.

# 9. Prompt Anti-Patterns

Named for in-flight detection. Each carries its signal and cure. These are how prompts fail — producing unreliable, unsafe, or brittle behavior (§1.2, §6.1).

**9.1 — Verbose prompts.** A prompt bloated with unnecessary instruction (§4.7 violated). *Signal:* the prompt is long; the load-bearing instructions (RE §30) are buried in the verbiage; much of it is unneeded (§4.2 noise-equivalent). *Cure:* minimal-sufficient (§4.7 — everything the behavior needs, nothing it doesn't); place the load-bearing instruction where attention is highest (RE §30 — first/last, not buried); cut the rest (§4.7). Verbose prompts bury the signal (RE §30 — the model attends less well to the load-bearing instruction buried in verbiage) and waste context (CX §5.10), degrading behavior (§6.4 — less reliable, the key instruction diluted).

**9.2 — Missing constraints.** A prompt omitting constraints the behavior must respect (§4.2 violated). *Signal:* behavior that violates a rule the prompt didn't state (a safety rule SE §7, an invariant AE §2.6, an operator constraint ME §3.6 the model wasn't told). *Cure:* constraint extraction (§4.2 — include the load-bearing constraints the behavior could violate). Missing constraints produce behavior that breaks rules the model wasn't told to respect (§4.2 — the model can't respect a constraint it wasn't given), a common and dangerous failure (SE — a missing safety constraint is unsafe behavior).

**9.3 — Hidden assumptions.** A prompt resting on assumptions not stated ([M1], §4.5-adjacent, CX §9.5). *Signal:* behavior correct only under an unstated assumption (the model assumed something the prompt didn't specify, and assumed differently than intended §1.2). *Cure:* make assumptions explicit (§4.6 — state what's meant, don't assume the model infers it §1.2); eliminate ambiguity (§4.6). Hidden assumptions in prompts are gaps the nondeterministic model (§1.2) fills variably (§9.7 under-specification's mechanism) — the prompt assumed the model would infer X, and it inferred variably.

**9.4 — Prompt drift.** A prompt degrading through accumulated edits (§2.6, TE-adjacent). *Signal:* a prompt edited many times, losing coherence (§1.6 — contradictory accumulated instructions), no longer matching its intent (§4.1); behavior degraded from edits nobody regression-tested (§6.7). *Cure:* version control (§2.7) and regression testing (§6.7 — every edit re-validated §6.6); periodic coherence review (§1.6 — the prompt re-read as a whole, contradictions §9-resolved); refactor a drifted prompt (§2.3 — reconstruct it coherent §1.6 rather than patch further). Prompt drift is the accumulated-edit decay (§2.6 — an unmaintained prompt degrading), prevented by versioning (§2.7) and regression (§6.7).

**9.5 — Prompt coupling.** Prompts that depend on each other in hidden ways (§5.4 violated, AE §10.8-analog). *Signal:* changing one prompt breaks another's behavior (a shared assumption §9.3 between prompts, an implicit dependency §5.4); prompts that can't be changed independently (§5.2 — coupled, not modular). *Cure:* composability (§5.4 — clean prompt boundaries §5.2, non-contradictory §1.6), modular design (§5.2 — each prompt-part independent). Prompt coupling makes the prompt system unmaintainable (§2.6 — a change ripples unexpectedly), the prompt-analog of hidden coupling (AE §10.8).

**9.6 — Over-specification.** A prompt dictating the *how* the model should determine (§1.8 violated, §4.7). *Signal:* the prompt over-specifies internal steps/method the model could determine better; brittle behavior (§9.10 — coupled to the specified approach, failing when it doesn't fit). *Cure:* specify the *what* (§4.4 — the behavior/output), leave the *how* to the model (§1.8 — its capability), unless the how is itself required (SE §4.9 — a mandated process). Over-specification brittles the prompt (§9.10) and fights the model's capability (§1.8 — dictating what the model could do better), reducing behavior quality (the model constrained to a specified-but-suboptimal approach).

**9.7 — Under-specification.** A prompt too vague to produce reliable behavior (§4.7, §1.3 violated). *Signal:* variable behavior (§1.2 — the model fills the unspecified gaps variably); output that doesn't match what was wanted (§4.4 — the output unspecified, so variable); the model "usually" does what was meant but not reliably (§6.4 — low robustness from the under-specification). *Cure:* complete specification (§1.3, §4 — intent §4.1, constraints §4.2, output §4.4 all specified), ambiguity elimination (§4.6). Under-specification is the opposite of over-specification (§9.6) — too little, leaving the nondeterminism (§1.2) to fill gaps; both miss minimal-sufficient (§4.7 — the sweet spot between them).

**9.8 — Provider lock-in.** A prompt coupled to a specific provider/model (§8.6 violated). *Signal:* the prompt depends on a provider's specific behavior/quirk (§8.1); it breaks on another provider/model (§8.8); the system's provider-agnosticism (AE §9.2) undermined by prompts that lock in. *Cure:* provider independence (§8.6 — write for capability §8.6, not provider quirk §8.1), future-proofing (§8.7 — for the competent stranger-intelligence §1.6). Provider lock-in in prompts re-introduces the lock-in the gateway (AE §9.2) removed — the model is swappable (AE §9.2) but the prompt isn't (§9.8), so the swap breaks the behavior (§8.8).

**9.9 — Tool leakage.** A prompt exposing/assuming tool internals it shouldn't (AE §10.3-analog, SE §7.6). *Signal:* a prompt that assumes a tool's internal behavior (coupling §9.5 to the tool's implementation, not its contract §3.5), or that leaks tool capability inappropriately (SE §7.6 — a prompt granting an agent tool-awareness beyond its role §3.4, SE §12.8 over-permissioned). *Cure:* tool prompts by contract (§3.5, AE §4.1 — the tool's contract, not its internals), scoped by role (SE §7.6 — the agent's tool-awareness matches its role §3.4, least privilege SE §1.5). Tool leakage couples prompts to tool internals (§9.5) or over-exposes capability (SE §7.6), both failures of the tool-interface discipline (§3.5).

**9.10 — Prompt brittleness.** A prompt that works narrowly but fails outside its tested cases (§6.4 low robustness, §9.6 over-specification's result). *Signal:* the prompt works on the cases it was built for but fails on variations (§6.3 edges), inputs (§6.3), or models (§8.8) it wasn't; low robustness (§6.4). *Cure:* robustness validation (§6.4 — tested across edges §6.3, inputs, models §8.8), minimal-sufficient not over-specified (§4.7, §9.6 — over-specification brittles), model-agnostic (§8.6 — so it's not brittle to model change §8.8). Prompt brittleness is low robustness (§6.4) — a prompt that works in its narrow tested envelope and fails outside it, cured by building and validating for robustness (§6.4) across the full envelope (§6.3, §8.8).

# 10. Prompt Decision Trees

Built per [M7 → skill S-007]. Prompt-specific; defer to prior engines where the decision is theirs.

**10.1 — Prompt vs Tool**
```
Is the behavior needed DETERMINISTIC (a fixed operation) or REASONED (requires intelligence judging §1.2)?
  ├─ deterministic (a fixed transformation, a known operation) → TOOL (a deterministic capability, MCP AE §9.10 — reliable,
  │     not subject to the nondeterminism §1.2; don't use a prompt where a tool's determinism is wanted §2.1)
  └─ reasoned (requires the model to judge, decide, adapt §1.2) → PROMPT (§1.1 — instruction to an intelligence)
       (rule: prompt the reasoning, tool the mechanical — a prompt for what should be a tool §2.1 is nondeterminism applied to the deterministic)
```

**10.2 — Prompt vs Workflow**
```
Is this a SINGLE reasoned behavior, or an ORCHESTRATED sequence of steps? (§5.7, OE)
  ├─ single behavior → PROMPT (§1.1 — one instruction to an intelligence)
  └─ orchestrated sequence (multiple steps, deterministic control flow OE) → WORKFLOW (OE — orchestrated prompts §5.8,
        deterministic where the flow should be deterministic OE, prompts §1.1 where reasoning is needed)
   (rule: prompt the reasoning steps, workflow the orchestration OE — the workflow is the deterministic control flow, the prompts are its reasoning steps)
```

**10.3 — Prompt vs Skill**
```
Is this a ONE-OFF instruction, or a REUSABLE capability used repeatedly? (§5.3)
  ├─ one-off → inline PROMPT (§10.8 — the specific task, inline §3.7)
  └─ reusable (a capability used across tasks/sessions — research RE, review CR §3.8, incident-response) → SKILL
        (a reusable prompt §5.3, validated §6 once, versioned §2.7, invoked repeatedly — the skills-as-prompts OE §7)
   (rule: a reusable prompt §5.3 is a skill — built, tested §6, maintained §2.6 as production software §5.3, with dependents §5.6)
```

**10.4 — Prompt vs Memory**
```
Is this INSTRUCTION (what to do) or KNOWLEDGE (what's true/known)? (§1.1 vs ME §1.1)
  ├─ instruction → PROMPT (§1.1 — how to behave)
  └─ knowledge → MEMORY (ME — what the system knows, retrieved ME §5 into context CX §4 the prompt directs behavior over)
   (rule: the prompt instructs the behavior §1.1; memory ME provides the knowledge CX §4.3 the behavior reasons over — they're paired §4.3, not substitutes)
```

**10.5 — Prompt vs Context**
```
Is this INSTRUCTION (what to do) or INFORMATION (what to reason over)? (§1.1 vs CX §1.1)
  ├─ instruction → PROMPT (§1.1 — the directive)
  └─ information → CONTEXT (CX §4 — the working set the prompt's behavior reasons over)
   (rule: the prompt says what to do §1.1, the context CX provides what to do it with CX §4 — construct both §4.3, the prompt over the context)
```

**10.6 — Single agent vs Multi-agent (prompting)**
```
Does the work fit one prompted mind, or need multiple coordinated agents? (OE §3.1, §13.1)
  ├─ one mind → SINGLE prompt (§1.1 — the task to one agent; don't over-orchestrate OE §1.3)
  └─ multiple (independent parallel work OE §3.2, or independent verification OE §8) → MULTI-AGENT prompting (§7 —
        cold-brief each §7.2, output contracts §7.6, composed OE §7); defer to OE §13.1 for the single-vs-multi decision
```

**10.7 — One prompt vs Prompt chain**
```
Is this one reasoning step, or multiple steps where each feeds the next? (§5.7)
  ├─ one step → ONE prompt (§1.1)
  └─ multiple dependent steps (each's output §4.4 feeds the next's input) → PROMPT CHAIN (§5.7 — chained by output-contract
        matching §4.4, verified OE §8 between steps where stakes warrant); or a workflow §10.2 if the orchestration is complex
```

**10.8 — Reference vs Inline (prompt composition)**
```
Is this prompt-content REUSED across prompts, or SPECIFIC to this one? (§5.2)
  ├─ reused (a standard role §3.4, common constraints §4.2, a recurring structure §5.5) → REFERENCE a module/template
  │     (§5.2, §5.5 — written once, composed §5.4, maintained centrally §2.6)
  └─ specific (this task §3.7, this instance) → INLINE (§3.7 — the specific instruction in the prompt directly)
   (rule: reference the reusable §5.2 for maintainability §2.6, inline the specific §3.7 for clarity — the same reference-vs-inline discipline as CX §5.3)
```

**12.9 — A model replacement.**

- *Process (§8.8):* re-validate (TE §6.9) → identify behavior differences (§8.1 — where the new model behaves differently) → adjust the few prompts that need it (§8.7 — minimal accommodation, not rewrite) → confirm robustness (§6.4) on the new model.
- *Tradeoff:* the model-agnostic discipline (§8.6) paid its cost up front (writing for capability not quirk §8.8, which is sometimes less-optimized for the current model) and is repaid at replacement (§8.8 — the swap is cheap re-validation TE §6.9, not a prompt rewrite), which over a decade of model changes (FABLE §15) is the winning trade [M15].

**12.10 — A future AI model that does not exist today.**
- *The ultimate future-proofing test (§8.7, [M18]):* prompts must work on a model that doesn't exist yet (AE §9.9 — the successor, FABLE §15 — the frontier of 2030+).
- *Design (§8.7, §1.6):* write for the *competent stranger-intelligence* (§1.6, [M18]) — depend on capability a better future model will also have (§8.6 — general competent reasoning), not on today's model's quirks (§8.8 — which the future model may not share) or limitations (§8.7 — workarounds for today's weaknesses may be unnecessary/wrong on a future model without them).
- *Validation (§2.4, TE §6.9):* the prompt can't be validated on the nonexistent model (§6 — no model to test on yet), so it's designed for *robustness to model change* (§6.4, §8.6 — model-agnostic, capability-based) and *re-validated when the future model arrives* (§8.8, TE §6.9 — the parity test on the new model).
- *The deepest tradeoff (§8.7, FABLE §15):* a prompt overfit to today's model (§8.8) is more-optimized *now* and *broken later* (§8.8 — on the future model); a model-agnostic prompt (§8.6) is less-optimized-now and *works later* (§8.7) — and for a decade-long system (Law 10) across many model generations (FABLE §15), the model-agnostic prompt wins ([M15] — the ten-year carrying cost), because the prompt is durable interface (§1.2) to intelligence, and the intelligence will keep changing (FABLE §15) while the prompt (§8.7 — written for capability §8.6) endures.
- *Why this matters most:* this is the prompt-engineering expression of the whole extraction's premise (AE §9.9 — design for the successor) — a prompt written for the competent stranger-intelligence (§1.6) is a prompt that a future model, reading it, executes correctly *as if it were written for it* — which is exactly what these documents are: instructions written for a future intelligence (this extraction set §1.6, [M18]) that does not exist as I write them, designed to be executed correctly by whatever mind reads them (AE §9.9). The prompt engine, at its limit, is the discipline of instructing minds you'll never meet — which is the discipline this entire extraction embodies.
